# План реализации csqtt-cli

Пошаговый план к `architecture.md`: решения Р1–Р8, правки ядра П1–П6, этапы Э0–Э5 — там.
Здесь — задачи, их порядок и признак готовности.

Как пользоваться:

- **Задача** — одна логическая правка и, как правило, один коммит. Номер задачи — буква
  этапа и число (`F3`, `C7`). На него ссылаются коммиты и журнал этапа.
- **Журнал этапа** — `doc/local/plan-eN.md`, в git не входит: ход работы, окружение,
  живые прогоны, решения по ходу. Сюда переносятся только итоги, без дат и окружения.
- **Готово, когда** — проверяемое условие: тест, команда или живой прогон. Задача без него
  не закрывается.
- **Живые прогоны** — короткие: один сценарий, проверка, уборка. Обрыв туннеля, через
  который идёт связь машины, — только с согласия пользователя.
- **Перенос из qwdtt-cli** — это копирование, переименование и тесты. Каждый перенесённый
  файл проверяется на код, пришедший из qWDTT или из Android-клиентов (§11 архитектуры):
  такой код не переносится, а пишется заново.

Оценки — в рабочих днях, грубо.

```
Э0 фундамент ──▶ Э1 socks ──▶ Э2 Windows tun ──▶ Э4 меню и релиз ──▶ Э5 auto_js
                     │
                     └──────▶ Э3 Linux tun ───────┘
```

Э2 и Э3 независимы друг от друга, оба опираются на Э1. Э4 нужен хотя бы один `tun`.

## Э0. Фундамент — 2–3 дня

Цель: репозиторий собирается, ядро вендорено и собирается, перенесённые пакеты проходят
тесты. Сети и сервера ещё не нужно.

### F1. Модуль и каркас

- `go.mod`: `github.com/FreedomCats/csqtt-cli`, та же версия Go, что в qwdtt-cli.
- `cmd/csqtt-cli/main.go` — заглушка с `version` и списком команд.
- `README.md` — две строки: что это и что проект в разработке.

**Готово, когда** `go build ./...` и `go vet ./...` проходят.

### F2. Вендор ядра — `scripts/vendorcore`

- Перенести движок правил из qwdtt-cli (`rules.go`: шаблон, замена, обязательное число
  совпадений). Преобразования Go-файлов (`convert.go`) не нужны: ядро копируется как есть.
- Копируются `rust-client/` и `shared/` апстрима. Исключаются сборочные скрипты под Android
  (`build_android_abis.ps1`, `build_so.bat`). Пути `#[path = "../shared/…"]` остаются
  рабочими: `core/rust-client` и `core/shared` лежат рядом.
- `core/CORE_VERSION`: адрес апстрима, коммит, версия из `Cargo.toml`, ревизия протокола.
- `-check` сверяет `core/` со снимком апстрима плюс правила; лишний или изменённый файл —
  ошибка с именем файла.
- Правил пока нет — набор пустой, но движок и тесты на нём уже работают.
- `scripts/internal/script` из списка F4 переносится здесь: команда на нём стоит.

**Готово, когда** `go run ./scripts/vendorcore` кладёт ядро 2.1.9 из свежего клона,
`-check` проходит, а ручная правка любого файла в `core/` его роняет. Тесты движка —
перенесённые из qwdtt-cli.

### F3. Сборка ядра — `scripts/buildcore`

- Обёртка над `cargo build --release --target <цель>` в `core/rust-client`. Бинарь `client`
  копируется в `build/out/csqtt-core[.exe]`. Цели: `x86_64-pc-windows-msvc`,
  `x86_64-unknown-linux-*`, `aarch64-unknown-linux-*`.
- Проверка тулчейна до сборки: версия `rustc` не ниже `rust-version` из `Cargo.toml`,
  понятная строка вместо ошибки cargo.
- Выяснить и записать в архитектуру (§09а, §09б):
  - что нужно `aws-lc-rs` на Windows и Linux (компилятор C, CMake, NASM);
  - собирается ли `musl` и кросс-сборка под `arm64`; если нет — `gnu`, и какая минимальная
    glibc;
  - не мешают ли участки под `cfg(target_os = "android")` (`udp_batch.rs`).
- `cargo test` ядра: какие тесты требуют живого сервера (`turn_integration_tests.rs`
  ходит в сервер под WSL) — их отделить флагом или фильтром.

**Готово, когда** `go run ./scripts/buildcore` собирает `csqtt-core` под Windows и Linux
`amd64`, `cargo test` без сетевых тестов проходит, а `csqtt-core --validate-vk-hashes
-peer 127.0.0.1:1 -password x -vk <выдуманный хеш>` печатает строку `HASH_CHECK:`.

### F4. Перенос пакетов, не зависящих от ядра

Из qwdtt-cli — с переименованием всего, что видно системе: имя адаптера, мьютекс второго
запуска, абстрактный сокет блокировки, таблица nftables, каталог настроек, записи
resolvconf, префикс секретов.

| Пакет | Что переносится | Что нет |
|---|---|---|
| `netguard` | всё: привязка своих сокетов, выбор интерфейса, `watch.go` | — |
| `winsys`, `linuxsys` | всё | — |
| `sudo`, `secretservice` | всё | — |
| `app` | имя программы — от него все имена в системе | — |
| `config` | каталог настроек (`dir.go`), `owner`, `secret*` | `load`, `save` — в C7: завязаны на схему профиля; `profile`, `validate`, `sharelink` — пишутся заново в C7 |
| `captcha` | `open*`, `profile`, `proxy` | окна (`webview2_windows`, `browser_linux`, `cdp`, `manual`) — в C9: стоят на `Request` и перехвате токена из `solver.go` и `token.go`, а те из Android-клиента qWDTT и пишутся заново |
| `cli` | — | `prompt`, `pause*`, `elevate*`, `elevated*` — в C10 вместе с `root.go`: это методы его `env` |
| `scripts` | `internal/script`, `internal/wintun`, `wintun`, `checktunnel` (без раздела `external`), `ctrlbreak`, `distcheck`, `sha256sums` | `release`, `notices` — в I3 |

Форк `tailscale-wf` — тем же `replace`; `go-webview2` придёт с окном капчи в C9.

Постоянные значения, по которым программа узнаёт свои следы в системе, — свои, не
унаследованные: GUID адаптера (`winsys.AdapterGUID`), GUID провайдера и подслоя WFP, метка
сокетов `SO_MARK` (`0x1075`). Обе программы могут стоять на одной машине, и одна не должна
принимать чужие фильтры и адаптер за свои. Имена (адаптер, мьютекс и абстрактный сокет
блокировки, таблица nftables, каталог настроек, записи resolvconf, метки секретов) идут от
`app.Name`.

**Готово, когда** `go test ./...` проходит на Windows и Linux, `-race` — тоже, а
`git grep -i qwdtt` находит только упоминания проекта-основы в документации.

### F5. CI

Два workflow, как в qwdtt-cli: Windows и Linux. В каждом — `go vet`, `go test`,
`vendorcore -check`, `buildcore`, `buildcore -test`. Кэш cargo. Linux — на раннере с glibc
старше 2.38 (`ubuntu-22.04`, §09б архитектуры). Ядро под Linux в F3 собрано и проверено
cargo напрямую; сам `buildcore` под Linux впервые запускается здесь.

**Готово, когда** оба workflow зелёные на ветке `main`.

Итог: `.github/workflows/windows.yml` и `linux.yml`. В каждом задание `test` (Go) и
`core`: апстрим скачивается на коммите из `core/CORE_VERSION`, затем `vendorcore -check`,
`rustup update stable` (образ раннера может отставать от `rust-version` ядра), кэш cargo
(реестр и `build/cargo`), `buildcore`, `buildcore -test`. На Linux `go test -race` идёт с
`CSQTT_TEST_DBUS=1`; тесты `linuxsys`, меняющие сеть, — заданием `netns` в контейнере
(`CSQTT_TEST_NETNS=1`, пропуск — провал). `core` на `ubuntu-22.04` проверяет потолок glibc 2.35.
Если апстрим перепишет историю и коммита не станет, `core` упадёт на первом шаге: пора
обновлять ядро. Репозиторий на GitHub пока приватный, публичным станет в I5.

Первый прогон — оба зелёные. Ядро, собранное на `ubuntu-22.04`, требует glibc не новее 2.34.
На Windows задание `core` без кэша идёт около 17 минут, на Linux — около 7.

## Э1. Подключение без прав — `socks` — 6–8 дней

Цель: `csqtt-cli connect -datapath socks` на Windows и Linux, браузер через SOCKS5 ходит
в сеть через сервер CSQTT.

### C0. Сервер для проверок

Сервер CSQTT 2.1.9 на VPS — ставит пользователь (`deploy.sh` или Docker из апстрима),
рядом с сервером qWDTT, на своём порту. Адрес, пароль и хеши — только в профиле и в
журнале этапа.

**Готово, когда** Android-приложение CSQTT подключается к этому серверу.

### C1. Процесс ядра — `internal/coreproc`

- `Config` → аргументы ядра (таблица §04 архитектуры). Нормализация воркеров — здесь же,
  с тестами на те же значения, что в тестах ядра (`main.rs`, `worker_count_tests`).
- Разбор вывода: события `__CSQTT_EVENT__|…`, `CAPTCHA_SOLVE|…`, `HASH_CHECK:…`, прочее —
  журнал. Неизвестное событие — строка журнала, а не ошибка.
- Запуск: каналы stdin, stdout и stderr, `CSQTT_EVENTS=1`. На Windows — Job Object с
  `KILL_ON_JOB_CLOSE`, ядро без своего окна консоли. На Linux — `Pdeathsig: SIGKILL`.
- Остановка: `STOP`, ожидание 3 с, затем принудительно. Ctrl+C в консоли ядру не
  доставляется — останавливает оболочка (урок `ctrlbreak` из qwdtt-cli).
- Тесты — на поддельном ядре: тот же тестовый бинарь в роли дочернего процесса (приём
  `TestHelperProcess`) печатает записанные строки настоящего вывода.

**Готово, когда** тесты проходят, включая два сценария: смерть оболочки убивает ядро, а
ядро, не ответившее на `STOP`, завершается принудительно.

Итог: `internal/coreproc`. `Config.Args`, `NormalizeWorkers`, `ParseLine` (события,
`CAPTCHA_SOLVE`, `HASH_CHECK`, остальное — `Log`), `Start`, `Send`, `Stop`, `Wait`. Пароль и
хеши пока идут аргументами, в stdin их переносит C2. Поддельное ядро — тестовый бинарь
(`TestMain` по `CSQTT_FAKE_CORE`): образцы вывода в формате ядра, ядро, глухое к stdin, и
оболочка, которую убивают. Оба сценария проверены и обратной правкой: без
`KILL_ON_JOB_CLOSE` или без `Pdeathsig` тест смерти оболочки падает, без своей группы
процессов падает тест группы. `TestRealCore` (`CSQTT_TEST_CORE=<путь к csqtt-core>`) гоняет
настоящее ядро без сервера: `PROCESS`, журнал, `STOPPED` и выход по STOP. В CI он идёт
после `buildcore`. Образцы настоящего вывода с живым сервером (`CONFIG`, `READY`, `STATS`)
снимаются в C11.

### C2. П1 — секреты через stdin

- Правило `vendorcore`: флаг `-secrets-stdin`; первая строка stdin —
  `SECRETS:<base64 json>` с `password` и `vk`. Без флага поведение прежнее. При `auto_js`
  строка `VK_JS_BOOTSTRAP:` идёт следом.
- Тест на Rust в ядре: разбор, слишком длинная строка, мусор, отсутствие строки за 15 с.
- `coreproc` передаёт секреты только так.

**Готово, когда** тесты проходят и в командной строке запущенного ядра нет ни пароля, ни
хешей (проверка — `Win32_Process.CommandLine`, `/proc/<pid>/cmdline`).

Итог: модуль ядра `secrets_stdin.rs` — наш файл, `vendorcore` кладёт его в `core/` из
`scripts/vendorcore/files/`. Четыре правила-вставки в `main.rs` подключают модуль и флаг.
Секреты читаются до рантайма через общий буфер `std::io::stdin()`, поэтому следующие
строки (`VK_JS_BOOTSTRAP:`, команды) не теряются. Тесты на Rust: разбор, необязательный
`vk`, слишком длинная строка, мусор без эха значений, не UTF-8, тайм-аут, секреты в
аргументах вместе с флагом. `coreproc` передаёт `--secrets-stdin` и пишет
`Config.SecretsLine` первой строкой. `TestRealCore` проверяет командную строку ядра
(`Win32_Process.CommandLine`, `/proc/<pid>/cmdline`), `TestRealCoreSecretsThenStop` — что
STOP, пришедший одной записью с секретами, доходит до ядра. Обратные правки: со своим
буфером stdin STOP теряется, с паролем в аргументах ядро не стартует — тесты падают.
Проверено на Windows и Linux. Попутно `buildcore` стал сохранять бит исполнения у
`csqtt-core`: `script.CopyFile` переносит права исходника.

### C3. П2 — закреплённый отправитель на loopback

- Правило: флаг `-listen-peer <адрес>`. Ядро принимает датаграмы только от этого адреса и
  отвечает только ему; чужие — отбрасываются и считаются. Свой порт ядро сообщает событием
  (или полем `CONFIG` — что окажется проще).
- Тест на Rust: чужой датаграм не меняет адресата ответов.

**Готово, когда** тест проходит, а без флага поведение прежнее.

Итог: модуль ядра `listen_peer.rs` — наш файл из `scripts/vendorcore/files/`, как
`secrets_stdin.rs`. С `-listen-peer <IP:порт>` задача чтения UDP диспетчера принимает
датаграмы только с этого адреса, чужие отбрасывает и считает (в журнал — 1-й, 2-й, 4-й…),
а адресат ответов закреплён с самого старта — ответ уходит оболочке и до её первого
датаграма. Без флага `PeerGate::admit` делает то же, что апстрим: адресат — последний
отправитель. Флаг с `-tun-uds`, адрес без порта, с портом 0 или `0.0.0.0` — отказ
стартовать. Свой порт ядро сообщает событием `LISTEN {port}` (в режиме `-tun-uds` его
нет). Одиннадцать однострочных правил: в `main.rs` — модуль, флаг, его нормализация,
разбор, вызов диспетчера и событие; в `dispatcher.rs` — `start_with_peer` (прежний `start` —
обёртка без закрепления для тестов апстрима), передача фильтра в задачу чтения и фильтр
вместо запоминания отправителя. Тесты на Rust: разбор флага, счёт чужих, событие и
три теста на настоящем диспетчере с двумя сокетами — чужой датаграм не попадает в туннель
и не уводит ответы, ответ закреплённому адресату до его первого датаграма, без флага ответы
идут последнему отправителю. Обратная правка (поведение апстрима при флаге) — оба теста на
закрепление падают. `coreproc`: `Config.ListenPeer` → `--listen-peer`, `ListenEvent`;
`TestRealCore` ждёт `LISTEN` и проверяет, что порт занят сокетом ядра. Проверено на Linux.

### C4. П5 — ручная капча 180 секунд

Правило в `captcha.rs`: время ручного окна — 180 с.

**Готово, когда** правило проходит `vendorcore -check`, а тест ядра на цепочку капчи не
сломан.

Итог: три правила в `captcha.rs` — константа `MANUAL_WEBVIEW_TIMEOUT` (180 с), она же в
вызове ручного окна в конце цепочки `auto`, и подключение тестового модуля
`captcha_window_tests.rs` (наш файл, дочерний к `captcha.rs`, чтобы видеть закрытый
`webview`). Тесты на виртуальных часах tokio: токен, пришедший через 179 с, принят; без
ответа окно закрывается ровно через 180 с. С прежними 60 с тест на 179 с падает. Внешних
ограничений короче окна нет: `auth.rs` ждёт решения без тайм-аута. Ядро не сообщает
оболочке, что время окна вышло, — окну оболочки (C9) нужен свой срок в 180 с.

### C5. Канал пакетов — `datapath/link.go`

- Сокет оболочки на `127.0.0.1:0`; на Windows — `SO_EXCLUSIVEADDRUSE`.
- Чтение и запись сырых IP-пакетов, счётчики сброшенных, отбрасывание IPv6 и не-IP
  пакетов в сторону адаптера.
- Тесты: обмен с поддельным ядром, переполнение, закрытие.

**Готово, когда** тесты проходят под `-race`.

Итог: `datapath.Link` — UDP-сокет на `127.0.0.1:0` (`ListenLink`), на Windows с
`SO_EXCLUSIVEADDRUSE`. Отправитель закреплён и со стороны оболочки: `Addr` уходит ядру в
`-listen-peer`, порт ядра из `LISTEN` — в `SetCorePort`, датаграмы с других адресов
отбрасываются; между попытками (`SetCorePort(0)`) пакеты к ядру сбрасываются, а не уходят
на порт вышедшего ядра. В обе стороны проходит только IPv4 с целым заголовком и длиной из
заголовка, равной длине пакета: IPv6 программ и не-IP ответы сервера сбрасываются.
Семантика UDP — сброс без ожидания и без ошибки, счётчики по причинам (`Stats`). Буфер
`ReadPacket` — не короче 65535 байт: так датаграм не обрезается ни на одной ОС. Тесты:
обмен с эхо-ядром под `-race`, отправитель — ровно `Addr`, не-IPv4 в обе стороны, чужой
процесс и ядро прежней попытки, работа без ядра, переполнение в обе стороны (запись не
ждёт, после него канал жив), закрытие, короткий буфер, порт `Link` не занять вторым
сокетом — с `SO_REUSEADDR` и `SO_REUSEPORT` на Linux, с `SO_REUSEADDR` на Windows.
Обратные правки (без проверки отправителя, без фильтра IPv4) — тесты падают. Проверено
на Linux; тесты Windows собираются и идут в CI.

### C6. `socks` — `datapath/socks.go`

- gVisor netstack (`gvisor.dev/gvisor/pkg/tcpip`) с канальной конечной точкой: адрес — из
  `TUNCONF`, MTU 1300, пакеты — через C5.
- SOCKS5: `CONNECT` к адресу и к имени. Имена резолвятся DNS из `TUNCONF` через тот же
  netstack.
- Тест без сети: два netstack, соединённых каналом, TCP-эхо через SOCKS5.

**Готово, когда** тест проходит, `curl --socks5-hostname` через поддельное ядро получает
ответ эхо-сервера.

Итог: `datapath.Socks` написан заново, без кода qwdtt-cli: тот стоял на SOCKS5 из ядра
qWDTT и `armon/go-socks5`. Netstack gVisor (только IPv4, TCP и UDP) на канальной конечной
точке с MTU 1300, адрес /32 из `TUNCONF`, пакеты — через `Link`. SOCKS5 свой (RFC 1928):
без пароля и только на loopback, команда `CONNECT` к адресу IPv4 и к имени; прочие команды,
IPv6 и неизвестные типы адреса получают свой код отказа сразу. Имена ищет свой резолвер у
DNS из `TUNCONF` через тот же netstack — UDP, обрезанный ответ повторяется по TCP, серверы
по очереди, короткий кэш, — без hosts и доменов поиска системы. `Socks` живёт весь сеанс:
`Link` и слушатель SOCKS5 открываются до запуска ядра, `Start` вызывается на каждую
попытку. При том же адресе соединения переживают перезапуск ядра, при другом — рвутся;

закрытие, порт SOCKS5 не занять вторым сокетом. Обратные правки ключевых мест — тесты
падают. Проверено на Linux; тесты Windows собираются и идут в CI.

### C8. Супервизор — `supervisor`

- Автомат по §09 архитектуры на событиях `coreproc`. Перенести `state.go` и `lifecycle.go`,
  отвязав их от типов ядра qWDTT. Политику перезапуска и backoff написать заново: в
  qwdtt-cli они перенесены из Android-клиента qWDTT.
- Хеш с `CALL_UNAVAILABLE` исключается из следующих попыток. Годных не осталось —
  остановка с подсказкой.
- Тесты — на записанных потоках событий: подключение, отказ сервера, падение ядра, перезапуск
  из панели, все хеши мёртвые.

**Готово, когда** тесты проходят под `-race`.

Итог: `supervisor` — `state.go` и `lifecycle.go` из qwdtt-cli на сообщениях `coreproc`,
`policy.go` свой. Автомат: `Starting` → `Credentials` (`PROGRESS`) → `Configuring`
(`TUNCONF`) → `Connected`, когда поднят datapath и есть воркер, в каком бы порядке ни
пришли `READY` и `TUNCONF`; `Degraded` — без воркеров или при подозрении на сеть, выход —
по воркерам, а после подозрения ещё и по трафику. Цикл запускает ядро на каждую попытку,
читает его вывод до конца, ставит и сбрасывает порт ядра в канале, поднимает datapath на
первый `TUNCONF` и меняет DNS на повторный, отдаёт капчу решателю в своей горутине.
Перезапуск — по выходу ядра, `fatal`, `SERVER_RESTART` (пауза 4 с, не неудача) и
деградации дольше 30 с; задержки `1 · 2^n` с до 64, туннель обнуляет их. Остановка без
повтора — отказ сервера (`handshake_rejected`), выход ядра до `PROCESS`, ошибка запуска и
конец хешей: `CALL_UNAVAILABLE` исключает хеш из следующих попыток, а когда годных не
осталось — подсказка без самих хешей. Тесты — на записях вывода ядра: подключение в
разном порядке, отказ и молчание сервера, падение ядра, перезапуск из панели, мёртвые
хеши, деградация, повторный `TUNCONF`, капча, остановка в задержке, утечка горутин; под
`-race`. На настоящем ядре с выдуманным хешем цикл доходит до конца хешей и останавливает
ядро. Обратные правки восемнадцати ключевых мест — тесты падают.

### C9. Капча — мост к окнам

- `CAPTCHA_SOLVE|auto|…` → сразу `CAPTCHA_RESULT|error:unsupported`.
- `CAPTCHA_SOLVE|manual|…` → окно WebView2 / браузер по CDP / ручной режим →
  `CAPTCHA_RESULT|<токен>` или `|error:<причина>`.
- Перехват токена — заново, по наблюдаемому поведению страницы VK: какой ответ несёт
  токен и как отличить слайдер от чекбокса. Сначала — живая запись поведения страницы
  (в журнал этапа), затем код и стенд-страница для тестов.
- Окна из qwdtt-cli — `webview2_windows`, `browser_linux`, `cdp`, `manual` с тестами —
  переносятся здесь, поверх нового `Request` и перехвата; с ними — форк `go-webview2`
  тем же `replace`.
- Решатель капчи ядра выключен (`ONLY_PRINT_URL=1`, Р7): его попытки портят сессию,
  которая потом приходит в окно. Авторешатель — открытый вопрос Р7, не в этой задаче.

**Готово, когда** тесты на стенде проходят, а живая капча решается в окне и туннель после
неё поднимается.

Итог (код): `coreproc` ставит ядру `ONLY_PRINT_URL=1`, прячет токен в эхе `[STDIN]
CAPTCHA_RESULT|…` журнала ядра и даёт мосту два понятия — `CaptchaError` (причина для ядра)
и `ErrCaptchaNoReply` (не отвечать); сторож проверяет, что выключатель в `captcha.rs` на
месте. Супервизор отвечает ядру по ним, интерфейс `CaptchaFunc` прежний. `captcha`:
перехват заново — один разбор ответов API страницы (`page.go`) для окна по CDP (сеть
браузера) и WebView2 (свой перехватчик JS, тело ответа — в Go как есть); `check` с `OK` —
токен, `ERROR_LIMIT` — `error:limit` и окно закрыто, `BOT` — ждать; тип капчи — в журнал;
ошибка VK в `initSession` — `error:init` и окно закрыто. Мост `Bridge`: `auto` —
`unsupported`, `manual` — окно платформы, не открылось — ручной режим; одно окно, свой
таймер 180 с, новый запрос закрывает прежнее, тот же `redirect_uri` — то же окно (§08).
Ручной режим — инструкция через вкладку Network и повтор на негодный ввод. Chromium — с
`--disable-extensions` и `--password-store=basic`. Стенд на `httptest` — страница и API
капчи: галочка → `OK`, галочка → `BOT` → слайдер → `OK`, `ERROR_LIMIT`, ошибка
`initSession`, закрытие окна, срок, фрейм, `XMLHttpRequest`, прокси; тесты с Chromium идут
в обычном прогоне, без него пропускаются, без графического сеанса — без окна.

Итог (живая приёмка): на Linux живая капча решена в окне Chromium — решатель ядра
выключен, оба `auto` получили `unsupported`, на `manual` открылось окно, после галочки
токен ушёл ядру (в журнале скрыт), и ядро получило учётные данные TURN. Подъём туннеля
после капчи ждёт сервера с протоколом ядра: сервер для проверок ответил `handshake_rejected`
(`FATAL_PROTOCOL`, другая версия протокола), и супервизор остановился без повтора, как и
должен. Открыто: туннель после капчи — после обновления сервера; окно WebView2 — прогоном
на Windows. Оба пункта проверит и C11.

## Э2. Системный VPN на Windows — 6–8 дней

Цель: `csqtt-cli connect` с `tun` по умолчанию: весь трафик системы через туннель, защита

### W1. Способ привязки для `primp`

Выяснить по `primp-reqwest`, есть ли `interface()` на Windows и Linux. Если нет —
проверить на Windows `local_address(<адрес физического интерфейса>)` при поднятых
маршрутах `/1`. Выбор и причина — в архитектуре (§06).

**Готово, когда** выбор записан, а пробный запрос к VK с выбранной привязкой при поднятых
маршрутах уходит через физический интерфейс.

Итог: у `primp` нет ни крючка на создание сокета, ни нужных настроек. Сокеты TCP
открывает коннектор `primp-hyper-util`; `connector_layer` получает уже соединённый сокет.
Штатно коннектор умеет только `interface` (`SO_BINDTODEVICE` по имени, кроме Windows) и
`local_address`; ни метки, ни `IP_UNICAST_IF` у него нет. Решение — вендорить
`primp-hyper-util` и привязывать сокет в его `connect` по индексу (§06).

- **Отклонены:** проброска `interface()` через обёртку `primp` — только Linux, без метки;
  `local_address` на Windows — нужен адрес, а не индекс, и способ держится на сильной
  модели хоста; на Linux `local_address` не уводит сокет мимо `/1` вовсе.
- **DNS.** Своих сокетов DNS у `primp` нет: `hickory-dns` в сборке нет, а
  `dns_resolver(dns::global())` заменяет `getaddrinfo`. Имена разрешает точка 1.

Проба — клиент `primp` с теми же версиями крейтов, что у ядра, в непривилегированном
пространстве имён: маршруты `/1` ведут в заглушку, рядом — копия физического интерфейса.
Результаты:

- без привязки и с `local_address` SYN уходят в заглушку, соединение не устанавливается;
- с привязкой сокета к физическому интерфейсу VK отвечает, все пакеты идут через него;
- `strace` видит только сокет резолвера и сокет TCP `primp`, оба с привязкой;
- строгий `rp_filter` бросает ответы на привязанные сокеты (§09б).

Живая проверка на Windows перенесена в W2.

### W2. П3 — привязка сокетов ядра

- Правила `vendorcore` в пяти точках (§06). Флаг `-bind-if <индекс>`, команда
  `BIND_IF:<индекс>`; на Linux — ещё `-mark`.
- Точки 4–5 (W1):
  - `primp-hyper-util` 0.1.22 вендорится в `core/` (MIT, лицензия сохраняется) и
    подключается через `[patch.crates-io]`; `primp-reqwest` и обёртка `primp` не
    меняются;
  - своя правка — отдельно от копии крейта, чтобы при обновлении был виден diff (Р2):
    нетронутая копия и правило `vendorcore` или иначе — решить здесь;
  - в крейте — общая для процесса настройка (атомики): индекс и метка. Ядро ставит её
    по `-bind-if`/`-mark` и меняет по `BIND_IF:`. `connect` в `http.rs` рядом с
    `bind_device` берёт текущие значения: Linux — `SO_BINDTOIFINDEX` и `SO_MARK`,
    Windows — `IP_UNICAST_IF`/`IPV6_UNICAST_IF`;
  - проверка, что патч применён: если `primp` апстрима потребует другую версию
    `primp-hyper-util`, `[patch]` перестанет действовать без ошибки;
  - при `-bind-if` — `no_proxy()` в обоих клиентах: прокси из окружения увёл бы запросы
    мимо привязки.
- Смена сети: настройка коннектора общая, поэтому новый индекс берут и клиенты точки 4
  (собираются на каждую попытку входа), и клиент точки 5 (живёт весь сеанс `auto_js`).
  Соединения из пула keep-alive на старом интерфейсе отомрут по ошибке или таймауту.
- Порядок байт в `IP_UNICAST_IF` — как в wireguard-go (урок qwdtt-cli), одинаково в
  точках 1–3 и в коннекторе. В `socket2` 0.6.5 `IP_UNICAST_IF` нет — свой `setsockopt` без
  новой зависимости.
- Тесты на Rust: после создания сокета опция стоит (`getsockopt`); для коннектора — тест
  в пропатченном крейте: у сокета после `connect` стоят индекс и метка.
- Сторож на Go: тест ищет в `core/rust-client` и в вендоренном `primp-hyper-util`
  конструкторы сокетов (`UdpSocket::bind`, `TcpStream::connect`, `Socket::new`,
  `Client::builder`) и сверяет со списком покрытых мест. Новое место — тест падает.

**Готово, когда** тесты проходят, сторож падает на искусственно добавленном сокете, а на
Windows запрос `primp` на пропатченном коннекторе при маршрутах `/1` через другой адаптер
уходит через физический интерфейс. Этот прогон — вместе с приёмкой C11 на Windows и с
согласия пользователя: связь машины на время прогона рвётся.

Итог: правка П3 — 18 правил `vendorcore` и два своих модуля (§06). `bind_if.rs` в ядре
разбирает `-bind-if` и `-mark`, отвечает на `BIND_IF:` и даёт сокеты точкам 1–3: UDP-сокет
привязывается сразу после `bind`, TCP-сокет точки 3 строится как `TcpSocket` и
привязывается до `connect`. Клиенты `primp` точек 4–5 строятся общим построителем, с
`-bind-if` — с `no_proxy()`. `csqtt_bind.rs` в вендоренном `primp-hyper-util` — общая для
процесса настройка (индекс и метка) и сама привязка: на Linux `SO_BINDTOIFINDEX` (на ядре
без него — `SO_BINDTODEVICE` по имени) и `SO_MARK`, на Windows `IP_UNICAST_IF` (индекс в
сетевом порядке) и `IPV6_UNICAST_IF` (в порядке хоста) своим объявлением `setsockopt`.
Правило вставляет её вызов в `connect` коннектора перед `bind_local_address`; тем же
вызовом ядро привязывает сокеты точек 1–3.

- **Копия крейта** — архив `.crate` с crates.io в `scripts/vendorcore/crates/` (Р2):
  перенос сверяет версию и sha256 с `Cargo.lock` апстрима и распаковывает его в `core/`,
  версия и сумма — в `CORE_VERSION`. Ядро зависит от крейта напрямую той же версией, что
  берёт `primp-reqwest`, — нового крейта в графе нет; в `Cargo.lock` у него убраны
  источник и сумма, как у пакета по пути.
- **`[patch]` действует** — четыре слоя (§06): сверка версии при переносе, `Cargo.lock`
  под `--locked`, вызов `csqtt_bind`, которого нет в крейте с crates.io, и тест на
  соединении `primp`.
- **Отказы.** Индекс без интерфейса, `-mark` без `-bind-if` или на Windows, метка без
  прав — ядро не стартует (`[ФАТАЛ] [П3] …`, у метки — подсказка про `CAP_NET_ADMIN`).
  Сокет, который не удалось привязать, не используется — ошибка вызывающему. `BIND_IF:`
  без `-bind-if`, с нулём, не числом или индексом без интерфейса — отказ в журнале,
  сокеты остаются на прежнем интерфейсе. Существование интерфейса проверяется отдельно:
  `SO_BINDTOIFINDEX` принимает любой индекс, а ошибка приходит только на отправке. Без
  `-bind-if` ядро ведёт себя как прежде.
- **Сторож** — в `vendorcore` (перенос, `-check`, тесты на настоящем `core/`): таблица
  мест создания сокетов, разрешения имён и HTTP-клиентов (и без построителя —
  `primp::get`, `Client::new`, `Client::default`) в `rust-client/`, `shared/` и
  вендоренных крейтах — файл, вызов, число, что обязано идти дальше в той же функции,
  причина. Тесты ядра, `tests/` и `examples/` крейтов и комментарии не смотрит; тестовый
  модуль без найденного конца — ошибка, а не пропуск остатка файла.
- **`coreproc`**: `Config.BindIf` и `Config.Mark` → `--bind-if=`, `--mark=`; `BindIf(index)`
  — команда `BIND_IF:<индекс>`.

Тесты на Rust: опции на сокетах точек 1–3 и на соединении `primp` (его сокет находится
среди дескрипторов процесса по адресу), отказы флагов и `BIND_IF:`, смена интерфейса на
ходу, сокет на пропавшем интерфейсе ничего не шлёт. Тесты, меняющие общую настройку,
идут в отдельном процессе: иначе сокеты параллельных тестов TURN ушли бы не на тот
интерфейс. Без прав на метку тест проверяет только, что отказ виден, и пишет о пропуске;
полная проверка — в непривилегированном пространстве имён. На Go — аргументы и команда на
поддельном ядре, на настоящем — запуск с `-bind-if`, `BIND_IF:` и отказ на индекс без
интерфейса. Сторож падает на подложенном в копию апстрима сокете.

Проба ядра на Linux — режим проверки хешей с выдуманным хешем, в непривилегированном
пространстве имён, где маршруты `/1` ведут в заглушку. Без `-bind-if` запросы к DNS
Яндекса уходят в заглушку, и VK недоступен; запасной системный DNS, как и записано в §06,
идёт мимо привязки. С `-bind-if` и с `-bind-if -mark` DNS и HTTPS идут через физический
интерфейс, VK отвечает («ссылка недействительна»), в заглушку не уходит ни одного пакета
TCP или UDP; с меткой у всех сокетов ядра наружу стоят и привязка, и метка. С прокси из
окружения на loopback и `-bind-if` ядро идёт к VK напрямую. Неверные флаги — отказ
стартовать.

На Windows тесты ядра проходят, в том числе тест порядка байт `IP_UNICAST_IF`; тесты Go на
настоящем ядре — тоже. Проба ядра на Windows — та же проверка хешей, маршруты `/1` ведут на
другой адаптер. Заглушка там — сосед с постоянной записью ARP. Маршрут на линк без соседа
не годится: ARP не проходит, и Windows уводит соединения через физический интерфейс, так что
без привязки VK ложно доступен. Без `-bind-if` VK недоступен; с `-bind-if` — и с
`HTTPS_PROXY` на мёртвый порт loopback — VK отвечает сразу. `-mark` и индекс без интерфейса —
отказ стартовать. Если адаптер привязки отключён, ядро не стартует (`IP_UNICAST_IF` —
`WSAEINVAL`). Сокет, привязанный до отключения, получает `WSAENETUNREACH`, и через
физический интерфейс не уходит ни одного пакета (захват `pktmon`).

### W3. `tun` на Windows

- Wintun через `golang.zx2c4.com/wireguard/tun` с постоянным GUID, мост к каналу C5 —
  пачками в обе стороны.
- `Persistent`, `Suspend`, `Reserver` (мьютекс) — из qwdtt-cli.
- По первому `TUNCONF`: адрес `/32`, MTU 1300, DNS, маршруты `0/1`, `128/1`, `::/1`,
  `8000::/1`.

**Готово, когда** тесты общей логики `tun` проходят, а тест с правами администратора
поднимает адаптер, ставит и снимает маршруты.

Итог: `datapath.Tun` на Windows — Wintun с постоянным GUID, `Link` и мост между ними
(`tun_windows.go`, `tun_bridge.go`); адрес, маршруты, метрика и DNS — `winsys`, как в
qwdtt-cli (архитектура, §05). Общая логика `Tun` не менялась, кроме двух полей адаптера:
список маршрутов для журнала и признак «IPv6 отбрасывает мост». Тесты моста — на подделке
адаптера: обмен в обе стороны, отброс не-IPv4, пакеты без ядра, повтор после сбоев,
остановка. Блокировка второго запуска — общий тест с помощником для Linux и Windows.
Тест с настоящим адаптером (`TestWintunAdapter`, `CSQTT_TEST_WINTUN=1`, права
администратора, `wintun.dll` рядом с тестовым бинарём) поднимает адаптер на своём GUID,
ставит маршруты на документационные префиксы, чтобы не забрать трафик машины, гоняет UDP
от программы через адаптер и мост к «ядру» на loopback и обратно, проверяет отброс IPv6,
`Suspend`, повторный `Start` и то, что после `Close` адаптера и маршрутов нет.

`connect -datapath tun` на Windows работает только с `-allow-leak`, пока нет защиты DNS и
kill-switch (W5). Без флага — отказ до подключения с готовыми командами, а мастер меню `tun`
не предлагает. Подсказка о правах на Windows — консоль администратора, метки ядру на
Windows не передаются. Живая проверка: туннель поднимается, маршруты `/1` обоих семейств и
DNS стоят на адаптере, внешний адрес мимо прокси — адрес VPS, загрузка идёт через туннель.
По Ctrl+C адаптер, маршруты и ядро уходят, снимок `checktunnel` совпадает с исходным.
После `taskkill /F` оболочки они уходят сразу, но в реестре остаётся ключ интерфейса с DNS
туннеля (§05). Он безвреден и не копится (GUID адаптера постоянный), поэтому остаётся как
есть.

### W4. DNS на ходу

Повторный `TUNCONF` → `UpdateDNS` → DNS адаптера и фильтры защиты DNS. Порядок перехода
фильтров — без мига без защиты.

**Готово, когда** тест с правами администратора меняет DNS дважды подряд, и между
состояниями нет момента без фильтров.

Итог: кода перехода писать не пришлось. Супервизор отдаёт повторный `TUNCONF` в
`UpdateDNS`, а общая логика `Tun` (`applyDNS`) уже шла в три шага: защита пускает прежние и
новые резолверы, DNS адаптера заменяется, защита пускает только новые. `winsys.DNSGuard`
при каждом `Enable` ставит новые правила раньше, чем снимает старые: новые — от тяжёлых к
лёгким, старые — от лёгких к тяжёлым. Тест на настоящем WFP (`TestDNSGuardChangeDNS`, права
администратора) меняет резолверы дважды подряд тем же порядком, что `Tun`, и после каждого
правила, которое встало или снято, читает подслой. На каждом слое на месте запрет порта 53,
разрешение своему процессу, loopback и резолверы, к которым на этом шаге ведёт DNS системы.
В конце перехода разрешены ровно новые резолверы, старых правил нет. Если сломать порядок
(сначала снять старые), тест падает на первом же шаге. К резолверам теста добавлены
нынешние резолверы системы, поэтому DNS машины во время теста работает. Тест с настоящим
адаптером дважды меняет DNS через `UpdateDNS`: DNS адаптера заменяется, адрес и маршруты
остаются. Живую смену DNS сервером не проверяли.

### W5. Защита DNS и kill-switch

`dnsguard` и `killswitch` из qwdtt-cli: разрешение «свой процесс» — для app ID обоих exe.
Ядро ищется по полному пути рядом с `csqtt-cli.exe`.

**Готово, когда** тесты `winsys` с правами администратора проходят, включая
`TestDNSGuardUnderGC`.

Итог: `winsys.OpenDNSGuard` принимает пути программ, которым разрешено всё, и `cli` на
Windows передаёт ему `csqtt-core.exe` рядом с `csqtt-cli.exe`. Правило «свой процесс» в
защите DNS и в «закрыто» срабатывает на любой из двух app ID. У защиты DNS на Windows
появился `BlockIPv6`: если IPv6 выключен на адаптере и маршрутов IPv6 нет, на слоях IPv6 к
ней добавляется часть «закрыто» (loopback, DHCPv6, ND и RA, локальная сеть, запрет всего).
`connect -datapath tun` на Windows больше не требует `-allow-leak`, меню снова предлагает
`tun`.

Тесты `winsys` от администратора проходят, включая `TestDNSGuardUnderGC`. Новый
`TestDNSGuardPermitsPrograms` копирует тестовый бинарь под двумя именами. При «закрыто»
DNS Яндекса отвечает копии, переданной в `OpenDNSGuard`, а другой — нет. Тесты `cli`
больше не открывают настоящую защиту, даже если запущены с правами: `TestMain`
подменяет её отказом, и настоящую берёт только тест в контейнере.

Живая проверка: `connect -datapath tun` без `-allow-leak` поднимает туннель. Пока туннель
поднят, стоят 12 фильтров WFP, DNS к чужому резолверу закрыт, к резолверу туннеля открыт,
внешний адрес — адрес VPS. После Ctrl+C и после `taskkill /F` фильтров, адаптера и маршрутов
нет. Туннель поднимался за секунды, и окна «закрыто» до подъёма живьём проверить не
успели: это пункт W8 «между попытками трафик закрыт».

### W6. Смена сети

`netguard/watch.go` → `BIND_IF:<новый индекс>`. Замер: время до восстановления трафика
после переключения Wi-Fi ↔ Ethernet с `BIND_IF` и с перезапуском ядра. Медленнее или
ненадёжнее — оставить перезапуск. Решение — в архитектуре (§06).

**Готово, когда** решение записано, а выбранный способ восстанавливает туннель в живом
прогоне.

Сделано (код, без замера). `Tunnel.Rebind` в супервизоре: ядру после `PROCESS` уходит
`BIND_IF`. Ядро до `PROCESS`, отказ ядра в журнале, просьба во время задержки и смена
того интерфейса, к которому ядро уже привязано (вернулся тем же, сменился только IPv6), —
перезапуск, как раньше (§06, §09). В `connect` способ выбирает скрытый флаг
`-net-switch restart|bindif`; по умолчанию — перезапуск, с `socks` флаг `bindif`
отклоняется. Тесты: супервизор на подставном ядре (команда без перезапуска, две просьбы
подряд — последняя, отказ, до `PROCESS`, во время задержки, просьба на интерфейс, который
у ядра уже есть), `connect` с подставной сменой сети, отказ `BIND_IF` на настоящем ядре
узнаётся по его строке.

Заодно — хвост ревью W3: адаптер Wintun, который пропал сам, раньше давал молча
вышедший мост и «поднятый» туннель. Теперь мост говорит об этом, `connect` кончается
ошибкой с подсказкой (§05). Тест с настоящим Wintun отключает адаптер через `netsh`: мост
замечает это за полсекунды. Помощь `connect` больше не говорит, что `tun` на Windows —
только с `-allow-leak` (осталось от W3).

Ревью W6: семь правок. Смена интерфейса, к которому ядро уже привязано, — перезапуск, а
не `BIND_IF` на тот же индекс. Серия сбоев моста считается по времени в сбое, а не от
первого сбоя. Сбой адаптера не заменяет уже известную причину конца и не даёт строки о
переподключении. Просьба на интерфейс, который у ядра уже есть, не перезапускает его.
`-net-switch bindif` с `socks` отклоняется. Отложено до итогов замера: отказ `BIND_IF`
узнаётся по тексту журнала ядра. Если `bindif` станет умолчанием, правка П3 должна давать
отдельное событие о принятии и отказе.

Осталось: живой замер на машине с двумя сетями (Wi-Fi и кабель) и решение.

### W7. Скорость моста

Замер пропускной способности и загрузки CPU `tun` против Android-клиента на том же сервере.
Если мост — узкое место, пакетная отправка и приём на loopback.

**Готово, когда** итог замера записан в журнал. Узкое место — отдельная задача.

Итог W7: мост — не узкое место. Без системы (подставной адаптер, ядро — сокет UDP)
он возит 1,4–1,9 Гбит/с пакетами по 1400 байт: в десятки раз больше, чем даёт канал;
бенчмарк — `BenchmarkBridgeToCore` и `BenchmarkBridgeToAdapter` в `internal/datapath`.
В живом прогоне `tun` и `socks` (без Wintun и моста) упираются в один и тот же потолок
загрузки, а оболочка и ядро заняты на единицы процентов одного ядра процессора. Предел
задаёт канал через TURN VK. Закачка в несколько раз медленнее загрузки — у Android-клиента
на том же сервере так же. Пакетная отправка на loopback не нужна.

### W8. Живая приёмка Э2

- внешний адрес — VPS; резолверы роутера и `8.8.8.8` на :53 недоступны;

- смена сети и выдернутый кабель — туннель возвращается сам;

- второй запуск — отказ до подключения;
- запуск двойным щелчком по `csqtt-cli.exe` (меню I1) доводит до работающего туннеля без
  набора команд;
- из архива релиза (I3) на чистой машине Windows туннель поднимается.

**Готово, когда** все пункты отмечены в журнале этапа.

## Э3. Linux — 5–7 дней

Цель: `sudo csqtt-cli connect` с `tun` на Linux, те же гарантии, что на Windows.

### L1. П4 и П6

- П4: при приёме дескриптора через `-tun-uds` — `SO_PEERCRED`, uid отправителя равен uid
  ядра, иначе соединение закрывается и считается.
- П6: проверить на 2.1.9, роняет ли запись не-IP пакета в TUN писатель (`run_tun`). Роняет —
  правило по образцу исправления focsq: пакет отбрасывается и считается.
- Тесты на Rust.

**Готово, когда** тесты проходят.

Итог: девять правил `vendorcore` и два своих модуля, оба — дочерние к файлам апстрима
(`#[path]`), чтобы тесты видели закрытое.

- **П4** — `tun_peer.rs`, дочерний к `tun.rs`. Сразу после `accept` ядро берёт
  `SO_PEERCRED` соединения и сравнивает uid отправителя с эффективным uid ядра:
  `SO_PEERCRED` отдаёт эффективный uid, и права на устройства определяет он же. Чужой uid
  или ошибка `getsockopt` — соединение закрывается, не читая из него ни байта, отказ
  считается (в журнал — 1-й, 2-й, 4-й…, с uid и номером отказа), и тот же вызов `receive`
  ждёт следующего соединения. Вызывающий ошибки не видит, поэтому нет и его паузы в 100 мс
  перед повтором: законный отправитель за отвергнутым принимается сразу. Заодно чужой
  процесс не может занять приём, подключившись и ничего не присылая. `SO_PEERCRED` есть
  на Linux и Android; на других unix — отказ всем (абстрактных сокетов там нет, и
  `-tun-uds` там и так не собирается). Четыре правила в `tun.rs`: модуль, поле и его
  создание в `FdReceiver`, проверка после `accept`.
- **П6** — `tun_drop.rs`, дочерний к `dispatcher.rs`. На 2.1.9 правка нужна: запись 0 байт
  и любая ошибка, кроме повторяемых и «интерфейс закрыт», останавливали писатель TUN, и
  туннель стоял до нового дескриптора. Теперь такой пакет отбрасывается и считается за
  весь процесс, а `try_write_tun_packet` отвечает `Complete` — писатель берёт следующий
  пакет с нулевым смещением, так что и после частичной записи хвост отброшенного не
  уйдёт. Журнал приглушён: первые 8 отбросов, дальше каждый 1000-й. Повторяемые ошибки и
  «закрыт» — как у апстрима. Пять правил в `dispatcher.rs`: модуль, две ветки отказа и
  удаление варианта `Failed`, который больше никто не возвращает.

Тесты на Rust. П4: решение по uid (свой — да, чужой, root при обычном ядре и ошибка —
нет); `SO_PEERCRED` пары сокетов — свой эффективный uid; отказ не-сокету; и настоящий
слушатель — один вызов `receive` отвергает отправителя, чей дескриптор после этого
закрыт, и принимает следующего с тем же слушателем. Сменить uid без root нельзя, поэтому
«чужим» отправителя делает тест: ядро на время ждёт другой uid; сам `SO_PEERCRED`
настоящего чужого процесса не проверен. П6: настоящий `write_tun` — `EINVAL` (eventfd) и
запись 0 байт (пустой датаграм) отбрасываются, следующий пакет доходит; EBADF («закрыт»)
по-прежнему останавливает писатель, следующий пакет остаётся в очереди; приглушение
журнала. Обратная правка — три теста на настоящем слушателе и писателе падают.

### L2. `tun` на Linux

- Свой `TUNSETIFF` с `IFF_TUN | IFF_NO_PI`, без `IFF_VNET_HDR`: `tun.CreateTUN` из
  wireguard-go включает разгрузку, которую ядро CSQTT не понимает.
- Настройка через `linuxsys`, блокировка `@csqtt-cli-tun`.
- Передача дескриптора: случайное имя абстрактного сокета, `SCM_RIGHTS`, на каждую
  попытку — новый дубликат.

**Готово, когда** тест в контейнере (`--cap-add NET_ADMIN`) поднимает адаптер и отдаёт
дескриптор поддельному получателю.

Итог: `datapath.Tun` (`tun.go` — общее, `tun_linux.go`, `tunfd_linux.go`; прочие ОС —
заглушка до W3) и режим дескриптора в супервизоре.

- **Адаптер** `csqtt-cli` — свой `TUNSETIFF` с `IFF_TUN | IFF_NO_PI`, без `IFF_VNET_HDR`,
  создаётся при первой надобности и живёт весь сеанс (`Persistent`). `Start` — адрес /32,
  MTU 1300, подъём, маршруты `0.0.0.0/1` и `128.0.0.0/1` через `linuxsys`, IPv6 — без
  маршрутов (закроет L3); другой адрес в новой попытке заменяет прежний на том же
  интерфейсе. `Suspend` снимает маршруты, `Close` закрывает дескриптор — интерфейс уходит
  с ним; безопасен до `Start`, повторно и из нескольких горутин разом. Блокировка второго
  запуска — абстрактный сокет `@csqtt-cli-tun` со счётчиком захватов в процессе
  (`Reserve` и открытие адаптера), чужой интерфейс с тем же именем — отказ с подсказкой.
  `Requires` — root, `Netguard`, без `/dev/net/tun` — `Unsupported`. DNS системы — L3: до
  неё `UpdateDNS` только запоминает DNS, а `connect` с `tun` по-прежнему отказывает.
- **Дескриптор ядру** — на каждую попытку новое случайное имя абстрактного сокета в
  `-tun-uds` и новый дубликат (`F_DUPFD_CLOEXEC`), один байт с `SCM_RIGHTS`, ожидание байта
  подтверждения, свой дубликат закрывается. События готовности слушателя ядра нет, поэтому
  по `PROCESS` — подключение с повтором через 20 мс на `ECONNREFUSED` и `EAGAIN` (очередь
  слушателя — 4), до 10 с. Перед отправкой — `SO_PEERCRED` слушателя: pid ядра и тот же
  эффективный uid, иначе дескриптор не уходит (имя сокета видно в командной строке ядра).
- **Супервизор**: `Options.TunFD` вместо `Link` (ровно одно из двух). Передача идёт в
  горутине попытки, её итог — в цикле: отказ или срок — конец попытки с обычной задержкой,
  `Connected` — только после подтверждения. У `Persistent`-datapath после неудачной
  попытки, до задержки, зовётся `Suspend`. Режим `socks` не изменился.

Тесты. Общая логика `Tun` на поддельном адаптере: одно открытие на сеанс, переадресация,
маршруты, `Suspend`, `Close` до `Start`, повторный и одновременный, отказы открытия и
настройки. Передача без прав, с поддельным получателем (слушатель абстрактного сокета,
отвечающий байтом, как ядро): копия того же дескриптора, ожидание слушателя, полная
очередь (`EAGAIN`), нет слушателя, чужой слушатель (дескриптор не уходит), закрытие без
ответа, неверный ответ, молчание. Блокировка — из второго процесса. Супервизор на
подставном ядре: новое имя и передача ядру своей попытки, `Suspend` между попытками, отказ
и срок передачи не вешают цикл, `Connected` ждёт дескриптор. В контейнере (`--cap-add
NET_ADMIN --device /dev/net/tun`, задание `netns` CI, тесты `…Netns`): настоящий адаптер
отдаёт дескриптор поддельному получателю — `TUNGETIFF` на принятом: имя адаптера и только
`IFF_TUN | IFF_NO_PI`; адрес, MTU, подъём, маршруты только IPv4; пакет UDP проходит в обе
стороны между системой и принятым дескриптором; второй адаптер из другого процесса —
отказ; `Suspend`, переадресация, второй дубликат; после `Close` интерфейса нет. Настоящее
ядро с `-tun-uds` (`TestRealCoreTunFD`, без прав — дескриптор пары сокетов) принимает
дескриптор и подтверждает его; с настоящим адаптером в контейнере — тоже. Обратные правки
ключевых мест — тесты падают.

### L3. Метка и nftables

- `-mark` ядру; таблица `inet csqtt-cli` с `owner`: защита DNS, kill-switch, закрытие IPv6.
- DNS системы — три способа из qwdtt-cli; проверка `rp_filter`.

**Готово, когда** тесты `linuxsys` проходят в контейнере.

Делается в три части, каждая — отдельным коммитом: **L3a** — DNS системы и защита DNS в
`datapath.Tun`; **L3b** — kill-switch и закрытие IPv6 (и `kill_switch` в профиле);
**L3c** — подключение в `connect` (выбор интерфейса, `-bind-if` и `-mark` ядру,
`rp_filter`, остатки DNS прошлого запуска, флаги `-no-kill-switch` и `-allow-leak`, `tun`
под `sudo`).

Итог L3a: `Tun` ставит и снимает защиту DNS и DNS системы; `connect` режим `tun` пока не
включает (L3c).

- **Интерфейсы** — как в qwdtt-cli: `datapath.DNSGuard` (`Enable`, `Disable`),
  `Requirements.DNSGuard` (у `tun` — да), `TunOptions.DNSGuard`. Сессию защиты —
  `linuxsys.OpenDNSGuard(метка)`, таблица `inet csqtt-cli` с `owner` — открывает и
  закрывает вызывающий; `nil` — без защиты. Платформа отдаёт `Tun` ещё `setDNS` и
  `revertDNS` адаптера.
- **DNS системы** — `linuxsys.DetectSystemDNS` при создании адаптера, до `TUNSETIFF`:
  незнакомый генератор `resolv.conf` — отказ открытия. Способ и его предупреждение — в
  журнал. Системе и защите достаются только резолверы IPv4: маршрутов IPv6 в туннель нет.
  Без резолверов IPv4 DNS системы не трогается, а защита закрывает DNS целиком.
- **Порядок.** `Start`: маршруты, защита, DNS системы; отказ защиты или DNS системы —
  ошибка попытки, и снимается всё, как в `Suspend`. `Suspend` и `Close`: DNS системы возвращается, защита
  снимается, затем маршруты (адаптер). DNS системы между попытками возвращается прежним, в
  отличие от qwdtt-cli: systemd-resolved шлёт запросы к DNS линка через сам линк, то есть
  в адаптер без ядра, и страница капчи между попытками не открылась бы.
- **DNS на ходу** — в три шага: защита пускает прежние и новые, DNS системы — новые,
  защита — только новые. Каждый `Enable` — один пакет nftables, ядро применяет его
  целиком, так что нет ни мига без защиты, ни мига, когда DNS системы ведёт туда, куда
  защита не пускает. Тот же переход — у `Start` с другим адресом в той же попытке. Отказ
  на ходу туннель не роняет: после отказа `Enable` (он снимает правила целиком) ставится
  прежний список, после отказа DNS системы защита пускает обе стороны; следующий `TUNCONF`
  доводит переход. Между попытками `UpdateDNS` только запоминает.
- **Попутно (ревью L2).** `TUNSETIFF` с `IFF_TUN_EXCL`: чужой постоянный TUN с тем же
  именем, появившийся после проверки, — `EBUSY` и тот же отказ, что у чужого интерфейса.
  Имя блокировки второго запуска — переменная пакета; тесты берут своё и передают его
  помощнику во втором процессе.

Тесты. Общие, на поддельных адаптере и защите, которые сами следят, что DNS системы
всегда среди резолверов, пускаемых защитой, и что защита и DNS включаются после
маршрутов: порядок `Start`, `Suspend`, `Close`; переход на ходу и `Start` с другим
адресом; `UpdateDNS` с тем же DNS и между попытками; только IPv4; отказы защиты и DNS
системы в `Start` (уборка) и на ходу (возврат прежней защиты, защита на обе стороны,
доводка); без защиты; `Close` до `Start` и повторный. В контейнере (задание `netns`):
настоящий `Tun` с настоящей `linuxsys.DNSGuard` и перезаписью `resolv.conf` — DNS к чужому
резолверу отбрасывается, к резолверу туннеля уходит в адаптер, в файле — DNS туннеля;
смена на ходу переводит и файл, и защиту; после `Suspend` и `Close` — прежний файл, копии
нет, таблица без правил; `TUNSETIFF` на чужой постоянный TUN — `EBUSY`. Тесты `linuxsys` в
контейнере — по-прежнему все проходят. Обратные правки ключевых мест — тесты падают.

Итог L3b: kill-switch, закрытие IPv6 и `kill_switch` в профиле готовы как части; `connect`
их ещё не зовёт и режим `tun` не включает (L3c).

- **IPv6.** `datapath.IPv6Blocker` — необязательная часть защиты DNS. `Tun` перед каждым
  включением защиты просит закрыть IPv6: маршрутов IPv6 в адаптер нет никогда, и пока
  туннель поднят, IPv6 наружу отбрасывается (в qwdtt-cli — только при MTU меньше 1280).
  Локальный IPv6 проходит, как в «закрыто»: loopback, сокеты с меткой, `fe80::/10`,
  `fc00::/7`, `ff00::/8`, ND и RA, DHCPv6; DNS к нему закрыт (запрет порта 53 раньше
  разрешений), резолвер туннеля с адресом IPv6 не разрешается. В `forward` (контейнеры и
  ВМ) — то же без служебных протоколов хоста. Списки общие с «закрыто». Без такой защиты —
  строка, что IPv6 идёт мимо туннеля.
- **Kill-switch** (`cli/killswitch.go`) — как в qwdtt-cli: обёртка над сессией защиты,
  «закрыто» (`Lockdown`) сразу при создании, `Enable` — защита DNS, `Disable` — снова
  «закрыто», `Locked` для супервизора, `BlockIPv6` насквозь. Отказ `Enable` без
  `-allow-leak` — ошибка и «закрыто», с ним — строка и правила сняты; не встало
  «закрыто» — громкая строка и правила сняты целиком. Капча мимо прокси снимает
  «закрыто» на время решения; капчи считаются (окна внахлёст), туннель, поднятый или
  упавший посреди капчи, учитывается.
- **Открытие защиты** (`cli/dnsguard.go`) — `setupDNSGuard` и `tolerantDNSGuard` из
  qwdtt-cli: таблица `linuxsys.OpenDNSGuard(netguard.SocketMark)`, на прочих ОС — отказ
  «пока только Linux»; отказ без `-allow-leak` — ошибка с подсказкой про `-allow-leak` и
  `-no-kill-switch`, с ним — предупреждение и работа без того, что не включилось.
- **Капча.** У моста `captcha.Options.Direct`: всё, что идёт в сеть мимо прокси, —
  ручной режим, окно без `Dial`, то же окно без прокси при `ErrProxy` (раньше в этом
  случае был ручной режим) — решается под ним; `cli` отдаёт туда kill-switch. Обёртки
  решателя qwdtt-cli (`killSwitchCaptcha`, `proxiedCaptcha`) здесь не годятся: запасные
  пути выбирает сам мост, и обёртка снаружи не отличила бы окно через прокси от ручного
  режима.
- **Супервизор.** `Options.KillSwitch`; после `Suspend` попытки, в которой туннель
  поднимался, — правдивая строка («заблокирован (kill-switch)» или «идёт мимо
  туннеля»), `Start` следующей — строка о возврате; отказ `Suspend` — строка, что снято
  не всё.
- **Профиль.** `kill_switch` (`KillSwitch *bool`, `KillSwitchOn`): пропуск — включён,
  пишется, только если задан; `profile add|set -kill-switch[=false]`, `profile show`.
- **Попутно (ревью L3a).** `linuxsys.SystemDNS.Set` отмечает поставленное до вызовов: после
  частичного отказа (systemd-resolved принял DNS, но не домены) `Revert` снимает и его.

Тесты. Kill-switch на поддельной сессии: создание — «закрыто», `Enable` — защита DNS,
`Disable` — «закрыто», отказы `Lockdown` и `Enable` с `-allow-leak` и без, капча при
«закрыто» и при поднятом туннеле, туннель поднят и упал посреди капчи, две капчи
внахлёст, отказы снятия и возврата. `setupDNSGuard`: отказ без `-allow-leak` — ошибка с
подсказкой, с ним — предупреждение, терпимая обёртка, `BlockIPv6` насквозь. Мост капчи:
`Direct` — для окна без `Dial`, окна без прокси и ручного режима, не для окна через
прокси и `auto`. `Tun`: просьба закрыть IPv6 перед каждым `Enable`. Супервизор: строки
по попыткам с kill-switch, без него и со снятым на время капчи. Профиль: запись, чтение,
`profile set` и `show`. В контейнере (задание `netns`, тесты `cli` `…Netns`, IPv6 включён
`--sysctl`): настоящий `Tun` и таблица под kill-switch — до `Start`, после `Suspend` и
`Close` наружу закрыто всё, кроме сокетов с меткой, loopback и локальной сети (DNS закрыт
и к ней), IPv6 тоже; после `Start` трафик идёт в адаптер, DNS — только к резолверу
туннеля IPv4, IPv6 наружу закрыт, а локальный IPv6 (link-local, ULA, мультикаст) открыт, и
DNS к нему — нет; капча снимает «закрыто» и возвращает; после закрытия таблицы правил нет.
`linuxsys` в контейнере при закрытом IPv6: локальный IPv6, ND и DHCPv6 проходят, echo
наружу и DNS к локальным адресам и к резолверу IPv6 в ULA — нет. Тесты `linuxsys` в контейнере — все проходят. Обратные правки ключевых мест —
тесты падают.

Итог L3c: `sudo csqtt-cli connect` в режиме `tun` на Linux поднимает системный VPN с
защитой DNS, kill-switch и закрытым IPv6.

- **`connect`.** Флаги `-no-kill-switch` и `-allow-leak` (в `socks` молчат, как в
  qwdtt-cli). `Requires` — до чтения секретов: не Linux — отказ с подсказкой
  `-datapath socks`, без root — с подсказками `sudo` и `-datapath socks`. Порядок до
  первой попытки (`cli/fulltunnel.go`): резерв адаптера, физический интерфейс и
  `rp_filter`, остатки DNS прошлого запуска (`Recover`), таблица защиты и «закрыто»,
  адаптер с защитой (`TunOptions.DNSGuard`, поэтому таблица — раньше `Open`; отказ `Open`
  её снимает). Снятие — в обратном порядке: слежение за сетью, адаптер, таблица, резерв.
- **Интерфейс и метка ядру** (`cli/netguard.go`) — на каждую попытку через
  `supervisor.Options.Prepare`: `-bind-if` — индекс IPv4, `-mark` — только если таблица
  защиты открылась. Без маршрута по умолчанию IPv4 ядро не запускается, попытка ждёт сеть.
  Строгий `rp_filter` на интерфейсе — отказ до подключения, на новом после смены сети —
  предупреждение, а попытки продолжаются с обычной задержкой; `sysctl` не меняется. Обратный фильтр IPv6 firewalld не проверяется:
  маршрутов IPv6 в туннель нет.
- **Смена сети** — перезапуск ядра: `netguard.Watch` зовёт `Tunnel.Restart`; пропажа сети
  попытку не трогает; без подписки интерфейс выбирается перед каждой попыткой. `BIND_IF:`
  без перезапуска — замер W6.
- **Супервизор.** Выход ядра до `PROCESS` окончателен, только если в этом цикле ядро ещё
  ни разу не доходило до `PROCESS` (негодные аргументы); иначе — обычная неудача: до
  `PROCESS` ядро уже ходит в сеть, и в новой сети, ещё не пропускающей наружу, выходит.
  `Options.Prepare` (отказ — неудачная попытка с обычной задержкой);
  `Tunnel.Restart` — просьба на одно место: обрывает попытку или прерывает задержку,
  следующая попытка — сразу и со сброшенным счётчиком неудач; пришедшая, когда попытка и
  так кончается, тоже даёт попытку без задержки.
- **Капча.** Окно ходит через прокси `csqtt-cli` сокетами с меткой на физическом
  интерфейсе; имена VK прокси разрешает своим резолвером к DNS Яндекса теми же сокетами.
  Без kill-switch окно ходит в сеть само. У kill-switch — признак закрытия: окно, закрытое
  после конца `connect`, правил не трогает. Задержка страницы из-за `ad.mail.ru` — на
  стороне Chromium (прокси отказывает сразу), не чинилась.
- **`sudo`.** `Main` первым делом принимает служебную команду связки ключей: под `sudo`
  файлы и секреты остаются у вызвавшего. Подсказка без root — готовая команда: с
  `-datapath tun`, если режим задан флагом, и с `-config` — и в ней, и в
  `profile set`. Остановка с уборкой — и по SIGHUP (закрыли терминал), не только по
  Ctrl+C и SIGTERM; под `nohup` (SIGHUP игнорируется) подписки на него нет, и подключение
  переживает терминал.
- Попутно: подсказка `-datapath` у `profile add|set` больше не говорит, что `tun` —
  в следующих версиях; в §04 флаг воркеров назван так, как его передаёт оболочка
  (`-workers`).

Тесты. Супервизор на подставном ядре: `Prepare` на каждую попытку и его отказ; `Restart`
посреди попытки, до `Connected`, во время задержки и пока попытка останавливается —
задержки и сброс счётчика. `connect` с подставными адаптером, таблицей, выбором
интерфейса и подпиской: порядок шагов и снятия, аргументы ядра (`-tun-uds`, `-bind-if`,
`-mark`), мост капчи с `Dial` и `Direct`; отказы (нет root, не Linux, строгий
`rp_filter`, остатки DNS, таблица, «закрыто», адаптер) с подсказками и уборкой;
`-allow-leak` (без метки и прокси), `-no-kill-switch` и `kill_switch = false`; `socks` без
интерфейса и таблицы; смена и пропажа сети, сеть, появившаяся после запуска, без
подписки. Резолвер прокси капчи — через хук сокетов и к заданному DNS. Kill-switch после
закрытия. Служебная команда связки — и функцией, и через `Main`. Выход ядра до `PROCESS`:
первым же ядром — конец, после работавшего — повтор. Подсказки без root с флагом режима и
`-config`; строка об окне капчи — только с прокси. SIGHUP останавливает цикл, а игнорируемый (`nohup`) — нет. В контейнере (задание
`netns`) тесты `linuxsys`, `datapath` и `cli` проходят без пропусков. Проба в контейнере
без сети наружу (интерфейс-заглушка с маршрутом по умолчанию): настоящий
`csqtt-cli connect` с настоящим ядром — у ядра `-tun-uds`, `-bind-if` и `-mark`, адаптер
`csqtt-cli`, таблица `inet csqtt-cli` в «закрыто» (наружу без метки — отказ, с меткой —
проходит), после `SIGINT` — ни адаптера, ни таблицы, `resolv.conf` прежний; при строгом
`rp_filter` — отказ с подсказкой, ядро не запускается. Обратные правки ключевых мест —
тесты падают.

### L4. Живая приёмка Э3

Как W8, плюс: в контейнере и на живой машине; `kill -9` оболочки — интерфейса нет,
остаток DNS убирает следующий запуск; капча в браузере под управлением от имени вызвавшего
`sudo`.

**Готово, когда** все пункты отмечены в журнале этапа.

Итог L4: живая приёмка пройдена с настоящими ядром и сервером — в контейнере (своё
сетевое пространство) и на живой машине; правок кода не понадобилось.

- **Подъём и утечки.** `sudo csqtt-cli connect -datapath tun` поднимает туннель за
  секунды; внешний адрес — VPS, ответы приходят через адаптер. DNS мимо туннеля закрыт по
  UDP и TCP — к резолверам системы и роутера, к публичным резолверам; DNS, выданный
  сервером в `TUNCONF`, ходит только через адаптер. Пункт W8 «`8.8.8.8` на :53
  недоступен» дословно не проверить, если сервер сам выдаёт этот адрес в DNS туннеля —
  тогда проверяется, что он идёт через адаптер. IPv6 наружу не уходит. DNS системы (и
  resolvconf, и сам `resolv.conf`) переключается на DNS туннеля и возвращается.
- **Между попытками.** Убитое ядро: в паузе запись DNS снята, трафик без метки — EPERM,
  через 1–2 с туннель снова поднят.
- **Смена сети.** Положенный на 45 с физический интерфейс: таймауты TURN → «сеть
  пропала», через 30 с без связи ядро перезапущено, трафик закрыт; попытки с растущей
  задержкой; после подъёма интерфейса и DHCP событие сети прерывает задержку, туннель
  возвращается за ~10 с.
- **Второй запуск** — отказ до подключения («адаптер уже занят…»), первый туннель жив.
- **Ctrl+C** — ни ядра, ни адаптера, ни таблицы, DNS прежний; снимок сети совпадает с
  исходным.
- **`kill -9` оболочки** — ядро умирает (`Pdeathsig`), адаптер исчезает, таблица
  `inet csqtt-cli` уходит сама (флаг `owner`), трафик идёт напрямую. Остаётся DNS туннеля в
  DNS системы; следующий `connect` его убирает («запись … прошлого запуска снята» /
  «прежний resolv.conf возвращён»), после его остановки снимок совпадает с исходным.
- **`rp_filter`.** Действует максимум из `all` и значения интерфейса: `all = 1` при
  `2` у физического интерфейса оболочка принимает.
- **Капча.** Живой капчи VK во время приёмки не было (креды приходили сразу). Окно
  проверено на стенде из процесса под обычным `sudo`: Chromium и все его дочерние
  процессы — от вызвавшего, с окружением его графического сеанса и сессионной шиной,
  временный профиль — его, после закрытия убран; токен доходит до моста, страница ходит
  через прокси `csqtt-cli` (`Dial`), мимо прокси — ни разу. В Wayland окно ещё не
  проверялось.

## Э4. Интерактивный режим и первый релиз — 3–4 дня

### I1. Меню и мастер

Две части, каждая — отдельный коммит.

**I1a. Меню и мастер.** `menu.go`, `wizard.go`, `menu_edit.go` из qwdtt-cli: меню при
запуске без аргументов в терминале и командой `menu`; мастер профиля — вставка ссылки
`csqtt://` или вопросы вместо неё, выбор `tun` или `socks`; пункты правки — ссылки на
звонки (с проверкой текущих), пароль, адрес сервера; новые ссылки на звонки, когда старые
закрылись.

**I1b. Повышение прав.** `elevate*`, `elevated*` из qwdtt-cli: подключение в `tun` без
прав — меню само перезапускает одно подключение (`menu -connect <профиль>`) через `sudo`
на Linux или окном UAC на Windows.

**Готово, когда** тесты меню проходят, а на Linux меню из терминала доводит до
работающего туннеля без набора команд. Двойной щелчок на Windows проверяется в W8.

Итог I1a: `internal/cli` — `menu.go`, `wizard.go`, `menu_edit.go` из qwdtt-cli под наши
пакеты. Своей логики подключения и записи профилей у меню нет: подключение —
`planConnect` и `plan.run`, как `connect`; запись — `storeProfile`, как `profile add|set`;
удаление — `profile rm`; проверка звонков — общие с `hashes check` функции.

- **Запуск.** Без аргументов, когда stdin и stdout — терминал, открывается меню; без
  терминала — список команд, как раньше (в нём теперь строка о меню). Команда `menu`
  (`-config`) без терминала отказывает. Служебная команда связки ключей принимается в
  `Main` раньше меню, поэтому `sudo csqtt-cli` работает как `sudo csqtt-cli connect`:
  файлы и секреты — у вызвавшего.
- **Пункты.** Подключиться к выбранному профилю (по умолчанию — `default_profile`, иначе
  первый); выбрать другой профиль на сеанс (`default_profile` не меняется); создать профиль
  мастером; обновить ссылки на звонки; заменить пароль или адрес сервера; удалить профиль;
  выход. Без профилей — только «Создать». Ошибка пункта печатается, и меню показывается
  снова.
- **Мастер.** Ссылка `csqtt://` скрытым вводом или Enter — вручную; имя (`home`, если
  свободно, иначе `profile-N`; занятое — с вопросом о замене, замена сохраняет `device_id`);
  адрес (без порта — `46000`); пароль дважды и ссылки на звонки — скрытым вводом; режим.
  Чего нет в ссылке, спрашивается как вручную. Неверный ответ переспрашивается, конец ввода
  на любом вопросе — отмена без записи. Первый профиль становится профилем по умолчанию.
  Режим: `tun` первым и по Enter; где `tun` не работает (признак — `Requires().Unsupported`
  у `datapath.Tun`, как в `connect`; на Windows — до W3), единственный пункт — `socks` по
  Enter и строка с причиной.
- **Ссылки на звонки.** Сначала текущие проверяются ядром, как `hashes check`, с исходом
  по номерам; закрытые звонки уходят, недоступные для проверки остаются. Затем — добавить
  новые или заменить все; больше шести вместе не принимается.
- **Отмена в пунктах правки.** Пустой ответ на новый пароль и на ссылки на звонки, без
  которых не обойтись (заменить все; добавить, когда ничего не осталось; новые ссылки после
  конца звонков), отменяет пункт: профиль не меняется, меню показывается снова, после конца
  звонков подключения снова нет. Приглашение это говорит (`[не менять]`, `[отмена]`).
  Иначе из скрытого вопроса не выйти: Ctrl+D на скрытом вводе в терминале не действует, а
  Ctrl+C закрывает всё меню. В мастере пустой ответ, как и прежде, переспрашивается.
- **Звонки закрылись** (`*supervisor.HashesExhaustedError`): меню спрашивает новые ссылки,
  записывает их и подключается снова.
- **`tun` не запустится** — нет прав root или система его не умеет: та же подсказка, что у
  `connect`, и предложение подключиться в `socks` на этот раз (профиль не меняется). Отказ
  `planConnect` для этого — тип `tunRefusal` с признаком «нужны права»; текст для
  командной строки прежний. Без прав root меню с I1b запрашивает их само (см. «Итог I1b»).
- **Сигналы** меню разбирает само. Ctrl+C во время подключения или проверки звонков
  останавливает только их и возвращает в меню, в самом меню — закрывает его (код 130,
  режим терминала восстанавливается, даже посреди скрытого ввода). SIGTERM (закрыли окно
  на Windows) и SIGHUP (закрыли терминал; под `nohup` подписки нет) во время подключения
  дают снять туннель и закрывают меню. Второй сигнал во время остановки — выход сразу (с
  A3b — иначе, см. `architecture.md` §09).
  Выход из меню выбором или концом ввода — без паузы перед закрытием окна.

Тесты (на подставном вводе и выводе): меню в терминале и без него, список профилей,
переспрос, ошибка подключения и возврат в меню, выбор профиля, удаление; мастер вручную,
по ссылке с хешами и без, второй профиль и замена с прежним `device_id`, переспрос всех
неверных ответов, отмена концом ввода на каждом вопросе, режим без `tun`; правка ссылок
(закрытые уходят, непроверенные остаются, только убрать, заменить все, предел шести,
проверка не удалась, отмена), пароля и адреса; пустой ответ на скрытый вопрос правки —
отмена (в трёх местах), а в мастере — переспрос; конец звонков — с подставным подъёмом и с
поддельным ядром через настоящие `supervisor` и `plan.run`; отказ `tun` без прав и без
поддержки — предложение `socks`; разбор сигналов; на Unix — настоящие SIGINT и SIGHUP
посреди подключения с поддельным ядром. Отдельный тест со сроком: на закрытом вводе
меню, мастер и каждый вопрос правки кончаются. Вывод тестов и число скрытых вопросов
ограничены: цикл, не кончающийся на конце ввода, роняет тестовый бинарь паникой, а не
копит вывод до исчерпания памяти. Обратные правки ключевых мест — тесты падают. Живая
проверка через псевдотерминал без root: мастер вручную и по выдуманной ссылке (секреты на
экране не видны) с удалением через меню, отмена мастера, Ctrl+C на скрытом вопросе (эхо
возвращается), подключение к профилю в `socks` без аргументов до «туннель работает»,
SOCKS5 отвечает, Ctrl+C — снова меню, ядра нет, выход. Под `sudo` без аргументов с
профилем в `tun`: меню находит профиль вызвавшего, подключение до «туннель работает», при
поднятом туннеле проверка утечек L4 без провалов (внешний адрес — не прямой, DNS мимо
туннеля и IPv6 наружу закрыты); Ctrl+C — снова меню, адаптера, таблицы `nftables` и ядра
нет, выход с кодом 0; сетевые снимки до и после совпадают.

Итог I1b: `internal/cli` — `elevate.go`, `elevate_other.go`, `elevate_windows.go`,
`elevated_other.go`, `elevated_windows.go` из qwdtt-cli под наш `tunRefusal`; в `menu.go` —
`menu -connect`, перезапуск с правами и разбор сигналов, пока он идёт.

- **`menu -connect <профиль>`** (`-config`): меню не показывается, сразу подключение к
  профилю; закрылись звонки — вопрос о новых ссылках, как в меню; после остановки — выход
  с кодом 0, без паузы. Ctrl+C до подъёма туннеля — тоже не сбой. Без прав root
  `menu -connect` себя не перезапускает, а кончается ошибкой (через `sudo` — «права root не
  получены: csqtt-cli запущен через sudo, но не от root», без `sudo` — подсказка `connect`):
  `sudo`, запускающий не от root (обёртка `exec "$@"`, `runas_default`), иначе вкладывал бы
  процессы без конца.
- **Нет прав root** (`tunRefusal` с признаком «нужны права»): меню не печатает подсказку
  `sudo csqtt-cli connect`, а само запускает одно подключение с правами —
  `menu -config <абсолютный путь> -connect=<профиль>` — имя одним аргументом, чтобы профиль
  с именем вроде `-h` не стал просьбой о помощи. Путь передаётся всегда, и без
  `-config` у меню: под `sudo` `csqtt-cli` взял бы `~/.config` вызвавшего, а
  `XDG_CONFIG_HOME`, из которого читало меню, `sudo` не передаёт.
- **Linux.** `sudo -- <свой исполняемый файл> menu -connect …` в том же терминале; перед
  этим строка «sudo спросит пароль вашей учётной записи». Меню ждёт его и после остановки
  подключения показывается снова. Код 130 (Ctrl+C на вопросе запущенного csqtt-cli) и
  `sudo`, умерший от SIGINT (Ctrl+C на пароле), — «Прервано», меню. Прочие коды — строка
  «sudo или подключение с правами root завершились с кодом N — причина выше» и меню: код 1 —
  и неверный пароль, и ошибка подключения, различить их нельзя, причину каждый напечатал сам.
  Файлы и секреты под `sudo` — у вызвавшего, как у `sudo csqtt-cli connect`.
- **Сигналы.** Терминал отдаёт Ctrl+C обоим процессам; пока идёт запущенный csqtt-cli,
  меню Ctrl+C не разбирает — подключение останавливает он. SIGTERM и SIGHUP в это время
  закрывают меню, когда он закончит.
- **Взять права негде** — `sudo` нет (на Windows — учётная запись не администратор, тип
  токена не `Limited`: UAC запустил бы другого пользователя с другим `%APPDATA%` и чужими
  секретами): причина и предложение `socks` на этот раз, как в I1a.
- **Windows** (готово к W3, пока не используется: `tun` отказывает раньше, по
  `Unsupported`): окно UAC (`ShellExecute` `runas`), подключение — в новом окне, меню в
  старом закрывается; «Нет» в окне UAC — строка и меню. Проверка прав `isRoot` на Windows —
  права администратора процесса (`isElevated`), на Linux — прежняя.
- Мастер: у `tun` — «нужны права root: меню запросит их при подключении (sudo)».

Тесты: аргументы перезапуска (абсолютный `-config`, путь по умолчанию из
`XDG_CONFIG_HOME`, профиль с именем `-h` — меню, а не помощь); `menu -connect` — подключение
без меню, новые ссылки при закрытых звонках, выход после остановки, после отказа от ссылок и
после Ctrl+C до подъёма, ошибка — код 1, без root — ошибка без перезапуска; перезапуск через подмену — меню ждёт и показывается снова, ошибка — строка и меню
без `socks`, `detached` закрывает меню без паузы; прав взять негде — `socks`; настоящий
перезапуск с подставным `sudo` в `PATH` — ждёт его, аргументы, код 0, 130, SIGINT, 1,
SIGKILL, `sudo` нет; разбор сигналов при запущенном csqtt-cli и на Unix — настоящие
SIGINT и SIGHUP во время перезапуска. Обратные правки ключевых мест — тесты падают. Живая
проверка через псевдотерминал без root и без сети, с подставным `sudo`: подпись `tun` в
мастере, меню зовёт `sudo -- <csqtt-cli> menu -config <путь> -connect=<профиль>`, код 0 —
снова меню, 130 — «Прервано», 1 — строка, Ctrl+C при идущем `sudo` — меню живо, `sudo`,
запускающий не от root, — ошибка без вложенного перезапуска, без `sudo` — причина и `socks`.
Живая проверка с настоящим `sudo` и сервером: меню от пользователя, профиль в `tun`,
«Подключиться» — строка о `sudo`, подключение от root до «туннель работает» за секунды; при
поднятом туннеле проверка утечек L4 без провалов (внешний адрес — не прямой, DNS мимо
туннеля и IPv6 наружу закрыты, DNS туннеля отвечает через адаптер); Ctrl+C — «остановлено»
и снова меню пользователя, адаптера, таблицы `nftables`, ядра и `csqtt-cli` от root нет;
выход с кодом 0; сетевые снимки до и после совпадают, профиль не изменён.

### I3. Сборка релиза

Две части, у каждой — свой коммит.

#### I3a. Скрипты сборки

- `scripts/release`: архивы для Windows `amd64`, Linux `amd64` и `arm64` с `csqtt-core`,
  `wintun.dll`, лицензиями, примером настроек, README; воспроизводимые архивы, как в
  qwdtt-cli. Ядро на Rust собирается под каждую цель отдельно: своё — `buildcore`, чужие
  цели — готовыми бинарями ядра (их собирает CI); Linux `arm64` — кросс-сборкой.
- `scripts/notices`: лицензии модулей Go и crates ядра (по `cargo metadata` и файлам
  лицензий из исходников crates).
- `distcheck` (перенесён в F4) знает только `csqtt-cli`: добавить `csqtt-core` в оба
  списка и право на исполнение — обоим бинарям в `tar.gz`.

**Готово, когда** `release` собирает архив Linux `amd64` (и `arm64` кросс-сборкой),
`distcheck` его принимает, а повторная сборка архивов из тех же бинарей даёт те же байты.

Итог I3a: `scripts/release` и `scripts/notices` перенесены из qwdtt-cli и дополнены ядром;
состав архива — один список в `scripts/internal/dist`, его берут и `release`, и `distcheck`.

- **Состав.** Windows (`zip`): `csqtt-cli.exe`, `csqtt-core.exe`, `wintun.dll`,
  `wintun-LICENSE.txt`; Linux (`tar.gz`): `csqtt-cli`, `csqtt-core`; во всех —
  `THIRD_PARTY_NOTICES.txt`, `csqtt-cli.example.toml`, `README.md`, `LICENSE-core.txt`
  (копия `core/LICENSE`). Файлы — в каталоге с именем архива. `LICENSE` оболочки нет до
  I4. Перед упаковкой `release` сверяет каталог со списком: лишний или недостающий файл —
  ошибка.
- **Воспроизводимость.** Время всех записей — 1980-01-01 (наименьшее для `zip`),
  порядок — по именам, в `tar.gz` формат ustar, владелец 0:0 без имён, права 0755 у
  `csqtt-cli` и `csqtt-core` и 0644 у остального, в заголовке `gzip` ни имени, ни
  времени; в `zip` атрибуты Unix 0644, без дескрипторов данных и поля расширенного
  времени. Время и права файлов на диске в архив не попадают.
- **Ядро.** Для каждой платформы — готовым бинарём (`-core os/arch=путь`, так сделает CI в
  I3b) или сборкой `buildcore` под цель из `scripts/internal/rusttarget` (общий с
  `buildcore` и `notices`). Что соберётся, проверяется до начала работы
  (`buildcore -check`): нет ядра хоть для одной платформы — одна ошибка со всеми
  платформами и подсказкой `-core`. Готовое ядро сверяется по заголовку ELF или PE с
  процессором платформы, у ядра Windows — ещё и импорт: с динамическим CRT
  (`vcruntime*.dll`, `msvcp*.dll`, `api-ms-win-crt-*`) оно не принимается. В конце ядро
  своей платформы запускается с неизвестным ключом — должно ответить строкой
  использования и кодом 2 (в сеть не ходит); `csqtt-cli version` — как в qwdtt-cli.
- **`buildcore`.** Кросс-сборка Linux `gnu` на Linux другого процессора: линкер, `CC` и
  `AR` цели — кросс-gcc Debian и Ubuntu (`aarch64-linux-gnu-gcc`), заданные в окружении
  переменные не перебиваются; без gcc — строка с именем пакета до сборки. Ядро под другую
  систему (Windows на Linux) — отказ до сборки. `-check` — только проверки; `-out` может
  быть абсолютным. Ядро Windows (msvc) — с `+crt-static`: рантайм C вшит, VC++
  Redistributable не нужен; C-код `aws-lc` и прочих `cc` собирает с `/MT` по тому же
  флагу.
- **`notices`.** Две части: модули Go (`go list -deps`, как в qwdtt-cli) и crates, от
  которых ядро зависит по `Cargo.lock` для этой цели (`cargo metadata --locked
  --filter-platform <цель>`: только обычные зависимости, без dev, build и процедурных
  макросов с их зависимостями). Список — с запасом: граф объединяет фичи и с
  dev-зависимостями, поэтому в нём бывают crates, не вошедшие в бинарь (`rustls`, `quinn`,
  `ring`); лишнее упоминание безвредно. Первой идёт стандартная библиотека Rust
  (текст Apache-2.0 из поставки `rustc`). Вид лицензии crate — поле `license`, тексты — из
  исходников. Два crate без файла лицензии разобраны поимённо, с версией и пояснением в
  файле: `alloc-stdlib` — файл `alloc-no-stdlib` (тот же репозиторий, автор и лицензия);
  `primp` — апстрим вендорит его без `LICENSE-MIT`, копия файла из архива `primp` 1.3.1 на
  crates.io лежит в `scripts/notices/licenses/` (тест сверяет её хеш). Любой другой crate
  без файла лицензии или без `license` — ошибка.
- **`distcheck`** знает ядро в обоих списках и требует право на исполнение у обоих
  бинарей; каталог без архивов — тоже провал.
- **Проверено.** Архивы Linux `amd64` и `arm64` собираются, `distcheck` их принимает,
  повторная сборка даёт те же байты. Архив Windows `amd64` так же собирался с готовым
  ядром прежней сборки, до проверки CRT; это ядро — с динамическим CRT, и теперь `release`
  его отклоняет. Ядро `arm64` собрано `buildcore` кросс-сборкой в контейнере Ubuntu
  22.04 (старший символ glibc — 2.34); `csqtt-cli` и `csqtt-core` из распакованного архива
  `arm64` запускаются под `qemu-aarch64`. Путей машины сборки в бинарях и уведомлениях нет.
  `+crt-static` проверен только тестами флагов: ядро Windows здесь не собиралось, его
  соберёт CI в I3b. Архив Windows на Windows не проверялся — W8.

## Э5. Режим `auto_js` — 3–4 дня

### A1. Разбор входа VK

По Android-клиенту CSQTT (`VkAuthWebViewManager.kt`, `VkTokenScraper.kt`) понять поведение:
адрес OAuth, где появляется токен, срок жизни. Это справка, код не переносится. Итог — в
архитектуру.

Итог A1: поведение входа VK и ядра в `auto_js` описано в `architecture.md`, §08а; там же
решения к A2/A3. Главное: токен — OAuth implicit flow на странице VK в окне, бессрочный,
права — всё, кроме сообщений; ядру — `VK_JS_BOOTSTRAP:` с `{"token": …}` той же записью,
что `SECRETS:`; ядро создаёт один звонок до `PROCESS`, TURN-креды берёт сессиями аккаунта
(их число при переподключениях не ограничено), `CALL_UNAVAILABLE` в этом режиме не шлёт;
`FINISH_VK_CALLS` перед `STOP` завершает звонок, без него создатель только выходит. Для A3
наш код придётся отвязать от хешей: нормализация воркеров, супервизор, `connect`,
предупреждение о воркерах; хеш созданного звонка прятать в журнале по виду строки. Что
проверить живьём: экран согласия и фрагмент адреса, отказ на отозванный токен, время до
`PROCESS`, завершение звонка и длительность остановки.

### A2. `csqtt-cli vk login | logout | status`

Окно WebView2 или браузер по CDP, перехват токена, запись в хранилище секретов. Перед
входом — предупреждение о риске для аккаунта и явное согласие.

**Готово, когда** вход сохраняет токен, а `status` показывает, что он есть, но не показывает
сам токен.

Итог A2 (код): `csqtt-cli vk login | logout | status` (`internal/cli/vk.go`). Перед входом —
предупреждение о риске (§08а, «Риск») и вопрос `[y/N]` при каждом входе; без терминала —
отказ до окна. Окно входа — `internal/captcha`: тот же браузер на Chromium по CDP на Linux и
WebView2 на Windows, что у капчи, со своим временным профилем; профиль удаляется до того,
как вход вернёт токен (в нём cookie VK). Разговор с браузером по CDP у капчи и входа теперь
общий (`converse`), различаются автоматы. Адрес `blank.html` с токеном окно по CDP ловит
перехватом запроса (`Fetch.requestPaused`, своя заглушка вместо страницы VK), запасные пути —
события навигации и `location.href`; WebView2 — скриптом на каждой странице через `Bind`.
Разбирает адрес одно место: фрагмент или строка запроса, ошибка VK, повторы — токен со
сроком и «тихий» токен VK ID по одному разу, потом ошибка. Токен — секрет `vk.token` в
хранилище секретов (связка ключей, `secrets.json` 0600, DPAPI), в `profiles.toml` — секция
`[vk]` с `token_ref` и `user_id` (§10). `vk status` показывает `user_id` и где лежит токен,
не сам токен; `vk logout` стирает токен локально и подсказывает отозвать доступ приложения в
настройках VK. Тесты окна по CDP — на настоящем Chromium против стенда OAuth: адрес входа — на
несуществующем хосте, вся сеть браузера — через прокси стенда, а мимо прокси правила
резолвера браузера не разрешают ни одного имени; окно WebView2 только собирается. Живая проверка на
настоящем VK на Linux: вход через VK ID по QR-коду и коду из приложения прошёл, экрана прав
VK не показал, токен перехвачен на `blank.html` до сети, срока у него нет, повторов не было,
`vk status` токен не печатает. Не проверены вживую отказ на экране доступа, закрытие окна и
окно WebView2.

### A3. Подключение с `auto_js`

`vk_hash_mode = "auto_js"`: токен — `VK_JS_BOOTSTRAP:`, `--allow-hash-redistribution`. При
остановке — `FINISH_VK_CALLS`, затем `STOP`, как Android: созданные звонки завершаются.

**Готово, когда** живой прогон без ручных хешей поднимает туннель, а после Ctrl+C
созданные звонки закрыты.

A3 — две части, каждая отдельным коммитом:

#### A3a. Профиль и запуск ядра

Поле профиля `vk_hash_mode = "auto_js"` (оно включает оба режима ядра и
`--allow-hash-redistribution`, хешей не нужно), нормализация воркеров без хешей — до 72;
в `coreproc` — токен строкой `VK_JS_BOOTSTRAP:` той же записью, что `SECRETS:`, и только
ядру в `auto_js`; маскировка журнала (`VK_JS_BOOTSTRAP:`, хеш созданного звонка по виду
строки); команда остановки с завершением звонка (`FINISH_VK_CALLS`, затем `STOP`) — не
раньше первой строки ядра; разбор `[ФАТАЛ] API <код>` до `PROCESS` (§08а).

**Готово, когда** тесты на подменном ядре проверяют аргументы, запись stdin, маскировку,
порядок и время команд остановки, разбор фатальных ошибок; старые профили и режим с
хешами не изменились.

Итог A3a (код): поле профиля `vk_hash_mode` — `manual` (или пусто) и `auto_js`, флаг
`profile add|set -vk-hash-mode`; в `auto_js` `vk_hashes_ref` не нужен, а заданный —
предупреждение, не ошибка (ядру хеши не уходят, при возврате к `manual` они на месте);
`profile add` хешей не спрашивает, `profile set`, вернувший профиль без хешей к `manual`,
спрашивает их сам; предупреждение о воркерах в `auto_js` — по пределу 72, без входа VK —
подсказка `vk login`. `coreproc.Config` — `VKHashMode`, `VKToken`, `AutoJS`,
`NormalizedWorkers` (72 в `auto_js`, `NormalizeWorkersAutoJS`): аргументы
`--vk-hash-mode=auto_js --vk-auth-mode=auto_js --allow-hash-redistribution`, в `SECRETS:` без
хешей, следом `VK_JS_BOOTSTRAP:` той же записью (не длиннее 4 КиБ) и только в `auto_js`; без
токена ядро не запускается (`ErrNoVKToken`). Журнал в `auto_js` прячет хеш созданного
звонка по виду строки (`call/join/`, `call%2Fjoin%2F`, `joinLink=`, `(хеш: …`), `CALL_UNAVAILABLE` —
без хеша; строки `SECRETS:` и `VK_JS_BOOTSTRAP:` прячутся всегда. Остановка в `auto_js` —
`Stop` и `StopFinishingCalls` (`FINISH_VK_CALLS` и `STOP` одной записью): команды — не
раньше первой строки ядра, до `PROCESS` — 30 с, на уборку — 8 с; убито или уборка не
подтверждена — `*CallLeftError`. Выход до `PROCESS` — `ParseFatal` → `*FatalError`: ошибка
API с кодом, сеть или прочее; `TokenRejected` — коды 5, 27, 28 без приписки метода. Тесты —
на подменном ядре, которое читает stdin, как настоящее (команды до чтения секретов
теряются — проверено и обратным тестом), сторож строк ядра; на настоящем ядре с сокетами на
loopback — секреты и токен читаются одной записью, первая строка — `[П3]`, отказ сети
разбирается. Супервизор и `connect` — в A3b.

#### A3b. Супервизор, `connect` и живая приёмка

Супервизор без пула хешей в `auto_js`: отказ токена до `PROCESS` — конец с подсказкой
`vk login`, сетевые сбои — повтор и на первой попытке; остановка — с завершением звонка и
сроком на уборку. `connect` и меню: токен из хранилища, без токена — понятная ошибка до
запуска ядра, `hashes check` в `auto_js` неприменим. Текст предупреждения `vk login` — без
обещания экрана прав (живой вход его не показал).

**Готово, когда** — как у A3.

Итог A3b (код): супервизор в `auto_js` работает без пула хешей и требует токен;
`CALL_UNAVAILABLE` в этом режиме не действует — мёртвый звонок лечится перезапуском
попытки, новое ядро создаёт новый звонок. Выход ядра до `PROCESS` разбирается по строке
`[ФАТАЛ]`: отказ токена — конец на любой попытке с подсказкой `vk login`; прочая ошибка
API VK — тоже конец на любой попытке («VK отказал: …»), чтобы не плодить сессии под
аккаунтом (кроме временных кодов — см. ниже «Итог: повторы временных ошибок VK»); сетевой сбой до VK — повтор, в том числе на первой попытке; прочее (и неверное
имя сервера) — как в режиме с хешами, а подсказка о сборке ядра — только когда ядро не
приняло аргументы или данные оболочки. Остановка в `auto_js` — и пользователем, и при
перезапуске — завершает созданный звонок (`FINISH_VK_CALLS`, затем `STOP`, до 45 с,
строка «завершаем звонок VK…»); если ядро пришлось убить, пользователь узнаёт, что звонок
мог остаться в аккаунте. Второй Ctrl+C во время остановки (в обоих режимах) убивает только ядро, а `csqtt-cli` доводит свою уборку
(маршруты, DNS, kill-switch); третий — завершает процесс; если прерывать нечего — второй
завершает процесс, как раньше. `connect`: токен из хранилища, без входа — ошибка с
подсказкой `vk login` раньше проверки прав `tun`; воркеров до 72. `hashes check` для
профиля в `auto_js` отказывает; меню не предлагает обновить ссылки на звонки и помечает
такие профили; мастер режима не спрашивает — `profile set -vk-hash-mode`. Текст `vk login`
не обещает экрана прав. README и пример настроек описывают режим.

Живая приёмка (Linux, режим `socks`, настоящие VK и сервер): без ручных хешей туннель
поднимается около секунды — сессия Calls, звонок создан, креды аккаунта 1/9, 18 воркеров
на линии; трафик через SOCKS выходит с адреса сервера. Ctrl+C — `Звонки завершены 1/1`,
остановка — доли секунды. Ctrl+C до `PROCESS` — команды дожидаются ядра, звонок создаётся
и сразу завершается (1/1). Двойной Ctrl+C до `PROCESS` — ядро убито сразу, `csqtt-cli`
предупреждает, что звонок мог остаться, и выходит штатно. В журнале хеш созданного звонка
только `<хеш>`, токена и строк stdin со значениями нет. Ядро в `auto_js` ходит к
`api.vk.ru`, `calls.okcdn.ru`/`api.ok.ru` и к TURN VK. Режим `tun` под `sudo`: туннель за
секунду, весь трафик системы — через адаптер, Ctrl+C — `Звонки завершены 1/1` за ~1 с, DNS
системы возвращён, сетевое состояние машины после — как до. Живьём не проверены:
перезапуск попытки, отказ токена, меню (перезапуск и меню проверены позже — ниже, «Живые
проверки хвостов Э5»).

Маскировка ключей гостевого пути: гостевой путь VK Calls ядра кладёт временные ключи в
адреса запросов (`anonymous_token` и `secret` — шаги 2–3, `anonymToken` и `session_key` —
шаг 5), а при сбое сети адрес целиком попадает в текст ошибки HTTP-клиента: в журнал ядра
(на экран при `-v` и в файл) в любом режиме и в пояснение «недоступен» у `hashes check`.
`coreproc` заменяет их значения на `<скрыто>` — только в форме параметра адреса
(`?…=`/`&…=`); хеш звонка обрабатывается как раньше. Сторож сверяет все параметры адресов
ядра со списком открытых и спрятанных: новый параметр после обновления ядра роняет тест.

Итог: повторы временных ошибок VK. Временные ошибки API VK до `PROCESS` в `auto_js` —
коды 1 (unknown error), 6 (too many requests per second), 10 (internal server error), с
припиской метода и без — больше не кончают цикл сразу: попытка повторяется до 5 раз с
паузами 2, 4, 8, 16, 32 с (свой счёт, отдельно от общего backoff), строка переподключения
называет ответ VK и номер повтора. Работающий туннель обнуляет счёт; смена сети — нет.
Шестая временная ошибка подряд — конец «VK отказал N раз подряд, повторы исчерпаны: …»
(`*VKError`, подсказка `connect` та же). Отказ токена и прочие коды, включая 9 (flood
control), — конец сразу, как раньше; сбои сети до VK — общий backoff.

Итог: журнал и фильтр доменов окна входа. Чтобы узнать, пройдёт ли вход в VK в сети с
белыми списками, у `vk login` есть скрытый диагностический флаг `-net-allow`: окно входа
ходит в сеть только через локальный прокси `csqtt-cli` (тот же, что у окна капчи) с
фильтром — список доменов с поддоменами, набор `vk` (домены VK) или `all` (всё, только
запись). Каждое соединение — строка `хост:порт — пропущен|отказ` без путей и запросов,
после закрытия окна — сводка. Без флага окно ходит в сеть само. Подробно — §08а
`architecture.md`, «Окно входа». На стенде проверено: адрес входа на разрешённом домене —
вход проходит, на неразрешённом — страница не грузится, оба видны в журнале. Живой список
доменов страницы входа VK ещё не снят — это сделает пользователь при новом входе.

Живая проверка (Linux, настоящий VK, `vk login -net-allow vk`): вход по QR-коду проходит,
когда окну открыты только домены VK, — ему хватило шести хостов в `vk.ru`: `oauth`, `id`,
`static`, `api`, `login`, `persiq`. Отклонённые — собственные запросы Chromium к сервисам
Google и одна картинка с CDN фотографий VK (`vkuserphoto.ru`) — входу не мешают. Закрытие
окна посреди входа — «окно входа VK закрыто до конца входа; токен не записан».

Живые проверки хвостов Э5 (Linux, настоящие VK и сервер): `vk logout` стирает токен, и
`connect` профиля в `auto_js` отказывает до подключения с подсказкой `vk login`.
Перезапуск попытки по смене сети в `tun`: прежний звонок завершается (`Звонки завершены
1/1`), новое ядро создаёт новый звонок, туннель снова поднят меньше чем за секунду;
сетевое состояние машины после остановки — как до. Меню: профиль помечен «звонок VK —
auto_js», пунктов о ссылках на звонки нет, подключение и Ctrl+C с возвратом в меню
работают. Не проверены живьём: отказ отозванного токена, временные ошибки VK (1, 6, 10),
окно WebView2 с прокси.

- **Предложения автору CSQTT** — `doc/upstream-proposals.md`: наши правки ядра, которые
  стоит предложить (Android-клиенту по ядру 2.5.0 заметно полезна П4 — `SO_PEERCRED`; П1 и
  П2 — мало или нет, таблица — в документе), и найденные ошибки ядра 2.5.0, которые мы не
  правили. Отправка — решение пользователя.
- **Обновление ядра** — при выходе новой версии апстрима: клон, `vendorcore`, `-check`,
  `cargo test`, короткий живой прогон. Если протокол сменился — README называет новую
  совместимую версию сервера.
- **Ядро 2.1.9 → 2.5.0.** Сервер нужен 2.5.0: `GETCONF` клиента стал другим (без
  устройства и метки ревизии), против сервера 2.1.9 клиент молчит — DTLS без ответа,
  `GETCONF` без подтверждения. Правки: П1 — пароль из `SECRETS` через пропущенное clap поле
  (флага `--password` у ядра больше нет); П2 — параметр нового `Dispatcher`; П3, П4 — новые
  якоря; **П6 снята** — ядро само отбрасывает пакет, который ОС не приняла в TUN; **П7** —
  проверка `ONLY_PRINT_URL` в решателе капчи, которую апстрим убрал. В перенос добавлен
  `domains.txt` (его вшивает ядро). Сторож сокетов знает `direct_relay.rs`: эти сокеты
  создаются только при маршрутизации мимо туннеля, которую оболочка не включает (как и
  `--srtp-mode` — ядро работает с умолчанием `auto`). Оболочка: убраны
  `--allow-hash-redistribution` и `--device-id` (ядро их отвергает); воркеры — группами по
  10, от 5 до 100 (умолчание 10, в `auto_js` — до 70), прежние значения профиля, кратные 9,
  отвергаются с объяснением; умолчание `obfs` — `unified`. Привязки пароля к устройству в
  2.5.0 нет, но одновременно с одним паролем работает одно подключение. `notices` берёт
  лицензии `etherparse` и `yasna` из репозиториев проектов (в архивах crates.io их нет).
  Лицензия ядра — по-прежнему PolyForm NC: так говорит `LICENSE` апстрима, хотя его
  `Cargo.toml` называет `Unlicense`. Живьём: `socks` и `tun` (Linux) поднимаются за 1–2 с,
  DTLS-SRTP, адрес — сервера, защита DNS держит; не проверены капча, `auto_js`, Windows.
  Кандидаты: маршрутизация мимо туннеля (эпоха подключения и события `TUN_LOST`, `WORKERS`
  — сделаны, следующие пункты).
- **Эпоха подключения (`-gen`/`-salt`).** Каждый процесс ядра, в том числе каждая попытка
  одного `connect`, получает свою пару: номер — время Unix в миллисекундах, строго
  возрастающий в процессе оболочки, соль — 16 байт `crypto/rand` в hex. Сервер 2.5.0 с ней
  принимает запрос отключения при остановке и сразу вычищает сессии прошлой попытки; с
  прежней пустой парой отключение отвергалось, а сессии жили до тайм-аута. В профиле и на
  диске пары нет (§04). Тесты: вид аргументов, разные пары у двух запусков, настоящее ядро
  с этими флагами поднимается. Живьём (`socks`): ядро запущено с парой, туннель поднят,
  трафик идёт, остановка по Ctrl+C — мгновенно; принял ли сервер отключение, со стороны
  клиента не видно — ответ ядро в журнал не пишет.
- **События `WORKERS` и `TUN_LOST`.** `coreproc` разбирает оба (§04). `WORKERS` — лимит
  воркеров сервера для пароля: меньше запрошенного — одна строка в выводе `connect` на
  каждое новое значение, с `-v` — строка журнала на каждое событие; строка состояния не
  меняется. `TUN_LOST` (только `tun` на Linux) — ядро потеряло дескриптор адаптера: если
  адаптер на месте и прошлая потеря была не ближе 60 с, ядро получает новый дубликат через
  тот же сокет и работает дальше без перезапуска; иначе, как и при неудачной передаче или
  выходе ядра с кодом 3 после `TUN_LOST`, сеанс кончается потерей адаптера тем же путём, что
  на Windows (`Failed`, §05), а не новыми попытками с тем же мёртвым адаптером. Тесты:
  разбор событий, строка о лимите (одна на значение, и в `connect` на поддельном ядре),
  повторная передача, повтор в пределах 60 с, адаптера нет, отказ передачи, выход с кодом 3,
  режим `-listen`; настоящее ядро теряет дескриптор (`EOF`) и принимает новый без
  перезапуска; в контейнере — удалённый адаптер проверка видит. Удаление адаптера
  (`ip link del`) ядро 2.5.0 не замечает и `TUN_LOST` не шлёт (§05).
  Живьём (`socks` и `tun`, сервер без лимита для пароля): событие `WORKERS` с нулём
  разобрано, без `-v` строки нет; `tun` поднимается и убирает за собой как прежде. Живой
  `TUN_LOST` вызвать не удалось — ядро его на удаление адаптера не шлёт.
- **Молчание сервера.** Сервер другой версии ядро 2.5.0 не узнаёт: метки версии протокола
  нет, сервер молчит, ядро повторяет рукопожатие без конца, и `connect` раньше висел на
  «получены креды VK». Теперь супервизор ждёт ответа сервера (`TUNCONF`, `READY`,
  `WORKERS`) 30 с с первых кредов VK попытки — два круга ядра с переходом на WRAP-SRTP;
  пока решается капча, срок не идёт, `NETWORK_SUSPECT` начинает его заново. Если туннель
  в этом `connect` ни разу не работал и сервер в нём ни разу не отвечал (`TUNCONF`,
  `READY`, `WORKERS`, `SERVER_RESTART`), молчание — конец: ядро останавливается штатно,
  `connect` выходит с ошибкой «сервер CSQTT не отвечает», версией ядра клиента и прочими
  причинами (адрес или порт, сервер выключен). Иначе — строка в выводе, одна на эпизод
  без связи, попытки идут дальше (§09). Версия ядра — из `core/CORE_VERSION` (пакет в корне
  модуля), её печатает и `csqtt-cli version`. Событие `DTLS` по-прежнему не разбирается.
  Тесты на поддельном ядре: первое подключение (с хешами и `auto_js`) — ошибка и `STOP`,
  без повторов; при восстановлении — строка, одна на эпизод, ядро не останавливают;
  сервер уже отвечал (`TUNCONF` без `READY`, `SERVER_RESTART`), а туннель не поднимался, —
  строка, без остановки; капча и время до кредов в срок не входят; подъём чуть быстрее
  срока, ответ `TUNCONF` без `READY` — без ошибки; `connect` на поддельном ядре — код
  возврата и текст; `version`. Живьём: профиль с адресом, который глотает UDP (TURN VK
  работает, «сервер» молчит), — `connect` выходит с кодом 1 через 30 с после кредов с этим
  объяснением; с настоящим сервером туннель поднимается за секунду и держится дольше срока.
- **`auto_js` на ядре 2.5.0 — живая проверка и уборка звонка.** `socks` и `tun`: туннель
  за секунду, трафик с адреса сервера, остановка — около секунды, в `tun` сеть после
  остановки такая же, как до; токена и bootstrap в журнале нет. Нашлось: при каждой остановке
  `connect` писал «звонок мог остаться в аккаунте». Ядро 2.5.0 выходит создателем из звонка
  сразу, как готовы TURN-боты (и даже при ранней остановке), после этого VK звонка уже не
  находит — `calls.forceFinish` отвечает `9000 Call not found` (видно в диагностической
  сборке ядра), и итог `Звонки завершены 0/1`. Теперь уборка подтверждена итогом `N/N`
  выхода создателя или завершения звонка, поздняя строка `0/N` прежний `N/N` не отменяет
  (§04, §08а); ядро не менялось. Тесты: таблица состояний звонка, остановка на поддельном
  ядре со сценарием 2.5.0. Живьём после правки — предупреждения нет. Капчу (П7) живьём не
  видели: VK её не выдал.
- **Мелочи после проверки `auto_js`.** Срок уборки звонка после `PROCESS` — 15 с вместо 8 с:
  ядро 2.5.0 при остановке ждёт выхода создателя до 9 с, потом `forceFinish` до 2 с,
  остановку рантайма до 2 с и сброс журнала до 1 с, и при ранней остановке и медленном VK
  оболочка убивала бы его раньше конца уборки; вся остановка — до 45 с (§04). Событие `DTLS`
  разбирается: с `-v` — строка «ядро: DTLS, воркер N: …», без `-v` — ничего (раньше с `-v`
  шла сырая строка события); `ROUTING` с тех пор тоже разбирается (см. «Маршрутизация мимо
  туннеля»). В набор `-net-allow vk` окна
  входа добавлен `vkuserphoto.ru` (аватар на странице входа). Тесты окон капчи и входа VK
  при прогоне на машине с графическим сеансом лучше гонять под `xvfb-run`, иначе окна
  Chromium открываются на экране.
- **Маршрутизация мимо туннеля (ядро 2.5.0).** По умолчанию весь трафик идёт через туннель.
  Решения пользователя: из режимов ядра — только встроенный список российских сервисов
  (`[profile.X.routing] template = true`); свои списки, `.ru`-зоны и белые списки в профиле не
  делаются; правило маршрутизации, которое сервер назначает паролю в панели (событие `ROUTING`),
  без согласия только показывается, а с `routing.server = true` применяется командой
  `UPDATE_DOMAINS` вместо опции профиля; белый список сервера применяется с заметным
  предупреждением. Сделано: П3 для прямых сокетов ядра (точки 6–8: TCP, UDP-сессия, DNS прямого
  домена) — без привязки в `tun` прямой трафик ушёл бы обратно в адаптер; опция профиля и флаги
  ядра; разбор `ROUTING` и строка в выводе; при прямом трафике подозрение на сеть снимает только
  `READY` (рост принятых байт даёт и прямой трафик); применение правила сервера — после `PROCESS`,
  без повторов в одном процессе ядра, с отбрасыванием элементов, ломающих команду, punycode для
  национальных доменов, пределами ядра (1024 домена в белом списке, 64 КиБ строки) и
  предупреждением о чёрном списке адресов на огромный публичный диапазон. Проверки: тест в
  контейнере с настоящим ядром (`TestRealCoreNetnsDirect`: прямое соединение — через физический
  интерфейс с меткой, в адаптер — ни пакета, «закрыто» пропускает помеченные; без `-bind-if` —
  пакеты в адаптере); живьём на Linux в `socks` и `tun` — сайт из встроенного списка и домен из
  правила сервера открываются с адреса машины, прочие — с адреса сервера, команда правила уходит
  один раз на процесс ядра и повторно после перезапуска, при перезапуске ядра kill-switch режет и
  прямой трафик; белый список сервера — строка-предупреждение, в туннеле только домен списка.
  Не проверено: Windows (R6). Не делалось (кандидаты):
  прямой трафик в Linux-`tun` без воркеров (ядро его выбрасывает), откат в туннель при неудачном
  прямом соединении, отдельный счёт прямого трафика (подробно — `doc/upstream-proposals.md`).
