# Архитектура csqtt-cli

Настольный **консольный** клиент к CSQTT: системный VPN поверх TURN-инфраструктуры звонков
VK. Оболочка на Go, ядро CSQTT на Rust — отдельным процессом рядом с ней.

Это только клиент. Установка сервера, веб-панель, обновления, автопауза на Wi-Fi и
исключения приложений остаются в Android-приложении CSQTT. Службы и автозапуска нет:
клиент работает, пока запущен `csqtt-cli connect`.

- **Ядро:** CSQTT 2.1.9, протокол `CSQTT-WIRE-3` ([amurcanov/csqtt](https://github.com/amurcanov/csqtt)),
  PolyForm Noncommercial 1.0.0
- **Свой код:** MIT (`LICENSE`; §11). Сборка целиком — некоммерческая из-за ядра
- **Основа оболочки:** [qwdtt-cli](https://github.com/FreedomCats/qwdtt-cli) — консольный
  клиент к qWDTT того же автора. Из него переносятся меню, профили, секреты, маршруты, DNS,
  kill-switch, окна капчи и слежение за сетью
- **Приоритет платформ:** Windows → Linux. macOS — не планируется
- **План работ:** этапы — §12, задачи по шагам — `plan.md`. Журналы этапов
  (`plan-e*.md`) ведутся локально в `doc/local/` и в репозиторий не входят

## 01. На чём стоит проект

Всё ниже проверено чтением кода ядра 2.1.9, а не взято из описаний.

| Факт | Где в ядре | Следствие |
|---|---|---|
| Туннель L3 без WireGuard: ядро возит сырые IP-пакеты, адрес `/32` и DNS сервер выдаёт строкой `TUNCONF:<ip>:<dns,…>` | `protocol.rs`, `session.rs`, `main.rs` | wireguard-go не нужен. Адаптер настраиваем сами по `TUNCONF` |
| Повторный `TUNCONF` — смена DNS на работающем туннеле | `main.rs` (`config_task`) | DNS адаптера и защиту DNS надо уметь менять на ходу |
| Ядро — отдельная программа: события `__CSQTT_EVENT__|<вид>|<json>` в stdout при `CSQTT_EVENTS=1`, команды в stdin | `events.rs`, `main.rs` | Встраивать как библиотеку не нужно, граница процесса уже есть |
| При `CSQTT_EVENTS=1` закрытие stdin останавливает ядро | `main.rs` (`start_control_input`) | Смерть оболочки = смерть ядра, на всех ОС |
| Режим `-listen`: обмен пакетами по UDP на loopback, ответ — адресу последнего отправителя | `dispatcher.rs` (`read_udp`, `ArcSwapOption`) | Та же дыра, что в qwdtt-cli закрывало решение Р4: один чужой датаграм уводит туннель. Нужна правка П2 |
| Режим `-tun-uds`: ядро получает готовый дескриптор TUN через абстрактный unix-сокет (`SCM_RIGHTS`) | `tun.rs`, `dispatcher.rs` (`run_tun`) | На Linux пакеты могут идти мимо оболочки |
| Сокеты ядра наружу создаются в 5 местах | `dns.rs`, `turn.rs`, `turn_stream.rs`, `auth.rs`, `vk_js_calls.rs` | Обход туннеля — правкой в этих точках (§06) |
| Свой резолвер: UDP :53 к DNS Яндекса, системный — только до первого `TUNCONF` | `dns.rs` | DNS ядра тоже должен идти мимо туннеля; защита DNS обязана его пропускать |
| Пароль и хеши VK передаются аргументами `-password`, `-vk` | `main.rs` (`Arguments`) | Видны любому процессу машины. Правка П1 переносит их в stdin |
| Капча: ядро печатает `CAPTCHA_SOLVE|<auto\|manual>|<redirect_uri>|<session_token>` и ждёт `CAPTCHA_RESULT|<токен или error:…>` | `captcha.rs` | Окна капчи qwdtt-cli подключаются к этому протоколу (§08) |
| Проверка хешей: `--validate-vk-hashes` печатает `HASH_CHECK:<json>` на каждый хеш и завершается | `main.rs` | Команда `csqtt-cli hashes` без своей логики |
| Воркеры — группами по 9, максимум 126; без `auto_js` — не больше 27 на хеш | `main.rs`, `worker.rs` | Нормализацию числа воркеров повторяем в валидации профиля |
| Ядро собирается под Windows (MSVC) без NASM и CMake и под Linux `gnu`; под `musl` — нет: у musl флаги `recvmmsg`/`sendmmsg` — `c_uint`, а в `msghdr` закрытые поля выравнивания | `udp_batch.rs`, сборка в Э0 | Linux — цель `gnu`, нижняя граница glibc — по машине сборки (§09б) |

### Что изучено рядом

- **CSQTT-Windows** ([r3waz73/CSQTT-Windows](https://github.com/r3waz73/CSQTT-Windows)) —
  клиент стороннего автора: WinForms, ядро без правок отдельным процессом, мост
  Wintun ↔ UDP на C#. Мимо туннеля ведут маршруты `/32`, адреса TURN выбираются регулярным
  выражением из журнала ядра. Ядро в нём совпадает с апстримом 2.1.9. Полезен как
  проверенный контракт запуска ядра.
- **focsq** ([luminescq/focsq](https://github.com/luminescq/focsq)) — Flutter, ядро собрано
  библиотекой, Wintun и `/dev/net/tun` встроены в само ядро. Мимо туннеля ведут половинные
  маршруты, 13 захардкоженных подсетей VK, `/32` на TURN и NRPT. Полезны правки ядра с
  пометкой `[FOCSQ]`: капча на десктопе, не-IP пакеты в TUN. Дизайн и бренд focsq закрыты
  — не берём.

### Что берём и что нет

**Берём:** ядро CSQTT целиком — авторизацию VK, решатель капчи (пока выключен, Р7), TURN
по UDP и TCP/TLS, WRAP-ключ, маскировку `audio`/`video`, FEC, диспетчер и воркеры,
проверку хешей.
Режим `auto_js` (ядро само создаёт звонки по токену VK) — отдельным этапом (Э5).

**Не берём:** установку сервера по SSH, веб-панель, автообновление, автопаузу на Wi-Fi,
исключения приложений, виджеты, Android-обвязку капчи.

## 02. Восемь решений

### Р1. Ядро — отдельный процесс, оболочка — на Go

`csqtt-cli` запускает `csqtt-core` (собранный из `core/` клиент CSQTT) и говорит с ним
через аргументы, stdin и stdout — как Android-приложение CSQTT.

**Причина.** Ядро уже устроено как подпроцесс: весь обмен — текстовые команды и события.
Связать Rust-библиотеку с Go — значит включить cgo, а qwdtt-cli собирается без него
(статический бинарь, кросс-сборка одной командой). Переписать на Rust оболочку — это
около 13 тысяч строк кода, уже проверенного на живых прогонах. Отдельный процесс заодно
держит границу лицензий: PolyForm NC у ядра, MIT у оболочки.

**Цена.** В qwdtt-cli библиотека была необходимым условием обхода туннеля: хук на сокеты
ставился изнутри процесса. Здесь этот хук переезжает в само ядро — правкой П3 (Р3).

### Р2. Ядро вендорится целиком, правки — правилами

Исходники `rust-client/` и `shared/` апстрима лежат в `core/` без изменений, поверх —
наши правки П1–П6 (§07). Перенос — `go run ./scripts/vendorcore` из свежего клона апстрима
(соседний каталог `csqtt` или `-upstream <клон>`), как в qwdtt-cli: каждое правило —
шаблон и обязательное число совпадений. Апстрим переписал строку — перенос падает, а не
теряет правку молча. `vendorcore -check` сверяет `core/` с апстримом и правилами. Версия
апстрима — в `core/CORE_VERSION`.

`core/` целиком принадлежит `vendorcore`: руками туда ничего не кладут, лишний файл
перенос удаляет, а `-check` называет. Правку, которую проще написать отдельным модулем,
чем вставками, `vendorcore` кладёт в `core/` из `scripts/vendorcore/files/` (тот же путь,
что в `core/`), а правила только подключают её. Файл с тем же путём в апстриме — ошибка
переноса.

Крейт crates.io, который приходится править (П3 — `primp-hyper-util`, §06), хранится
нетронутым — архивом `.crate` с crates.io в `scripts/vendorcore/crates/`. Перенос берёт
версию и контрольную сумму крейта из `Cargo.lock` апстрима, сверяет с ними архив,
проверяет пути внутри него и распаковывает в `core/`. Дальше файлы крейта — как файлы
апстрима: к ним применяются правила, их сверяет `-check`. Своя правка к крейту — те же
правила и модуль из `files/`. Апстрим поднял версию крейта — перенос падает и называет
архив, который нужно положить. Версия и сумма крейта записываются в `CORE_VERSION`
строкой `crate`. Архив, а не распакованная копия: происхождение проверяется суммой из
`Cargo.lock`, второй копии кода крейта в репозитории нет, сеть ни переносу, ни `-check` не
нужна, а изменения крейта при обновлении видны в diff `core/`. `.gitignore` крейта не
переносится: он прятал бы файлы крейта от git репозитория.

Не трогается только выход сборки cargo
(`core/rust-client/target`). Текст переносится с LF, как он лежит в git апстрима; концы
строк `-check` не различает — git на Windows выкладывает файлы с CRLF. Лицензия ядра
из корня апстрима переносится в `core/LICENSE`: PolyForm требует, чтобы текст лицензии
шёл с каждой копией кода.

**Причина.** Апстрим публикуется снимками без истории изменений, и между версиями меняется
протокол: клиент от прежней ревизии с новым сервером несовместим. Поэтому `rust-client` и
`shared` переносятся только вместе и только целиком. Свои правки должны быть видны
отдельно от кода апстрима, иначе каждое обновление превращается в ручное слияние.
focsq правит ядро изнутри — так делать не будем.

### Р3. Обход туннеля — привязка сокетов ядра к физическому интерфейсу

Когда `tun` забирает весь трафик системы, сокеты ядра — VK, DNS, TURN — тоже попадают в
туннель, и туннель зависит от самого себя. Оболочка выбирает физический интерфейс (как
`netguard` в qwdtt-cli) и передаёт его индекс ядру. Ядро привязывает к нему каждый свой
сокет: на Windows — `IP_UNICAST_IF`/`IPV6_UNICAST_IF`, на Linux — `SO_BINDTOIFINDEX` и
метка `SO_MARK` для защиты DNS и kill-switch (§06, §09б). Сокеты клиентов HTTPS (`primp`)
привязывает так же вендоренный и пропатченный коннектор `primp-hyper-util` (§06).

**Причина.** Оба существующих десктоп-клиента ведут трафик ядра мимо туннеля маршрутами, и
это ненадёжно. Адреса TURN узнаются из журнала уже после того, как сокет открыт; адреса VK
меняются вместе с CDN; захардкоженные подсети устаревают; между новым адресом и
появлением маршрута есть окно, когда пакеты уходят в туннель. С kill-switch маршруты не
помогают вовсе — нужен признак сокета, а не адреса.

### Р4. Канал пакетов: loopback с закреплённым отправителем, на Linux — дескриптор TUN

- **Windows, `tun` и `socks`; Linux, `socks`.** Оболочка держит UDP-сокет на
  `127.0.0.1` и обменивается с ядром сырыми IP-пакетами (режим `-listen`). Правка П2:
  ядро принимает датаграмы только от адреса, переданного при запуске, и только ему
  отвечает. Ядро слушает `127.0.0.1:0`, свой порт сообщает событием `LISTEN`, и оболочка
  (`datapath.Link`) так же принимает только с этого порта. Сокет оболочки на Windows — с `SO_EXCLUSIVEADDRUSE`, чтобы его порт никто не
  занял.
- **Linux, `tun`.** Оболочка создаёт `/dev/net/tun` (`IFF_TUN | IFF_NO_PI`, без
  `IFF_VNET_HDR`), настраивает его и передаёт дескриптор ядру через `-tun-uds` — тем же
  способом, что Android. Пакеты идут между ядром и адаптером напрямую, без копирования
  через оболочку. Правка П4: ядро принимает дескриптор только от процесса с тем же
  эффективным uid (`SO_PEERCRED`) — абстрактный сокет открыт всем процессам машины.
  Чужое соединение закрывается, не читая, и ядро ждёт следующего. Оболочка в ответ
  отдаёт дескриптор, только если сокет слушает запущенное ею ядро (тот же
  `SO_PEERCRED`, со стороны подключившегося): имя сокета видно в командной строке ядра, и
  чужой процесс мог бы занять его раньше.

**Отвергнуто:** Wintun внутри ядра, как у focsq, — это второй платформенный слой на Rust
рядом с нашим `winsys` и большая правка ядра.

### Р5. Жизнь процесса ядра

Ядро запускается на каждую попытку подключения и завершается с ней. Порядок остановки:
команда `STOP`, ожидание до 3 секунд, затем принудительное завершение. В `auto_js` сроки
и порядок свои: ядро сначала создаёт звонок и только потом читает команды (§04, «Остановка»).
Страховки на случай падения оболочки:

- stdin ядра — канал оболочки; при `CSQTT_EVENTS=1` его закрытие останавливает ядро на
  любой ОС;
- Windows — Job Object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`: ядро не переживёт оболочку,
  даже если зависнет;
- Linux — `Pdeathsig: SIGKILL` при запуске, вдобавок к проверке `getppid` в самом ядре.
  `Pdeathsig` срабатывает на завершение потока, создавшего процесс, а не всей оболочки,
  поэтому горутина, запустившая ядро, держит свой поток (`LockOSThread`), пока ядро живо.

Ctrl+C в консоли ядро не получает: ядро ловит его само и без этого остановилось бы мимо
оболочки. На Windows оно запускается без консоли (`CREATE_NO_WINDOW`), на Linux — в своей
группе процессов.

`csqtt-core` ищется только в каталоге `csqtt-cli`, как `wintun.dll` в qwdtt-cli: ни
текущий каталог, ни `PATH` не подходят.

### Р6. Секреты — через stdin, не через аргументы

Правка П1: флаг `-secrets-stdin`, и первой строкой stdin ядро читает
`SECRETS:<base64 json>` с паролем и хешами. Токен VK для `auto_js` и так приходит через
stdin (`VK_JS_BOOTSTRAP:`), следующей строкой той же записи.

Как устроено (`secrets_stdin.rs`):

- json — `{"password": "…", "vk": "…"}`, `vk` — то же, что значение `-vk` (хеши через
  запятую); в `auto_js` оболочка его не передаёт. Других полей нет;
- строка читается до рантайма и до разбора режима, поэтому секреты так же получает и
  `-validate-vk-hashes`;
- ждёт 15 с, строка — не длиннее 16 КиБ. Пароль или хеши в аргументах вместе с флагом —
  ошибка: прятать уже нечего;
- читается через `std::io::stdin()`, а не своим буфером. Следующие строки остаются в общем
  буфере stdin, и `tokio::io::stdin` ядра читает их следом. Со своим буфером они бы
  пропали — проверено обратной правкой: STOP, пришедший одной записью с секретами, не
  доходил;
- сообщения об ошибках не содержат значений: журнал ядра пишется в файл.

**Причина.** Командную строку процесса видит любой пользователь машины: на Linux —
`/proc/<pid>/cmdline`, на Windows — `Win32_Process.CommandLine`. Пароль подключения — это
WRAP-ключ: из него выводится ключ маскировки, и его утечка равна компрометации всего
транспорта.

### Р7. Капча: окно, затем вручную; решатель ядра выключен

Цепочка ядра (`captcha.rs`, режим `auto`): Rust v2 дважды → два автоматических
прогона в WebView по 10 секунд → Rust v2 ещё раз → ручное окно на 180 секунд (П5; у
апстрима — 60). Вся цепочка идёт на одной сессии капчи: `redirect_uri` и
`session_token` в каждом её запросе одни и те же.

**Решатель ядра выключен.** Оболочка запускает ядро с `ONLY_PRINT_URL=1`: шаги Rust v2
сразу отказывают, не трогая сессию. Живая запись показала, что решатель её портит: на
галочке он получает `BOT`, на слайдере — ошибку, а потом человек в окне на той же сессии
ставит галочку и получает `ERROR_LIMIT` («Лимит попыток исчерпан») — капчу уже не решить.
С выключенным решателем окно получает нетронутую сессию, и галочка в нём проходит.
Выключатель — проверка в самом ядре; тест-сторож в `coreproc` падает, если новая версия
ядра её потеряет.

Оболочка отвечает на `CAPTCHA_SOLVE`:

- `auto` — сразу `error:unsupported`: автопрогона в окне на десктопе пока нет, ждать
  20 секунд незачем;
- `manual` — окно капчи: WebView2 на Windows, браузер на Chromium под управлением (CDP)
  на Linux, иначе — ручной режим со страницей в браузере системы и токеном, который
  человек переносит в терминал (§08).

Правка П5 поднимает время ручного окна с 60 до 180 секунд: опыт qwdtt-cli показал, что
человеку минуты не хватает. Конец окна ядро оболочке не сообщает — окно оболочки
закрывается своим таймером на те же 180 секунд.

**Открытый вопрос — авторешатель.** Он нужен: сейчас капчу на десктопе решает только
человек. Капча бывает только в пути входа VK `legacy` (повтор
`calls.getAnonymousToken` с `success_token`); режим ядра по умолчанию — `vkcalls`, где
капча редка, а в `legacy` ядро уходит после двух неудач VK Calls. Android-клиент на
`CAPTCHA_SOLVE|auto` запускает собственный автоматический WebView на 10 секунд, дважды.
Гипотеза: авторешение на Android даёт прежде всего этот автопрогон, а не Rust v2. Тогда
авторешатель на десктопе — такой же автопрогон в нашем окне на `auto` вместо
`unsupported`, а решатель ядра остаётся выключенным, пока не доказано, что он не портит
сессию для окна. Проверяется живыми прогонами, когда до него дойдёт очередь.

### Р8. Профили в TOML, секреты — в DPAPI и связке ключей

Как в qwdtt-cli: в `profiles.toml` нет ни одного секрета; пароль, хеши и токен VK
шифруются DPAPI на Windows и лежат в связке ключей (Secret Service) на Linux, без неё — в
`secrets.json` с правами `0600`. Поля профиля — §10.

## 04. Протокол с ядром (`coreproc`)

### Запуск

| Поле профиля | Аргумент ядра |
|---|---|
| `peer` | `-peer <хост:порт>` |
| `workers` | `-workers <число>` — уже нормализованное (§10): с хешами — не больше 27 на хеш, в `auto_js` — не больше 72 (`Config.NormalizedWorkers`); короткое имя `-n` ядро тоже понимает |
| `obfs` | `-obfs audio\|video` |
| `turn_transport` | `-turn-transport udp\|tcp_tls` |
| `turn_host`, `turn_port` | `-turn`, `-port` — только если заданы |
| `fingerprint` | `-fingerprint` |
| `client_ids` | `-client-ids` |
| `vk_hash_mode = "auto_js"` | `-vk-hash-mode auto_js`, `-vk-auth-mode auto_js`, `--allow-hash-redistribution`; хеши не нужны (§08а). `manual` и пусто — флагов нет, хеши профиля |
| `captcha_mode` | `-captcha-mode` (по умолчанию `auto`) |
| `device_id` | `-device-id` — постоянный на профиль |
| пароль, хеши; токен VK в `auto_js` | через stdin (П1, §08а) |
| — | `-listen 127.0.0.1:0` и `-listen-peer` (П2) или `-tun-uds <случайное имя>` |
| — | `-bind-if <индекс>`, на Linux ещё `-mark <метка>` (П3) — для всех пяти точек, включая коннектор `primp`; `-mark` — только вместе с `-bind-if` |

Окружение: `CSQTT_EVENTS=1` и `ONLY_PRINT_URL=1` — решатель капчи ядра выключен (Р7).
Число потоков рантайма ядро выбирает само по числу воркеров.
Флаги передаются в виде `--имя=значение`: значение с дефиса в начале, отдельным словом,
ядро прочло бы как флаг. Пароля, хешей и токена VK среди аргументов нет — только
`--secrets-stdin`. Ядро в `auto_js` без токена не запускается (`ErrNoVKToken`).
Неверные флаги П3 — индекс без интерфейса, `-mark` без `-bind-if` или на Windows, метка
без прав — ядро не стартует: строка `[ФАТАЛ] [П3] …` в журнале и ненулевой код выхода.

### События (stdout)

| Событие | Что делает оболочка |
|---|---|
| `PROCESS {pid}` | запоминает pid для журнала; в режиме `-tun-uds` — отдаёт ядру с этим pid дескриптор адаптера (§05) |
| `LISTEN {port}` | порт UDP-сокета ядра в режиме `-listen` (П2): туда `link` шлёт пакеты; в режиме `-tun-uds` события нет |
| `CONFIG {config}` с `TUNCONF:…` | первое — `Datapath.Start`; следующие — `UpdateDNS` |
| `PROGRESS {kind:"credentials"}` | шаг «VK» в строке состояния |
| `READY {worker}` | первый — «туннель работает»; счётчик живых воркеров |
| `STATS {active, bytes_up, bytes_down}` | строка состояния: воркеры, трафик, скорость |
| `ACTIVE_ZERO` | живых воркеров нет — `Degraded` (§09) |
| `NETWORK_SUSPECT` | серия таймаутов TURN — проверить сеть, `Degraded` |
| `CALL_UNAVAILABLE {hash, code}` | хеш помечается мёртвым (как 954 в qwdtt-cli); в `auto_js` не приходит (§08а), а если придёт — без хеша: `coreproc` его стирает |
| `SERVER_RESTART {source:"panel"}` | сервер перезапущен из панели — перезапуск через 4 с, как на Android |
| `ERROR {code, message, fatal}` | `fatal` — конец попытки; `handshake_rejected` и `handshake_timeout` — отказ и молчание сервера, у каждого своя строка для пользователя (тексты — по живым прогонам) |
| `STOPPED` | ядро закончило уборку |

Кроме событий в stdout приходят `CAPTCHA_SOLVE|…` (§08) и `HASH_CHECK:{…}`. Остальной вывод
ядра — журнал на русском в stderr: он идёт в журнал `csqtt-cli` и на экран при `-v`. Токены
капчи в журнале оболочка прячет до вывода (§08), хеши звонков `csqtt-cli` печатает номерами
в профиле (`<хеш №2>`). В `auto_js` хеш созданного ядром звонка оболочке неизвестен, и
`coreproc` прячет его по виду строки (`<хеш>`, §08а); значения строк `SECRETS:` и
`VK_JS_BOOTSTRAP:`, если они вдруг попадут в журнал, прячутся в любом режиме. Так же в
любом режиме прячутся временные ключи гостевого пути VK Calls в адресах запросов
(`anonymous_token`, `secret`, `anonymToken`, `session_key` → `<скрыто>`): при сбое сети
адрес целиком попадает в текст ошибки HTTP-клиента — в журнал и в пояснение «недоступен»
у `hashes check`.

**Выход до `PROCESS`.** Причину ядро пишет строкой `[ФАТАЛ] …` и выходит с кодом 1;
`coreproc.ParseFatal` разбирает её в `*FatalError`: ошибка API VK или OK Calls с кодом
(`API <код>: …`, с методом, если ядро его приписало), сеть (запрос не ушёл, ответ не
дочитан, HTTP не 2xx, ответ не JSON), не разрешилось имя сервера (`FatalPeer`), ядро не
приняло данное оболочкой (`FatalClient`: аргументы, `-bind-if`, секреты и данные `auto_js` в
stdin) или прочее (ответ VK не того вида). `TokenRejected` — VK отверг токен (§08а).

**Проверка хешей** (`csqtt-cli hashes check`) — тот же бинарь в режиме
`--secrets-stdin --validate-vk-hashes` (`coreproc.CheckHashes`): хеши — строкой `SECRETS:`,
пароль в ней пустой (проверке он не нужен), сервер не нужен. Ядро печатает `HASH_CHECK` на
каждый хеш — `valid`, `invalid` с кодом VK, `unavailable` — и выходит; команд stdin в этом
режиме оно не читает, поэтому отмена сразу завершает процесс. Хеши проверяются по одному:
два запроса к VK (мёртвый отсеивается на первом), при неудаче — вторая попытка, тайм-аут
запроса 20 с (он обрывает попытку). Живой хеш — несколько секунд, если VK тормозит — до
полутора минут.

### Команды (stdin)

Первой строкой — `SECRETS:<base64 json>` (П1, Р6), за ней при `auto_js` —
`VK_JS_BOOTSTRAP:<base64 json>` — той же записью (§08а); запись не длиннее 4 КиБ, чтобы
ядро получило её одним чтением. Дальше — команды:

`STOP` · `PAUSE` · `RESUME` · `CAPTCHA_RESULT|<токен>` · `CAPTCHA_RESULT|error:<причина>` ·
`FINISH_VK_CALLS` (`auto_js`: при остановке завершить звонок, §08а).
Добавляет правка П3: `BIND_IF:<индекс>` — новый физический интерфейс без перезапуска
ядра; его берут все новые сокеты, в том числе соединения `primp` (§06). Отказ — ядро
запущено без `-bind-if`, индекс не число, ноль или без интерфейса — строка в журнале,
отдельного события нет; сокеты остаются на прежнем интерфейсе.

**Остановка.** С хешами — `STOP`, 3 с, затем принудительно (Р5). В `auto_js` — `Stop`
(создатель выходит из звонка) или `StopFinishingCalls` (`FINISH_VK_CALLS` и `STOP` одной
записью — звонок завершается), выбор за вызывающим:

- команды уходят не раньше первой строки вывода ядра или его выхода: записанные до того,
  как ядро прочло `SECRETS:`, оно выбросит вместе с буфером bootstrap (§08а). Первая
  строка с `-bind-if` — `[П3] Сокеты ядра — через интерфейс …` сразу после секретов, без
  него — `[VK JS] Сессия Calls подтверждена`; до чтения секретов ядро пишет только
  `[ФАТАЛ]` перед выходом;
- сроки: до `PROCESS` — 30 с с начала остановки (ядро создаёт звонок и команд не
  читает), после `PROCESS` — 8 с на уборку (`calls.forceFinish` до 2 с, журнал до 1 с);
- не уложилось — ядро убивается, и `Stop` возвращает `*CallLeftError` (`Killed`). Тот же
  тип — если ядро вышло, но звонок создан, а итог уборки не `N/N`
  (`[VK JS] Звонки завершены K/N` или `Создатель вышел из звонков K/N`): звонок мог остаться;
- `Kill` — убить ядро сразу, не дожидаясь сроков (второй Ctrl+C, §09): идущая остановка
  возвращается тут же, в `auto_js` — с `*CallLeftError` (`Killed`). Ядро, убитое уже после
  того, как подтвердило уборку `N/N`, звонка не оставило — ошибки нет.

Разбор событий и строк — чистая функция с тестами на записях настоящего вывода ядра,
снятых живым прогоном (без адресов и хешей). Строки, по которым оболочка разбирает
`auto_js` (отказ, хеш звонка, итог уборки), сверяет с исходником ядра тест-сторож
`TestAutoJSStringsInCore`.

## 05. Datapath

Ядро всегда делает одно: принимает сырые IP-пакеты и уносит их через TURN. Datapath
решает, откуда пакеты берутся, и настраивает систему по `TUNCONF`.

Супервизору от datapath нужно немногое, а канал с ядром он получает отдельно — ровно один
из двух:

```go
type Datapath interface {
    Start(ctx context.Context, conf datapath.TunConf) error // первый TUNCONF попытки: адрес /32 и DNS
    UpdateDNS(dns []netip.Addr) error                       // повторный TUNCONF с другим DNS
}

// Link — loopback (socks, tun на Windows): Addr — в -listen-peer, порт ядра — из LISTEN.
type Link interface {
    Addr() netip.AddrPort
    SetCorePort(port uint16)
}

// TunFD — дескриптор адаптера (tun на Linux): имя — в -tun-uds, дескриптор — после PROCESS.
type TunFD interface {
    SocketName() string
    SendFD(ctx context.Context, socket string, pid int) error
}
```

`Requirements`, `Persistent` (`Suspend`), `Reserver`, `DNSGuard` (`Enable`, `Disable`) и
необязательный `IPv6Blocker` — из qwdtt-cli без изменений по смыслу; в `Requirements` пока
только `Unsupported`, `Admin`, `Netguard` и `DNSGuard`. `Requires` и `Close` у реализаций
есть, но вызывает их `connect`, а не супервизор, поэтому общего интерфейса с ними нет.

| Реализация | Как доставляет трафик | Права | Охват | Этап |
|---|---|---|---|---|
| `socks` | gVisor netstack + SOCKS5 на `127.0.0.1:1080`, канал — loopback | не нужны | только программы с прокси | Э1 |
| `tun` (Windows) | Wintun (`golang.zx2c4.com/wireguard/tun`, без WireGuard) ↔ loopback | администратор | весь трафик системы | Э2 |
| `tun` (Linux) | `/dev/net/tun`, дескриптор у ядра | root | весь трафик системы | Э3 |

`external` из qwdtt-cli нет: WireGuard в протоколе не участвует.

**`socks`.** В qwdtt-cli netstack стоял за wireguard-go, здесь он сам — конец туннеля:
адрес /32 — из `TUNCONF`, MTU — 1300, как у адаптера Android-клиента. SOCKS5 — свой:
`CONNECT` в Э1, `UDP ASSOCIATE` позже. Пароля у него нет, поэтому слушает он только
loopback: иначе туннель был бы открыт всей сети. Имена из запросов `CONNECT` резолвятся
DNS туннеля через тот же netstack — свой резолвер, без hosts и доменов поиска системы, —
так что DNS приложения не идёт мимо туннеля. Запрос, который туннель не выполнит (IPv6,
`BIND`, туннель ещё не поднят), получает отказ сразу, а не по таймауту.

`Socks` живёт весь сеанс и владеет `Link`. Слушатель SOCKS5 открывается до запуска ядра,
чтобы занятый порт выяснился до входа в VK. `Start` вызывается на каждую попытку: при том
же адресе соединения переживают перезапуск ядра, потому что TCP повторит пакеты, сброшенные
между попытками. При другом адресе соединения рвутся: ответы на прежний не придут.

**`tun`, общее.** Маршруты — как в qwdtt-cli: `0.0.0.0/1` и `128.0.0.0/1` на адаптер,
исходный шлюз не трогается. Сервер выдаёт только IPv4, но `::/1` и `8000::/1` тоже уходят
на адаптер: иначе весь IPv6 машины шёл бы мимо туннеля с настоящим адресом. Пакеты IPv6
оболочка отбрасывает, не отдавая ядру, и программы откатываются на IPv4. На Linux, где
пакеты идут мимо оболочки, IPv6 не маршрутизируется в туннель вовсе — IPv6 наружу
закрывает таблица защиты (`datapath.IPv6Blocker` из qwdtt-cli), а локальная сеть IPv6
работает, как и на Windows.

Не-IP пакеты от сервера (служебные ответы) в адаптер не пишутся: на Windows их
отбрасывает мост, на Linux их не принимает сам TUN, а правка П6 в ядре отбрасывает такой
пакет и продолжает запись.

**`tun` на Linux.** Адаптер `csqtt-cli` — свой `TUNSETIFF` на `/dev/net/tun` с
`IFF_TUN | IFF_NO_PI`, без `IFF_VNET_HDR` (`tun.CreateTUN` из wireguard-go включает
разгрузку, которой ядро CSQTT не понимает). Создаётся он при первой надобности — первая
передача дескриптора или первый `Start` (`Open` — чтобы отказ выяснился до VK) — и
живёт весь сеанс. Интерфейс не постоянный: он исчезает с последним дескриптором, так что
упавшие оболочка и ядро адаптера не оставляют, а чужой интерфейс с тем же именем — не
остаток, его не удаляют, а называют в отказе. Второй `csqtt-cli` с `tun` на машине
получает отказ по абстрактному сокету `@csqtt-cli-tun` (`Reserve` — до первой попытки).
`Start` задаёт адрес /32 из `TUNCONF` (новый в другой попытке заменяет прежний на том же
интерфейсе), MTU 1300, поднимает адаптер и ставит `0.0.0.0/1` и `128.0.0.0/1`, затем —
защиту DNS и DNS системы; `Suspend` снимает их и маршруты, `Close` — их же и закрывает
дескриптор.

`connect` с `tun` готовит всё до похода в VK, чтобы отказ был понятной ошибкой, а не
циклом переподключений. Ещё до чтения секретов — `Requires`: на другой системе отказ с
подсказкой `-datapath socks`, без root — с подсказками `sudo` и `-datapath socks`. Затем
по порядку: резерв адаптера (`Reserve`); физический интерфейс для сокетов ядра и проверка
`rp_filter` на нём (§06, §09б); остатки DNS упавшего прошлого запуска (`Recover` — после
резерва, когда второго `csqtt-cli` с адаптером быть не может; незнакомый генератор
`resolv.conf` — отказ здесь же); таблица защиты и «закрыто» (§09б); адаптер (`Open`).
Защита открывается раньше адаптера: `Tun` получает её только при создании
(`TunOptions.DNSGuard`), а отказ `Open` снимает и таблицу. Затем — слежение за сетью и
цикл супервизора. Снимается всё в обратном порядке: слежение, адаптер (DNS системы и
защиту снимает его `Close`), таблица, резерв.

DNS системы — как в qwdtt-cli: способ (systemd-resolved, resolvconf Debian или openresolv,
перезапись `/etc/resolv.conf`) `linuxsys.DetectSystemDNS` выбирает при создании адаптера,
и незнакомый генератор `resolv.conf` — отказ открытия, до VK. Защита DNS — таблица
nftables `inet csqtt-cli` с `owner` (`linuxsys.DNSGuard`): сессию открывает вызывающий и
отдаёт в `TunOptions.DNSGuard`, `Tun` только включает и снимает правила; `nil` — без
защиты. Системе достаются только резолверы IPv4: маршрутов IPv6 в туннель нет. Порядок:
маршруты, защита, DNS системы — пока DNS системы прежний, запросы к нему защита
отбрасывает, а не выпускает мимо туннеля. `Suspend` и `Close` — в обратном порядке: DNS
системы, защита (с kill-switch её `Disable` закрывает трафик, и мига без маршрутов и без
запрета нет), маршруты. В отличие от qwdtt-cli, DNS системы между попытками возвращается
прежним: systemd-resolved шлёт запросы к DNS линка через сам линк, то есть в адаптер без
ядра, и страница капчи не открылась бы. Отказ защиты или DNS системы в `Start` — отказ
попытки, и снимается всё, как в `Suspend`.

IPv6 туннель не везёт никогда, поэтому перед включением защиты `Tun` каждый раз говорит ей
закрыть IPv6 (`IPv6Blocker`): пока туннель поднят, IPv6 наружу отбрасывается. Проходят,
кроме loopback и сокетов с меткой, локальная сеть IPv6 (`fe80::/10`, `fc00::/7`,
`ff00::/8`), ND и RA, DHCPv6 — то же, что в «закрыто» (§09б), так что локальная сеть ведёт
себя, как IPv4 и как на Windows. DNS к ней закрыт: запрет порта 53 стоит раньше
разрешений, а резолвер туннеля с адресом IPv6 не разрешается вовсе. Транзитному IPv6
контейнеров и ВМ (цепочка `forward`) — то же, без служебных протоколов хоста: наружу
туннеля нет и у него, а локальная сеть открыта. В qwdtt-cli IPv6 закрывался только при MTU
меньше 1280, когда ядро Linux снимает IPv6 с адаптера, — здесь маршрутов IPv6 в адаптер нет
при любом MTU.
Защита без `IPv6Blocker` или без защиты вовсе — строка в журнал, что IPv6 идёт мимо
туннеля. Kill-switch для `Tun` — та же защита в обёртке (§09б), `Tun` о нём не знает.

DNS на ходу (повторный `TUNCONF`) — в три шага: защита пускает прежние и новые резолверы,
DNS системы становится новым, защита пускает только новые. `Enable` заменяет правила
одним пакетом nftables, а пакет ядро применяет целиком, поэтому нет ни мига без
защиты, ни мига, когда DNS системы ведёт туда, куда защита не пускает. Отказ на ходу
туннель не роняет: отказ `Enable` снимает правила целиком, и `Tun` ставит прежний список
снова; отказ DNS системы оставляет защиту пускающей и прежние, и новые; следующий
`TUNCONF` доводит переход.

Дескриптор ядру — на каждую попытку новый дубликат (`F_DUPFD_CLOEXEC`) на новое случайное
имя абстрактного сокета (`csqtt-cli-tun-` и 32 шестнадцатеричных знака) в `-tun-uds`.
Слушатель ядро открывает вскоре после `PROCESS`, а события готовности в этом режиме нет,
поэтому по `PROCESS` оболочка подключается с повтором через 20 мс, пока сокета нет
(`ECONNREFUSED`) или очередь слушателя (4) полна (`EAGAIN`), — не дольше 10 с. Затем —
проверка слушателя по `SO_PEERCRED` (Р4), один байт с `SCM_RIGHTS` и ожидание байта
подтверждения ядра; свой дубликат оболочка закрывает. Отказ или срок — конец попытки, как
отказ `Start`, а `Connected` наступает, только когда дескриптор принят.

## 06. Обход туннеля

```
ДОРОЖКА 1 — ТРАФИК ПРИЛОЖЕНИЙ

 Приложения → адаптер csqtt-cli → канал пакетов → диспетчер ядра → маскировка → TURN-relay VK → VPS
                                  (loopback или                    9…126 воркеров
                                   дескриптор TUN)

ДОРОЖКА 2 — СОБСТВЕННЫЕ СОКЕТЫ ЯДРА

 Сокеты ядра → привязка к индексу физического интерфейса → Wi-Fi / Ethernet → Интернет
 VK HTTPS, DNS, TURN UDP/TCP        (П3: IP_UNICAST_IF · SO_BINDTOIFINDEX + SO_MARK;
                                     VK HTTPS — в коннекторе primp-hyper-util)
```

### Пять точек

| # | Где | Что | Правка |
|---|---|---|---|
| 1 | `dns.rs` · `query_dns_server` | DNS для имён VK, UDP :53 | привязка после `bind`, до `send_to` |
| 2 | `turn.rs` · `UdpSocket::bind` | TURN по UDP | привязка после `bind` |
| 3 | `turn_stream.rs` · `TcpStream::connect` | TURN по TCP/TLS | сокет `TcpSocket` (tokio), привязка, затем `connect` |
| 4 | `auth.rs` · `build_browser_client` | API VK по HTTPS | пропатченный коннектор `primp-hyper-util` |
| 5 | `vk_js_calls.rs` · `Client::builder` | API звонков VK (`auto_js`) | пропатченный коннектор `primp-hyper-util` |

Точки 1–3 — `setsockopt` сразу после создания сокета; сокеты им даёт свой модуль ядра
`bind_if.rs`. Точки 4–5 — клиенты `primp`: обёртка над форком reqwest (`primp-reqwest`),
сокеты TCP открывает его коннектор из `primp-hyper-util` (`connect` в `http.rs`). Снаружи
крючка на создание сокета нет: `connector_layer` получает уже соединённый сокет, а
обёртка не пробрасывает и его. Штатно коннектор умеет только `interface`
(`SO_BINDTODEVICE` по имени, на Windows его нет) и `local_address`; ни метки, ни
`IP_UNICAST_IF` у него нет.

Поэтому `primp-hyper-util` вендорится в `core/` (MIT, лицензия сохраняется) и подключается
через `[patch.crates-io]`; `primp-reqwest` и обёртка `primp` не меняются. Значения в
коннектор идут не через построитель, а через общую для процесса настройку в самом
пропатченном крейте: индекс и метку ядро ставит по `-bind-if` и `-mark` и меняет по
`BIND_IF:`. Каждое новое соединение в `connect` берёт текущие значения — после штатных
настроек сокета (среди них `bind_device`), до `bind_local_address` и `connect`:

- **Linux** — `SO_BINDTOIFINDEX` по индексу (на ядре без него — `SO_BINDTODEVICE` по
  имени интерфейса) и `SO_MARK`;
- **Windows** — `IP_UNICAST_IF` (индекс в сетевом порядке байт) или `IPV6_UNICAST_IF` (в
  порядке хоста), как в wireguard-go; `setsockopt` — своим объявлением из `ws2_32`, без
  новой зависимости. Меток на Windows нет: метка там — ошибка.

Эта привязка — модуль `csqtt_bind` в пропатченном крейте. Тем же вызовом ядро привязывает
сокеты точек 1–3, так что настройка и код привязки у всех пяти точек одни. Ядро зависит
от `primp-hyper-util` напрямую ради этой настройки — той же версии, что берёт
`primp-reqwest`, поэтому крейт в графе один. Своя правка лежит отдельно от копии крейта:
крейт — нетронутым архивом, правка — правилами и модулем (Р2).

**Ошибки.** Без `-bind-if` ничего не меняется. С ним привязка обязательна:

- неверные флаги — отказ стартовать (§04); `-bind-if` ставится первым делом, и для
  туннеля, и для проверки хешей;
- сокет, который не удалось привязать, не используется — ошибка уходит вызывающему, а
  соединение `primp` не открывается;
- `BIND_IF:` с негодным индексом отклоняется, прежний индекс остаётся (§04).

`SO_BINDTOIFINDEX` существования интерфейса не проверяет: сокет с несуществующим индексом
привязывается, а ошибка приходит только на `connect` или `send` (`ENODEV`). Поэтому и
`-bind-if`, и `BIND_IF:` сначала проверяют, что интерфейс с таким индексом есть, и
привязывают пробный сокет. Если интерфейс пропал уже после проверки, на Linux сокеты на нём
ничего не шлют (`ENODEV`) — мимо привязки они не уходят. Как `IP_UNICAST_IF` ведёт себя
после удаления адаптера на Windows, ещё не проверено — это часть живой пробы W2 на Windows.

Привязку сокета `primp` к интерфейсу проверила проба в пространстве имён, где маршруты
`/1` ведут в заглушку. Без привязки и с `local_address` SYN уходят в заглушку и
соединение не устанавливается. С привязкой к физическому интерфейсу VK отвечает, и все
пакеты идут через него. Так же — проба самого ядра с П3 (W2): без `-bind-if` запросы к DNS
Яндекса уходят в заглушку и VK недоступен; с `-bind-if` и `-mark` DNS и HTTPS идут через
физический интерфейс, в заглушку не уходит ни один пакет TCP или UDP, а у всех сокетов
ядра наружу стоят привязка и метка.

**Отклонённые способы.**

- Проброска штатного `interface()` через обёртку `primp`: работает только на Linux, по
  имени и без метки.
- `local_address` на Windows. Сокет с заданным адресом источника уводит мимо `/1`
  сильная модель хоста: маршрут ищется только среди маршрутов интерфейса с этим адресом.
  Но нужен адрес, а не индекс; адрес один, и при IPv4 коннектор отбрасывает адреса IPv6
  (утечки нет, но нет и IPv6); при включённом `WeakHostSend` способ не работает. На Linux
  `local_address` не помогает вовсе: модель хоста слабая, и SYN уходит в `/1` туннеля.
- Пропуск ядра в kill-switch Linux по группе процесса или по cgroup вместо метки:
  решают только метку, а на Windows оставляют `local_address`.
- Свой прокси CONNECT в ядре, через который ходит `primp`: лишний модуль и петля через
  loopback ради того, что правка коннектора даёт напрямую.

**DNS внутри `primp`.** Своих сокетов DNS у `primp` нет. `hickory-dns` в сборку ядра не
входит. Системный `getaddrinfo` (`GaiResolver`) заменён резолвером ядра: оба клиента
строятся с `dns_resolver(dns::global())`. Имена для точек 4–5 разрешает точка 1 (UDP к DNS
Яндекса), и её привязки достаточно. Проба это подтверждает: `strace` видит только сокет
UDP резолвера и сокет TCP `primp`, оба с привязкой.

Мимо привязки идёт только запасной путь `dns.rs`: если DNS Яндекса не ответил за 5 с, а
`TUNCONF` в этом процессе ещё не было, ядро спрашивает системный резолвер. Такой запрос
делает система: чужой процесс (systemd-resolved, служба Dnscache) или `getaddrinfo` без
привязки и метки. При закрытом kill-switch он блокируется, и в сети, где DNS Яндекса
недоступен, запасной путь не работает. Учесть в W5 и Э3; в П3 этот путь не меняется.

**Прокси из окружения.** Ядро не вызывает `no_proxy()`, поэтому `primp` берёт
`HTTP(S)_PROXY` и `ALL_PROXY` из окружения (реестр Windows он не читает). Когда прокси
слушает на loopback, привязка действует только на сокет до прокси, а к VK прокси ходит
своими сокетами. Поэтому с `-bind-if` клиенты строятся с `no_proxy()` (их общий
построитель — в `bind_if.rs`); без `-bind-if` поведение прежнее. Проба W2: с прокси из
окружения на loopback и `-bind-if` ядро идёт к VK напрямую.

**Сторож** — по образцу `TestNetguardCoverage` из qwdtt-cli, но в самом `vendorcore`: он
работает при переносе, в `-check` и в тестах `vendorcore` на настоящем `core/`. Сторож
ищет в коде `rust-client/` и `shared/`, включая вендоренные крейты, все вызовы, которые
создают сокет, разрешают имя или строят HTTP-клиент — и без построителя (`primp::get`,
`Client::new`, `Client::default`), — и сверяет их с таблицей покрытых мест. У каждого места — файл, вызов, число таких вызовов и причина: одна из пяти точек,
сокет без выхода наружу (loopback канала пакетов, unix-сокет `-tun-uds`) или путь мимо
привязки по решению: запасной системный DNS, `GaiResolver` коннектора (в ядре заменён
резолвером ядра), SOCKS-прокси коннектора (с `-bind-if` прокси выключены). Для мест с привязкой задано ещё, что обязано идти дальше в той же
функции: после создания сокета — вызов привязки (в `bind_if.rs` и в `connect`
коннектора), в построителе клиента — `no_proxy()`, у клиентов точек 4–5 — резолвер ядра
`dns_resolver(dns::global())`. Новое место, другое число вызовов или пропавшая
привязка — перенос и `-check` падают. Тесты ядра (`*_tests.rs`, модули `#[cfg(test)]`),
`tests/` и `examples/` крейтов и строки комментариев сторож не смотрит: в сборку ядра
они не входят. Тестовый модуль, конец которого не найден, — ошибка: остаток файла не
выпадает из проверки молча. Новая версия апстрима с новым сокетом не пройдёт `vendorcore -check`, а не
начнёт молча уводить трафик в петлю.

**Действует ли `[patch]`.** Если `primp` апстрима потребует другую версию
`primp-hyper-util`, `[patch.crates-io]` перестанет действовать без ошибки, и привязка
`primp` пропадёт. Это ловят четыре слоя:

1. перенос сверяет версию крейта в `Cargo.lock` апстрима с архивом и падает, если она
   другая или версий несколько;
2. правило на `Cargo.lock` привязано к версии архива, а `cargo --locked` без
   действующего патча ядро не соберёт;
3. ядро вызывает `csqtt_bind`, которого в крейте с crates.io нет, — без патча оно не
   скомпилируется;
4. тест на Rust находит среди дескрипторов процесса сокет соединения `primp` и проверяет
   на нём индекс и метку.

**Смена сети.** Индекс интерфейса выбирает и сторожит `netguard` из qwdtt-cli (уведомления
о маршрутах, сворачивание серий событий). Выбор — интерфейс маршрута по умолчанию
(`0.0.0.0/0`); половины `/1` туннеля в него не попадают, так что свои маршруты туннель не
перезапускают.

Сейчас смена сети — перезапуск ядра, как в qwdtt-cli. `-bind-if` (индекс IPv4) и `-mark`
ядро получает на каждую попытку (`Options.Prepare` супервизора, §09), а `Watch` на смену
интерфейса зовёт `Tunnel.Restart`: попытка обрывается, следующая начинается сразу, и новое
ядро получает новый индекс. Без перезапуска ядро в новую сеть не пошло бы: на Linux
сокеты на пропавшем интерфейсе получают `ENODEV`, мимо привязки они не уходят. Пропажа
сети попытку не перезапускает: новой не на чем подключиться, а возврат сети — ещё одна
смена, и перезапуск один на выдернутый и вставленный кабель. Интерфейс пропадал и
вернулся тем же (сон, переподключение Wi-Fi) — тоже перезапуск: сокеты через него мертвы.
Нет маршрута по умолчанию IPv4 — ядро не запускается, попытка ждёт обычную задержку или
`Restart`; интерфейс IPv6 его не заменит: ядро ходит к DNS Яндекса и TURN по IPv4. Не
вышло подписаться на уведомления — строка, и интерфейс выбирается заново перед каждой
попыткой, так что новая сеть подхватится, когда попытка оборвётся сама. У нового
интерфейса проверяется `rp_filter`: строгий — предупреждение, а не отказ (сеть может
смениться ещё раз). Попытки при этом продолжаются с обычной задержкой — и тогда, когда ядро
выходит, ещё не начав работу (§09), — но не удаются, пока фильтр строгий.

Без перезапуска сеть можно сменить командой `BIND_IF:<новый>`: новые сокеты ядра
привяжутся к новому интерфейсу, старые умрут по таймаутам, и воркеры переподключатся сами.
Это касается и `primp`: настройка коннектора общая для процесса, поэтому новый индекс берут
и клиенты точки 4 (они собираются на каждую попытку входа), и клиент точки 5 (он живёт
весь сеанс `auto_js`). Соединения из пула keep-alive на старом интерфейсе отомрут по
ошибке или таймауту, и клиент откроет новые. Заменит ли это перезапуск — решит замер W6.

**Свои сокеты оболочки.** Прокси окна капчи (§08) ходит к VK сокетами `csqtt-cli` — их
привязывает тот же `netguard`, что в qwdtt-cli, с той же меткой, что у ядра. Имена VK
прокси разрешает своим резолвером к DNS Яндекса теми же сокетами, а не DNS системы: при
«закрыто» DNS системы закрыт, а systemd-resolved ходит своими сокетами, без метки.

## 07. Правки ядра

Все правки — правила `scripts/vendorcore` поверх апстрима (Р2). Каждая — с тестом на
Rust в самом ядре и упоминанием в `doc/upstream-proposals.md`, если её стоит предложить
автору.

| # | Правка | Зачем | Этап |
|---|---|---|---|
| П1 | `-secrets-stdin`: пароль и хеши первой строкой stdin | секреты не видны в списке процессов (Р6) | Э1 |
| П2 | `-listen-peer <адрес>`: принимать и отвечать только ему; порт ядра — событием `LISTEN` | чужой датаграм не уводит туннель (Р4) | Э1 |
| П3 | `-bind-if`, `-mark`, команда `BIND_IF:`: привязка сокетов в 5 точках; для `primp` — в вендоренном `primp-hyper-util` | обход туннеля (Р3, §06) | Э2 |
| П4 | проверка `SO_PEERCRED` при приёме дескриптора TUN: чужой uid — соединение закрыть, не читая, и ждать следующего | чужой процесс не подменит TUN (Р4) | Э3 |

сервер не отличает csqtt-cli от Android-клиента.

## 08. Капча

Капчу решает человек в окне (Р7), окна — из qwdtt-cli (`internal/captcha`): WebView2 на
Windows, браузер под управлением по CDP на Linux, ручной режим везде. Запрос — строка
`CAPTCHA_SOLVE` в stdout ядра, ответ — `CAPTCHA_RESULT` в stdin; между ними — мост
`captcha.Bridge`, его `Solve` и есть решатель супервизора.

**Страница капчи.** `id.vk.ru/not_robot_captcha` ходит в API запросами
`POST …/method/captchaNotRobot.<метод>`: `initSession` (тип капчи — `show_captcha_type`,
обычно `checkbox`), `settings`, `componentDone`, затем на действие человека — `check`, после
токена — `endSession`; без действий несколько минут — `refreshSession`. Токен — только в
ответе `check`: `response.success_token` при `status=OK`, редиректа с ним нет. Перехват
написан заново по этому поведению, код Android-клиентов (`CaptchaWebViewManager.kt` у
qWDTT и CSQTT) не переносится из-за лицензии (§11):

- окно видит ответы API — браузер по CDP сетью (`Network.getResponseBody`), страница не
  меняется ни на байт; WebView2 — перехватчиком JS поверх `fetch` и `XMLHttpRequest`,
  который передаёт тело ответа в Go как есть;
- разбирает их одно место для всех окон: `check` с `OK` и токеном — исход; `ERROR_LIMIT`
  — сразу `error:limit`, окно закрывается; ошибка VK в ответе `initSession` (живьём
  бывала 10, Internal server error) — сразу `error:init`, окно закрывается: капчи на
  странице не будет, человеку в окне делать нечего; `BOT` и прочее — ждать дальше,
  страница переходит к другой капче (слайдеру) в том же окне; тип капчи из `initSession`
  и `check` — в журнал, токен — никогда. На разметку страницы и классы CSS перехват не
  опирается.

**Одно окно.** Капча может понадобиться нескольким воркерам сразу, но ядро отдаёт запросы
по одному (канал результата в `captcha.rs` один и стоит под замком, лишние ответы
отклоняются): следующий приходит, только когда прежний решён или вышло время. Канал ядро
чистит перед тем, как напечатать запрос, — значит, ответ на прежний запрос, пришедший
после нового, ядро приняло бы за ответ на новый. Отсюда правила моста:

- новый запрос закрывает прежнее окно, а на прежний запрос ядру не отвечают ничем;
- тот же `redirect_uri`, пока окно открыто, второго окна не открывает: окно отвечает
  новому запросу, время отсчитывается заново;
- время окна — свои 180 секунд; вышло — окно закрывается, ядру не отвечают: оно ждало
  столько же и уже перестало;
- окно закрыл человек — `error:closed`; окно не открылось (нет браузера, сбой
  WebView2) — та же капча в ручном режиме.

**Ручной режим.** Ссылка в браузере системы; человек ещё до галочки открывает
инструменты разработчика (F12) на вкладке Network, решает капчу и копирует из ответа
`captchaNotRobot.check` значение `success_token` или ответ целиком — разбор примет и то,
и другое, а на негодное объяснит, что не так, и подождёт ещё.

Ответ он читает из общего читателя строк stdin (`lines.Reader`), того же, что у вопросов
CLI. Чтение stdin не прервать: брошенное по концу попытки чтение капчи так и ждёт строку.
Поэтому оно не бросается, а остаётся общим — следующий, кто спросит, получит его строку;
строку, пришедшую, когда её никто не ждал, и капча, и вопрос CLI выбрасывают как ответ не
на свой вопрос. Читатель читает только по запросу: скрытый ввод секретов читает терминал
мимо него и спрашивается до подключения, пока чтения нет.

**Браузер под управлением** запускается со своим пустым профилем и с
`--disable-extensions` (расширения, которые система ставит всем профилям, иначе приходят
и в пустой: живая запись поймала такое, перезагружавшее страницу и менявшее User-Agent) и
`--password-store=basic` (без похода в связку ключей сеанса).

**Токен в журнале.** Ядро повторяет каждую команду stdin в журнал — и
`CAPTCHA_RESULT|<токен>`, а адрес капчи печатает строкой `[КАПЧА] solveOnce URL: …` с
`session_token`. `coreproc` прячет оба токена в строке журнала до того, как она уйдёт на
экран или в файл.

**Kill-switch.** Как в qwdtt-cli: окно ходит через локальный прокси `csqtt-cli` (только
`CONNECT` на 443 к доменам VK), сокеты прокси привязаны к физическому интерфейсу, и
kill-switch на время капчи не снимается. Всё, что идёт в сеть мимо прокси, мост
оборачивает в `Options.Direct`, и на это время kill-switch снимается со строкой в выводе:
ручной режим (браузер системы), окно без прокси и то же окно, если прокси не поднялся
(`ErrProxy`: мост держит второй экземпляр окна без `Dial`; окно не открылось вовсе —
ручной режим). После капчи «закрыто» возвращается, если туннель так и не поднялся; при
поднятом туннеле правила не трогаются, а упавший посреди капчи туннель браузер не
отрезает. Окно прежнего запроса может ещё закрываться, когда открылось новое, поэтому
капчи считаются, и «закрыто» возвращается после последней. Имена VK прокси разрешает
своим резолвером к DNS Яндекса сокетами с меткой (§06): DNS системы при «закрыто» закрыт.
Ctrl+C посреди капчи мимо прокси: мост возвращается, не дожидаясь окна, и `connect`
закрывает таблицу раньше, чем окно; kill-switch помечен закрытым, и конец такой капчи
правил больше не трогает. Без kill-switch (`-no-kill-switch`, `kill_switch = false`, его
отказ под `-allow-leak`) окно ходит в сеть само, без прокси, и снимать нечего.

Страница капчи в `<head>` грузит синхронный скрипт с `ad.mail.ru`. Прокси отказывает
такому `CONNECT` сразу (403), но Chromium загрузку страницы держит, и через прокси она
открывается на 10–15 секунд дольше, хотя `initSession` и галочка проходят. Задержка — на
стороне браузера; пускать этот домен в список прокси не стали.

## 08а. Режим `auto_js`

В режиме `auto_js` ядро само создаёт звонок VK по токену аккаунта пользователя вместо
ручных ссылок на звонки. Ниже — поведение ядра 2.1.9 (`vk_js_calls.rs`, `main.rs`,
`auth.rs`, `worker.rs`) и Android-клиента CSQTT (только как справка о поведении).

### Токен

Токен — access token VK, полученный OAuth implicit flow:

    https://oauth.vk.ru/authorize?client_id=7793118&scope=1073737727
      &redirect_uri=https%3A%2F%2Foauth.vk.ru%2Fblank.html&display=page
      &response_type=token&revoke=1&v=5.199

После входа (и экрана доступа приложения, если VK его покажет) VK переводит окно на
`https://oauth.vk.ru/blank.html`, токен — во фрагменте адреса: `access_token`, `expires_in`, `user_id`. Права `scope` — все, кроме
сообщений, включая `offline`: токен должен быть бессрочным и даёт широкий доступ к
аккаунту, хранить его надо как пароль. Обновления у токена нет. Отозванный или неверный
токен ядро встречает на старте: первый же запрос к VK возвращает ошибку API, ядро
пишет `[ФАТАЛ] API <код>: …` и не запускается.

Живой вход (Linux): через VK ID — QR-код и код из приложения VK; экрана прав VK при этом
не показал; токен пришёл во фрагменте `blank.html` без срока. Ещё не проверено, с каким
кодом и текстом приходит отказ на отозванный токен (ожидается код 5).

Android-клиент CSQTT сначала даёт войти на `vk.ru`, затем проходит OAuth сам с cookie
окна; запасной путь и сторонние десктопные клиенты — OAuth-страница прямо в окне. Без
входа в VK `oauth.vk.ru/authorize` уводит на `id.vk.ru/auth` с тем же `redirect_uri`: вход
идёт через VK ID.

### Передача ядру

Аргументы: `--vk-hash-mode=auto_js --vk-auth-mode=auto_js --allow-hash-redistribution`,
хеши не нужны. В stdin следом за `SECRETS:` (Р6) — строка
`VK_JS_BOOTSTRAP:<base64 json>`, json — `{"token": "…"}`; base64 — стандартный, с
выравниванием `=`, не длиннее 32 КиБ. Ядро ждёт её 15 с, но читает не сразу, а после
разрешения имени сервера, и своим буфером: всё, что пришло после строки в том же чтении,
теряется. Поэтому `SECRETS:` и `VK_JS_BOOTSTRAP:` пишутся одной записью: тогда bootstrap
уже лежит в общем буфере stdin после чтения секретов, а команды, пришедшие позже, ждут в
канале. Команды той же записью, что bootstrap, теряются; команды, попавшие в канал до
того, как ядро прочло `SECRETS:`, — тоже (они окажутся в одном буфере с bootstrap).
Поэтому оболочка шлёт команды остановки не раньше первой строки вывода ядра (до чтения
секретов ядро ничего не пишет) или его выхода: до `PROCESS` ядро их всё равно не
исполняет.

Bootstrap шлётся только ядру, запущенному с `auto_js`: без этого режима строку прочтёт
читатель команд и повторит её в журнал (`[STDIN] …`) вместе с токеном.

### Что делает ядро

До события `PROCESS` и до чтения команд ядро открывает сессию VK Calls под аккаунтом
(`messages.getCallToken` в API VK, затем `auth.anonymLogin` в API OK Calls по адресу из
ответа — только `api.ok.ru` или `*.okcdn.ru`) и создаёт **один** звонок
(`vchat.startConversation`); хеш — из его `join_link`. Неудача — `[ФАТАЛ] …` в журнале и
код 1 без `PROCESS`.

TURN-креды выдаёт не гостевой путь, а сессии аккаунта. На каждые 18 воркеров — свой номер
кредов (номеров не больше 9). Каждый запрос кредов открывает новую сессию аккаунта
(`messages.getCallToken` + `auth.anonymLogin` со случайным `device_id`) и берёт
`vchat.getConversationParams` по созданному звонку. Креды номера обновляются после 18
выделений, после отказа и при каждой повторной попытке, так что число сессий аккаунта за
подключение не ограничено; плюс сессия создателя. Повторно выданный TURN-набор ядро
отвергает. Номер без кредов переходит на гостевой путь `vkcalls` по тому же звонку. Предела
27 воркеров на хеш в `auto_js` нет: до 126 воркеров на одном звонке. Создатель остаётся в
звонке, пока ядро работает.

Событие `CALL_UNAVAILABLE` при работе `auto_js` не приходит: ошибка гостевого пути
приходит в общей ошибке режима, и воркеры просто повторяют запрос кредов. Мёртвый звонок
оболочка видит как `ACTIVE_ZERO`/`NETWORK_SUSPECT` (§09) и перезапускает ядро — новое ядро
создаёт новый звонок.

Все запросы — HTTPS клиентом `primp` с маскировкой под браузер; это пятая точка обхода
туннеля (§06), имена — резолвером ядра.

### Остановка

`FINISH_VK_CALLS` ставит флаг, действует при остановке: после `STOP` ядро закрывает
воркеры и завершает звонок `calls.forceFinish` (не дольше 2 с; журнал
`[VK JS] Звонки завершены K/1`). Без флага создатель только выходит из звонка
(`vchat.hangupConversation`), звонок не завершается. Убитое ядро не делает ни того, ни
другого. Android шлёт `FINISH_VK_CALLS` и `STOP` одной записью при остановке
пользователем и ждёт ядро 3,2 с.

Пока звонок создаётся, ядро команд не читает: `STOP` сработает только после `PROCESS`,
и только с этого момента SIGINT ведёт к уборке. SIGTERM ядро не ловит — уборки нет.

Как останавливает `csqtt-cli` — §04, «Остановка»: команды не раньше первой строки ядра,
до `PROCESS` — до 30 с, на уборку — 8 с; не дождались или ядро не подтвердило уборку —
`*CallLeftError`, звонок мог остаться. `Stop` — только выход создателя, `StopFinishingCalls`
— с завершением звонка; супервизор шлёт `StopFinishingCalls` при любой остановке
(ниже, «Как делает csqtt-cli»).

### Журнал

`[VK JS] Сессия Calls подтверждена` · `Звонок создан` / `Звонок не создан: …` ·
`Создатель удерживает звонок` · `Креды аккаунта N/9 готовы` / `недоступны: … · переход
на Авто` · `Переход на Авто #N выполнен` / `не выполнен` · `Звонки завершены K/1` ·
`Создатель вышел из звонков K/1`. Токен, ключ сессии и id звонка ядро не печатает. Хеш
созданного звонка в журнале есть: началом — в строках `[КРЕД #N] Запрос (хеш: …)`,
целиком — в адресах гостевого пути (`call%2Fjoin%2F<хеш>`, `fb.do?joinLink=<хеш>`) внутри `Переход на Авто #N не
выполнен: …` и `[КРЕД #N] Ошибка: … Повторяем…`. Оболочке этот хеш неизвестен, поэтому она прячет его по виду
строки (`call/join/…`, `call%2Fjoin%2F…`, `joinLink=…`, `хеш: …`), а не по списку хешей профиля.
Ключи гостевого пути в тех же адресах прячутся в любом режиме (§04).

### Как делает csqtt-cli (решения к A2, A3)

- **Вход** — `csqtt-cli vk login`: OAuth-страница VK (адрес выше) прямо в окне — WebView2
  на Windows, Chromium по CDP на Linux, как окно капчи (§08). Пользователь сам входит; если
  VK покажет экран доступа приложения, сам его подтверждает. При входе через VK ID (QR-код
  и код из приложения) живьём экрана доступа не было: окно закрылось сразу после входа.
  Поэтому о правах токена человек узнаёт из нашего предупреждения, и согласие на нём —
  это и согласие на доступ. Токен перехватывается из адреса `blank.html` (ниже, «Окно
  входа»). Окно — с временным профилем браузера: cookie VK не сохраняются. Путь Android с
  подтверждением согласия за пользователя не делаем: на страницах VK окно ничего не
  нажимает.
- **Перед входом** — предупреждение о риске и явное согласие (ниже, «Риск»): вопрос
  `[y/N]` при каждом входе, Enter — отказ; без терминала на stdin — отказ, окно не
  открывается. Повторного предупреждения при включении `auto_js` в профиле нет: без входа
  профиль с `auto_js` не подключится.
- **Токен один на установку**, не на профиль; хранится в хранилище секретов (§10). Где
  связки ключей нет, он, как и пароль сервера, ложится в файл с правами 0600.
  `vk logout` стирает его локально, к VK не ходит: у VK токен действует, пока доступ
  приложения не отозван в настройках аккаунта, — об этом команда и говорит. `vk status`
  говорит, есть ли токен и где он лежит, и показывает `user_id`, но не сам токен.
- **Профиль** — одно поле `vk_hash_mode = "auto_js"`: оно включает оба режима ядра и
  `--allow-hash-redistribution`; хеши звонков не нужны. Второе значение — `manual` (как у
  флага ядра), то же, что пустое поле. Воркеров — не больше 72, как у Android: больше
  `coreproc` урезает, `profile` предупреждает. Хеши вместе с `auto_js` — не ошибка, а
  предупреждение: ядру они не уходят, а профиль, переключённый обратно, найдёт их на месте.
- **Ошибки до `PROCESS`**: отказ токена — конец без повторов с подсказкой `vk login`;
  сетевые сбои до VK — повтор, в том числе на первой попытке. Отказ токена
  (`FatalError.TokenRejected`) — ошибка API без приписки метода (её даёт первый запрос с
  токеном, `messages.getCallToken`) с кодом 5 (авторизация не удалась: токен неверный,
  просрочен или отозван), 27 или 28 (токен сообщества или приложения). Код 4 сюда не
  входит: у VK это неверная подпись запроса, у OK Calls — общая ошибка запроса. Ошибки API
  OK Calls (`auth.anonymLogin`, `system.getInfo`) тоже идут без приписки, но таких кодов у
  них нет. Прочие ошибки API (создание звонка, лимиты, коды 17 и 18, которые у VK и OK
  Calls значат разное) — тоже конец на любой попытке («VK отказал: …», `*VKError`):
  каждая попытка создаёт звонок и сессии под аккаунтом, и повтор вслепую — лишний след и
  риск для аккаунта. Остальное (имя сервера, аргументы, ответ VK не того вида) — как любой
  выход до `PROCESS` (§09).
- **Подключение** — `connect` и меню. Без входа VK — ошибка до запуска ядра (и до проверки
  прав `tun`: входят без `sudo`) с подсказкой `vk login`; токен не читается или пуст — то
  же. Токен — из хранилища по `[vk] token_ref`, хеши профиля не читаются, воркеров — не
  больше 72. `hashes check` для такого профиля — отказ, меню не предлагает ссылок на
  звонки. Мастер профиля режима не спрашивает: `auto_js` включается
  `profile set <профиль> -vk-hash-mode auto_js` после `vk login`.
- **Остановка** — с завершением звонка (`StopFinishingCalls`) при любой остановке ядра: по
  Ctrl+C и перед следующей попыткой — та всё равно создаст новый звонок, а брошенные —
  лишний след в аккаунте. Пока она идёт (до 38 с), выводится строка «завершаем звонок
  VK…», после Ctrl+C — с подсказкой, что второй Ctrl+C убьёт ядро сразу, но звонок тогда
  может остаться. Звонок мог остаться (`*CallLeftError`) — строка об этом.
- **Отзыв токена посреди сеанса** виден только строками журнала `[VK JS] Креды аккаунта
  N/9 недоступны: Auto JS session #N: API 5: …` — не `[ФАТАЛ]`; номер кредов при этом
  уходит на гостевой путь по тому же звонку и может работать дальше. Отдельной реакции
  нет: если связь пропала, ядро перезапускается по `Degraded` (§09), новое ядро на первом
  же запросе получает отказ токена — и цикл кончается с подсказкой `vk login`.

### Окно входа

Окна — из `internal/captcha`, рядом с окнами капчи; разговор с браузером по CDP у них общий,
различаются автоматы. Срок на вход — 5 минут; закрыл окно — отмена; окна нет (нет браузера
на Chromium или WebView2 Runtime) — ошибка: ручного режима, как у капчи, у входа нет. На
страницах VK окна ничего не выполняют и не нажимают.

**Где окно видит адрес с токеном.** Какой путь сработает у настоящего VK, живьём ещё не
проверено, поэтому окно по CDP слушает все:

- `Fetch.requestPaused` — перехват документа `blank.html` (`oauth.vk.ru`, `oauth.vk.com`)
  главного фрейма до сети: адрес — `request.url`, фрагмент — отдельно, `request.urlFragment`.
  Окну отвечает своя заглушка (`Fetch.fulfillRequest`), запрос к VK не уходит, как у
  Android. Перехват включается до того, как окно откроет страницу входа: иначе редирект
  мог бы проскочить. На стенде фрагмент здесь виден и при редиректе сервера, и при
  переходе из JS;
- `Page.frameNavigated` главного фрейма (`frame.urlFragment`) и
  `Page.navigatedWithinDocument` (смена фрагмента на той же странице);
- крайний — `Runtime.evaluate location.href` на открывшейся `blank.html` (это уже
  заглушка). Нет токена и там — ошибка «токена в адресе нет».

В go-webview2 события начала навигации нет. Окно WebView2 ставит скрипт, который
выполняется на каждой странице до её собственного кода, и тот в главном фрейме отдаёт
`location.href` в Go через `Bind` — только на `blank.html` или при фрагменте `#payload=`,
и ещё раз при смене фрагмента. Сама `blank.html` VK тут грузится из сети, но фрагмент в
запрос не попадает.

**Разбор адреса** — одно место для обоих окон. Токен и ошибку принимает только с
`blank.html`: сначала фрагмент, нет в нём ни токена, ни ошибки — строка запроса. Адрес,
который окно смотрит ради `payload=`, токена не даёт, даже если `access_token` в нём есть,
— только повтор на «тихий» токен. `error` с `error_description` — ошибка с текстом VK
(отказ человека на экране согласия). Одну навигацию окна видят несколькими событиями, решение по
адресу принимается один раз. `user_id` берётся, только если это число.

**Повторы** — как у Android, по одному разу: токен со сроком (`expires_in` не 0) — окно
открывает страницу входа заново, второй такой — ошибка; «тихий» токен VK ID (фрагмент
`payload=` с `silent_token` на `oauth.vk.ru` или `oauth.vk.com`) — страница входа заново
через 1,5 с, второй — ошибка. Сторонние сайты, где Android-клиент тоже ищет `payload=`, на
вход не влияют: наш вход возвращается на `blank.html` VK. Без `expires_in` токен
принимается, как у обоих настольных клиентов CSQTT.

**Профиль окна** — свой временный каталог (`csqtt-cli-vklogin-…`), отдельно от профилей
капчи. В нём после входа — cookie сессии VK, поэтому вход ждёт, пока окно закроется и
профиль удалится, и только потом возвращает токен; не удалился — предупреждение с путём.
Брошенные профили (старше часа) следующий запуск убирает вместе с профилями капчи.

Токен и адреса в вывод не попадают: тип токена прячет значение при печати, `-v` у
`vk login` пишет только, что окно увидело (перехват, где виден фрагмент, повтор, длину
токена), без адресов.

### Риск

Режим пользуется неофициальными браузерными методами VK и OK Calls и маскирует запросы
под браузер. Автор CSQTT предупреждает: блокировку аккаунта VK исключить нельзя, лучше
второстепенный аккаунт. Поэтому вход — только после предупреждения и явного согласия
пользователя (§12, Э5). В предупреждении сказано и то, что токен бессрочный и даёт
широкий доступ к аккаунту, а каждое подключение создаёт звонок и сессии аккаунта, число
которых при переподключениях не ограничено.

## 09. Супервизор

Автомат из qwdtt-cli, состояния — по событиям ядра:

```
Idle ──▶ Starting ──▶ Credentials ──▶ Configuring ──▶ Connected ◀──▶ Degraded
            ▲         (PROGRESS)       (TUNCONF)       (READY)        (ACTIVE_ZERO,
            │                                                          NETWORK_SUSPECT)
            └──── Reconnecting ◀── выход ядра · fatal ERROR · SERVER_RESTART ·
                                   долгий Degraded · смена сети (Restart)

Stopping ◀── из любого состояния: Ctrl+C, отказ сервера, ядро не запускается,
             годных хешей не осталось или VK не принял токен (auto_js)
```

- `Connected` — когда поднят datapath и на линии есть воркер: `READY` и `TUNCONF` ядро
  шлёт из разных задач, и порядок их не гарантирован. Линия проходится только вперёд:
  `PROGRESS` приходит на каждый кред, поздний не откатывает поднятый туннель.
- `Degraded` — живых воркеров нет (`ACTIVE_ZERO`, `STATS` с нулём) или ядро заподозрило
  сеть (`NETWORK_SUSPECT`). Выход — новый `READY`, `STATS` с воркерами, а после
  подозрения на сеть — ещё и с выросшим принятым трафиком. После того как ядру послан
  `STOP` (Ctrl+C, перезапуск, отказ), состояние до выхода ядра не меняется: воркеры
  уходят по нашей же остановке, и «без связи» это не значит.
- Воркеры ядро переподключает само. Перезапуск процесса ядра — только когда ядро
  завершилось, прислало `fatal`, сервер перезапущен из панели или `Degraded` длится
  дольше порога (30 с; уточнит живой прогон).
- Без повтора, сразу в `Stopping`: `handshake_rejected` — сервер отказал (неверный или
  просроченный пароль, пароль другого устройства, другая версия протокола), как на
  Android; первое же ядро цикла вышло, не прислав `PROCESS` (негодные аргументы, ядро не
  той версии). Молчание сервера (`handshake_timeout`) — повтор: сервер мог быть просто
  недоступен. Выход до `PROCESS` после того, как ядро в этом цикле уже работало, — тоже
  повтор с обычной задержкой: аргументы годны, а до `PROCESS` ядро уже ходит в сеть —
  проверяет интерфейс `-bind-if` и разрешает имя сервера, — и в новой сети, которая ещё не
  пропускает наружу, выходит. Причина в строке переподключения — что ядро вышло, не начав
  работу, с последней строкой его журнала.
- В `auto_js` (§08а) выход до `PROCESS` разбирается по строке `[ФАТАЛ] …`
  (`coreproc.ParseFatal`): отказ токена — конец на любой попытке (`*TokenRejectedError`,
  `connect` подсказывает `vk login`), прочая ошибка API VK — тоже конец на любой попытке
  (`*VKError`, «VK отказал: …»): каждая попытка — сессии и запросы под аккаунтом. Сбой
  сети до VK — повтор и на первой попытке: запрос до VK не дошёл. Прочее, в том числе
  неверное имя сервера (ядро разрешает его до VK), — по общему правилу выше; причину
  `connect` берёт из `StartupError.Fatal` и о сборке ядра подсказывает, только если ядро не
  приняло аргументы или данные оболочки (`FatalClient`) или причины в журнале нет.
- Backoff — `1 · 2^n` секунд, где n — неудачи подряд, не больше 64; `Connected` его
  обнуляет. После `SERVER_RESTART` — пауза 4 с, как на Android, и это не неудача.
- `CALL_UNAVAILABLE` исключает хеш из следующих попыток; текущее ядро держит остальные
  хеши само. Годных хешей не осталось — остановка с подсказкой, а меню само спрашивает
  новые ссылки. В `auto_js` пула хешей нет (`NewTunnel` требует токен вместо хешей), и
  событие ничего не исключает: мёртвый звонок виден как `Degraded` и лечится перезапуском —
  новое ядро создаёт новый звонок.
- Остановка ядра в `auto_js` — `StopFinishingCalls` всегда: и по Ctrl+C, и при перезапуске
  попытки (§08а, «Как делает csqtt-cli»). Строка «завершаем звонок VK…» — в начале
  остановки, `*CallLeftError` — строкой после неё. В режиме с хешами — `Stop`, как раньше.
- **Второй Ctrl+C.** Первый отменяет контекст `Run`, второй, пока туннель
  останавливается, убивает ядро (`Core.Kill`), не дожидаясь его уборки, — и уборка самого
  `csqtt-cli` (маршруты, DNS, kill-switch) идёт как обычно. Следующий сигнал убивает
  процесс. Связь — через контекст: `supervisor.WithAbort` кладёт в него, куда отдать
  второй сигнал, `Run` на время работы ставит туда своё (`OnAbort`). Так устроены
  `Interrupt` у `connect` и обработчик сигналов меню; когда прерывать нечего (`Run` ещё не
  начался или уже кончился), второй сигнал, как и прежде, завершает процесс.
- Капча — в своей горутине: решатель ждёт человека до трёх минут, а вывод ядра нужно
  читать. Решателя нет — ядро сразу получает `CAPTCHA_RESULT|error:unsupported`. Причина
  отказа для ядра — из `coreproc.CaptchaError`; на `coreproc.ErrCaptchaNoReply` (время
  окна вышло, пришёл новый запрос) ядру не отвечают (§08).
- Канал пакетов узнаёт порт ядра из `LISTEN` и забывает его, когда ядро вышло: порт
  вышедшего ядра может занять чужой процесс. `Socks` живёт весь сеанс, его строит и
  закрывает `connect`.
- Вместо канала на loopback — дескриптор адаптера (`TunFD`, `tun` на Linux): ядро
  получает `-tun-uds` с новым именем на каждую попытку, по `PROCESS` ему в своей горутине
  уходит новый дубликат дескриптора (§05). Отказ или срок передачи — конец попытки;
  `Connected` — только когда ядро дескриптор приняло, даже если `TUNCONF` и `READY` пришли
  раньше.
- `tun` — `Persistent`: адаптер живёт весь `csqtt-cli connect`. После неудачной попытки,
  до задержки, цикл зовёт `Suspend` — снять маршруты, DNS системы и защиту DNS (§05; на
  Windows — W5); с kill-switch вместо них встаёт «закрыто». По Ctrl+C и при окончательной
  остановке — нет: адаптер убирает `Close` у `connect`.
- Если в попытке туннель поднимался (`Start` прошёл), после `Suspend` цикл пишет, куда
  теперь идёт трафик системы, спросив `Options.KillSwitch`: «заблокирован (kill-switch)»
  или «идёт мимо туннеля» — kill-switch мог не встать (`-allow-leak`) или быть снят на
  время капчи. `Start` следующей попытки — строка, что трафик вернулся в туннель. Отказ
  `Suspend` — строка, что снято не всё; следующая попытка начинается всё равно.
- `Options.Prepare` дописывает в настройки ядра перед каждой попыткой то, что между
  попытками меняется: `-bind-if` и `-mark` (§06). Отказ (сети нет) — ядро не
  запускается, попытка неудачна, следующая — через обычную задержку.
- `Tunnel.Restart(причина)` — перезапуск по просьбе снаружи (смена сети, §06), из любой
  горутины. Идущая попытка получает `Stop` и кончается с этой причиной; если она и так
  уже останавливается, причина остаётся прежней, но следующая попытка всё равно
  начинается сразу. Идущую задержку перед попыткой просьба прерывает. Следующая попытка —
  без задержки и со сброшенным счётчиком неудач: новая сеть — новый счёт. Просьба одна на
  место: две до исполнения — один перезапуск; просьбу, пришедшую между попытками, забирает
  следующая попытка — она и есть перезапуск.

## 09а. Специфика Windows

Почти всё — из qwdtt-cli (его §09), с двумя отличиями:

- **Разрешение в WFP — двум программам.** Правила «свой процесс» в защите DNS и
  kill-switch пишутся для app ID и `csqtt-cli.exe`, и `csqtt-core.exe`: DNS к VK и TURN
  идут из ядра.
- **DNS меняется на ходу.** Повторный `TUNCONF` меняет DNS адаптера
  (`SetInterfaceDnsSettings`) и пересобирает фильтры защиты DNS под новые адреса.
  Переход — без мига без защиты, тем же порядком «новые от тяжёлых к лёгким, старые от
  лёгких к тяжёлым».

Права, мьютекс второго запуска, маршруты `/1`, защита DNS фильтрами WFP, kill-switch и
форки зависимостей (`tailscale/wf`, `go-webview2`) — без изменений.

**Сборка ядра.** Цель `x86_64-pc-windows-msvc`, нужен MSVC (Visual Studio или Build Tools с
C++); консоль разработчика не нужна — cargo и `cc` находят его сами. NASM и CMake не
нужны: зависимости включают у `aws-lc-sys` готовые объекты NASM (`prebuilt-nasm`), а
собирает он без CMake. Пути машины сборки в бинарь не попадают: `buildcore` переписывает
их для rustc (`--remap-path-prefix`) и для `cl.exe` (`/d1trimfile`, в длинной и короткой
форме 8.3 — `aws-lc-sys` отдаёт пути исходников в ней).

**Поставка.** Zip: `csqtt-cli.exe`, `csqtt-core.exe`, `wintun.dll` с лицензией,
`csqtt-cli.example.toml`, `LICENSE.txt` (MIT, лицензия оболочки), `LICENSE-core.txt`
(PolyForm NC), `THIRD_PARTY_NOTICES.txt` (зависимости Go и Rust), `README.md`.

## 09б. Специфика Linux

Из qwdtt-cli (его §09а): root через `sudo` с файлами и браузером от имени вызвавшего,
блокировка второго запуска абстрактным сокетом, netlink без `ip` и `nft`, DNS системы
тремя способами, таблица nftables с `owner`.

- **Метка ядра.** Пропуск в таблице защиты DNS и kill-switch — по `SO_MARK`. Метку
  выбирает оболочка, ядро ставит её на свои сокеты (П3). Ядро под `sudo` работает с
  правами root, как оболочка, поэтому `CAP_NET_ADMIN` для метки у него есть. Сокетам
  `primp` (точки 4–5) метку ставит пропатченный коннектор (§06): их HTTPS к VK нужен
  ядру и при закрытом kill-switch. `-mark` ядро получает, только если таблица защиты
  открылась: без таблицы метку пропускать некому, а без `CAP_NET_ADMIN` ядро с ней не
  стартовало бы вовсе. `-bind-if` — всегда, когда трафик системы идёт в туннель.
- **`sudo`.** Файл настроек и секреты остаются у вызвавшего: связку ключей его сеанса
  `csqtt-cli` открывает через служебную команду самого себя, запущенную от его имени;
  `Main` принимает её первым делом, до разбора команд и до меню, поэтому `sudo csqtt-cli`
  (меню) работает так же, как `sudo csqtt-cli connect`. Окно капчи — тоже от его имени.
  Меню без root само зовёт `sudo -- <csqtt-cli> menu -config <путь> -connect=<профиль>` в
  том же терминале и ждёт его (§10); путь — всегда: `XDG_CONFIG_HOME` меню `sudo` не
  передаёт.
- **Адаптер мимо оболочки.** Пакеты `tun` идут между ядром и `/dev/net/tun` напрямую
  (Р4), оболочка их не видит.
- **Kill-switch** — как в qwdtt-cli: второй набор правил той же таблицы,
  `linuxsys.DNSGuard.Lockdown` («закрыто»: сокеты с меткой, loopback, DHCP, ND и RA,
  локальная сеть; DNS — никуда, даже к локальной сети). `cli` открывает таблицу до первой
  попытки и ставит «закрыто» сразу; обёртка `killSwitchGuard` отдаётся `Tun` вместо
  защиты: её `Enable` — защита DNS, `Disable` (`Suspend`, `Close`, отказ `Start`) —
  снова «закрыто». Включён по умолчанию; выключают `kill_switch = false` в профиле
  (`profile set -kill-switch=false`) и `-no-kill-switch` на запуск. Не открылась таблица
  или не встало «закрыто» — отказ подключаться с подсказкой; с `-allow-leak` —
  предупреждение и работа без того, что не включилось (отказ правил посреди сеанса —
  строка, а не сбой попытки; не встало «закрыто» между попытками — правила снимаются
  целиком, со строкой). IPv6 и в «закрыто», и при поднятом туннеле — как IPv4: локальная
  сеть, ND и DHCPv6 проходят, DNS к ним — нет; при поднятом туннеле IPv6 наружу закрыт
  (§05). Общие списки — `localNets` и служебные протоколы хоста в `linuxsys`.
- **Обратный фильтр.** Ответы на привязанные сокеты ядра приходят на физический
  интерфейс, а обратный маршрут к источнику ведёт в туннель, и строгий `rp_filter` их
  отбрасывает. Это проверено пробой W1. Как и в qwdtt-cli, оболочка `sysctl` не меняет, а
  до подключения отказывает с подсказкой `rp_filter=2` (и `-datapath socks`). Смотрится
  значение выбранного интерфейса IPv4 с учётом `all`: ядро Linux берёт большее из двух,
  поэтому нестрогий режим на интерфейсе перекрывает строгий `all`. Не прочлось значение —
  строка, а не отказ. Строгий фильтр у интерфейса, на который сменилась сеть, —
  предупреждение: сеть может смениться ещё раз; `connect` не завершается, попытки идут с
  обычной задержкой и не удаются, пока фильтр строгий.
- **Обратный фильтр IPv6 у firewalld** (`IPv6_rpfilter`), который qwdtt-cli проверял, здесь
  не мешает и не проверяется: маршрутов IPv6 в туннель нет, обратный путь ответов IPv6
  ведёт через тот же физический интерфейс. Ядро IPv6 почти не видит: имена VK оно
  разрешает в A-записи, и ему передаётся один индекс IPv4.

**Сборка ядра.** Цель `gnu`, нужны Rust и gcc; CMake не нужен. `aws-lc-sys` сам
передаёт gcc `-ffile-prefix-map`, rustc получает `--remap-path-prefix` от `buildcore` —
путей машины сборки в бинаре нет. `musl` без правки ядра не собирается: три места в
`udp_batch.rs` (§01). Правка возможна, но смысла в ней мало, пока хватает `gnu`.

Нижняя граница glibc у `csqtt-core` задаётся машиной сборки. Собранный с glibc 2.41, он
требует 2.38 только ради `__isoc23_strtol` и `__isoc23_sscanf`: их подставляют в C-код
`aws-lc` заголовки glibc 2.38 и новее. Всё остальное — не новее 2.34. Поэтому релиз
собирается на системе с glibc старше 2.38 (Ubuntu 22.04 — 2.35). CI собирает ядро там же
и падает, если в `csqtt-core` есть символ glibc новее 2.35.

**Поставка.** `tar.gz` для `amd64` и `arm64`: статический `csqtt-cli`, `csqtt-core` с
целью `gnu` (связан с glibc), лицензии, пример настроек, README.

## 10. Конфиг и секреты

```toml
# %APPDATA%\csqtt-cli\profiles.toml · ~/.config/csqtt-cli/profiles.toml

default_profile = "home"

[vk]                               # вход VK для auto_js, один на файл (§08а)
token_ref      = "dpapi:…"         # access token — секрет vk.token
user_id        = "…"               # id аккаунта, не секрет

[profile.home]
peer           = "203.0.113.10:46000"
password_ref   = "dpapi:…"         # пароль подключения = WRAP-ключ
vk_hashes_ref  = "dpapi:…"
vk_hash_mode   = "manual"          # manual | auto_js: звонок создаёт ядро (§08а)
device_id      = "…"               # создаётся при записи профиля, не меняется
workers        = 18                # кратно 9; не больше 126 и 27 на хеш (auto_js — 72)
obfs           = "audio"           # audio | video
turn_transport = "udp"             # udp | tcp_tls
datapath       = "tun"             # tun | socks
kill_switch    = true              # tun: трафик закрыт, пока туннель не поднят

[profile.home.socks]
listen = "127.0.0.1:1080"
```

- **`device_id`** — постоянный: сервер может закрепить главный пароль за первым
  подключившимся устройством, и новый id на каждый запуск выглядел бы как чужое устройство.
  Его заводит запись профиля (16 шестнадцатеричных знаков, как `ANDROID_ID`
  Android-клиента), дальше он только переписывается; свой можно вписать руками. Профиль,
  написанный руками без него, `connect` перед подключением записывает заново — иначе ядро
  представилось бы серверу как `unknown`.
- **`vk_hash_mode`** — `manual` (или пусто): хеши профиля, `vk_hashes_ref` обязателен;
  `auto_js` — звонок создаёт ядро по входу VK (`[vk]`, §08а), `vk_hashes_ref` не нужен, а
  если задан — остаётся на случай возврата к `manual` (`profile` предупреждает, что хеши не
  используются). Флаг `profile add|set -vk-hash-mode`; `profile add` в `auto_js` хешей не
  спрашивает, а `profile set`, вернувший профиль без хешей к `manual`, спрашивает их сам.
  `connect` в `auto_js` берёт токен по `[vk] token_ref` (без входа — ошибка с подсказкой
  `vk login`), `hashes check` отказывает, меню не показывает пункт ссылок на звонки;
  мастер меню режима не спрашивает.
- **Умолчания:** `peer` без порта — `46000`, `workers` — 18, `datapath` — `tun`,
  `kill_switch` — включён (пишется, только если задан), `obfs` и `turn_transport` — как у
  ядра. `workers` проверяется по правилам ядра (кратно 9, от 9 до
  126); предел 27 на хеш ядро применяет само, и аргумент `-workers` уже урезан
  (`coreproc.NormalizeWorkers`); в `auto_js` предела на хеш нет, а воркеров не больше 72
  (`coreproc.NormalizeWorkersAutoJS`). `socks.listen` — только loopback, как требует `NewSocks`.
- **Ссылки `csqtt://`** — `csqtt://connect?v=2&host=…&peer=…&password=…&hashes=…` и старый
  вид `csqtt://<пароль>@<хост>:<порт>`; разбор — свой, в `config/sharelink.go`, по формату
  панели сервера. `peer` — только порт; значения закодированы `encodeURIComponent`, «+»
  пробелом не считается; хеши — через «+», каждый раскодируется отдельно (`%2B` — часть
  хеша), от одного до шести, повторы выбрасываются. Повтор параметра, пустое поле, `v`
  не `2` — ошибка; неизвестные параметры пропускаются. Как и Android-клиент, принимается
  ссылка, у которой потерялись все `&`. Ссылку при вставке не видно, сообщения об ошибках
  её не повторяют, пароль и хеши сразу уходят в хранилище секретов.
- **Секреты в CLI.** Пароль, хеши и ссылку `csqtt://` команды `profile` спрашивают только
  скрытым вводом (из конвейера — строками stdin); ссылка или значение флага-вопроса
  (`-password=…`) в аргументах — отказ без повтора значения, лишний аргумент в сообщении
  тоже не повторяется. `profile show` печатает только, где лежит секрет, читается ли он и
  сколько хешей. Хеши хранятся разобранными, через запятую, не больше шести.
- **`connect [флаги] [профиль]`**: `-datapath tun|socks` — режим на этот запуск (без
  флага — из профиля); `-no-kill-switch` — kill-switch выключен на этот запуск;
  `-allow-leak` — подключаться, даже если защита DNS и kill-switch не включились (поля в
  профиле у него нет: согласие на утечку — на один запуск); `-v` — подробно: журнал ядра,
  datapath и капчи; `-config` — другой файл настроек. `-no-kill-switch` и `-allow-leak`
  действуют только в `tun`: у `socks` нет ни защиты DNS, ни kill-switch, и флаги, как в
  qwdtt-cli, ему не мешают. `tun` требует root (`sudo csqtt-cli connect`) и пока есть
  только на Linux; отказ — до чтения секретов, с подсказками `sudo` и `-datapath socks`.
- **Мёртвые хеши** профиль сам не меняет — ни `connect`, ни `hashes check`: они называют
  номер хеша в профиле, заменяет хеши человек (`profile set <имя> -hashes`) — или меню.
- **Меню** — `csqtt-cli` без аргументов в терминале (на Windows — двойной щелчок) и
  команда `menu [-config]`; без терминала запуск без аргументов печатает список команд.
  Своей логики у меню нет: оно зовёт то же, что команды (`planConnect` и `plan.run`,
  `storeProfile`, `profile rm`, проверка `hashes check`). Мастер профиля — ссылка
  `csqtt://` или вопросы; секреты — скрытым вводом; конец ввода на любом вопросе — отмена
  без записи. Режим `tun` предлагается первым там, где он работает (`Requires` у
  `datapath.Tun`, как в `connect`), иначе — `socks`. Правка ссылок сначала проверяет
  текущие: закрытые звонки уходят, непроверенные остаются. Закрылись все звонки посреди
  сеанса — меню спрашивает новые и подключается снова. `tun` без поддержки — подсказка
  `connect` и `socks` на этот раз. `tun` без прав — меню само перезапускает одно подключение
  с правами, `menu -connect <профиль>` (меню не показывается, после остановки — выход): на
  Linux через `sudo` в том же терминале, ждёт его и показывается снова; на Windows — окном
  UAC, подключение в новом окне, старое закрывается. Взять права негде (`sudo` нет; на
  Windows учётная запись не администратор — UAC поднял бы другого пользователя с чужими
  `%APPDATA%` и секретами) — `socks` на этот раз. Сигналы меню разбирает само: Ctrl+C во
  время подключения возвращает в меню, второй, пока ядро останавливается, убивает ядро
  (§09), в меню — закрывает его; SIGTERM и SIGHUP снимают туннель и закрывают меню. Пока идёт подключение, запущенное через `sudo`, сигналы
  разбирает оно, а SIGTERM и SIGHUP закроют меню после него.
- **Секция `[vk]`** — вход в VK для `auto_js` (§08а), одна на файл, а не на профиль; её
  пишут `vk login` и `vk logout`, в файле она идёт до профилей и пишется, только если не
  пуста. `vk login` проверяет файл до окна, а пишет в копию, прочитанную после него: пока
  окно открыто, файл могли поменять другие команды. `token_ref` — ссылка на access token в том же хранилище, что пароль профиля, под
  именем `vk.token` (с точкой, как `<профиль>.password`: в имени профиля точки нет).
  `user_id` — id аккаунта, только цифры; не секрет, его показывает `vk status`.
  `token_ref`, не похожий на ссылку `<хранилище>:<идентификатор>`, — ошибка без значения в
  тексте (скорее всего, это сам токен); ключи `token`, `access_token`, `vk_token` —
  ошибка с подсказкой про `vk login`. Версии до A2 файл с `[vk]` не примут, как и любое
  новое поле.
- Неизвестный ключ — ошибка; секрет в самом TOML — ошибка с подсказкой, куда его класть.
  Файл пишется целиком из структуры, пустые поля не записываются. Всё — как в qwdtt-cli.
- Поля §04 сверх этой схемы (`turn_host`, `fingerprint`, `client_ids`,
  `captcha_mode`) в профиль пока не заведены: появятся с задачей, которой понадобятся.
  Старые файлы при этом останутся годными.

## 12. Этапы

### Э0. Фундамент — 1–2 дня

Модуль Go, перенос пакетов из qwdtt-cli без кода qWDTT, `scripts/vendorcore` для Rust
и `core/` из апстрима 2.1.9, `scripts/buildcore`. Сборка `csqtt-core` на Windows и под
Linux (`gnu` и `musl`, `amd64` и `arm64`) — выяснить, что нужно `aws-lc-rs` и не мешают
ли участки ядра под `cfg(target_os = "android")`. CI: тесты Go и `cargo test` ядра.

### Э1. Подключение без прав — `socks`, Windows и Linux

`coreproc` (запуск, события, команды, Job Object / Pdeathsig), правки П1, П2, П5, канал
loopback, `socks` на netstack, профили и секреты, окно капчи, команда `hashes`. Итог:
браузер через SOCKS5 ходит в сеть через сервер CSQTT.

### Э2. Системный VPN на Windows

`tun` на Wintun ↔ loopback, правка П3 (выбор способа для `primp`), маршруты, DNS со сменой
на ходу, защита DNS и kill-switch с двумя app ID, слежение за сетью и замер
`BIND_IF` против перезапуска.

### Э3. Linux

`tun` с дескриптором у ядра, правки П4 и П6, метка `SO_MARK`, nftables, DNS системы,
`sudo`. Живая приёмка — в контейнере и на машине, как Э4 qwdtt-cli.

### Э4. Интерактивный режим и релизы

Меню при запуске без аргументов, мастер профиля, ссылки `csqtt://`, проверка ссылок на
звонки, архивы релиза со `SHA256SUMS.txt`.

### Э5. Режим `auto_js`

Вход в VK через OAuth в окне WebView2 или браузере под управлением, токен — в хранилище
секретов, передача ядру через `VK_JS_BOOTSTRAP:`. Перед входом — предупреждение о риске
для аккаунта VK и явное согласие. Поведение и решения — §08а.
