# Архитектура csqtt-cli

Настольный **консольный** клиент к CSQTT: системный VPN поверх TURN-инфраструктуры звонков
VK. Оболочка на Go, ядро CSQTT на Rust — отдельным процессом рядом с ней.

Это только клиент. Установка сервера, веб-панель, обновления, автопауза на Wi-Fi и
исключения приложений остаются в Android-приложении CSQTT. Службы и автозапуска нет:
клиент работает, пока запущен `csqtt-cli connect`.

- **Ядро:** CSQTT 2.1.9, протокол `CSQTT-WIRE-3` ([amurcanov/csqtt](https://github.com/amurcanov/csqtt)),
  PolyForm Noncommercial 1.0.0
- **Свой код:** предварительно MIT, окончательно — до первой публикации (§11)
- **Основа оболочки:** [qwdtt-cli](https://github.com/FreedomCats/qwdtt-cli) — консольный
  клиент к qWDTT того же автора. Из него переносятся меню, профили, секреты, маршруты, DNS,
  kill-switch, окна капчи и слежение за сетью
- **Приоритет платформ:** Windows → Linux. macOS — не планируется
- **План работ:** этапы — §12, задачи по шагам — `plan.md`. Журналы этапов
  (`plan-e*.md`) ведутся локально в `doc/local/` и в репозиторий не входят

## 01. На чём стоит проект

Всё ниже проверено чтением кода ядра 2.1.9, а не взято из описаний.

| Факт | Где в ядре | Следствие |
|---|---|---|
| Туннель L3 без WireGuard: ядро возит сырые IP-пакеты, адрес `/32` и DNS сервер выдаёт строкой `TUNCONF:<ip>:<dns,…>` | `protocol.rs`, `session.rs`, `main.rs` | wireguard-go не нужен. Адаптер настраиваем сами по `TUNCONF` |
| Повторный `TUNCONF` — смена DNS на работающем туннеле | `main.rs` (`config_task`) | DNS адаптера и защиту DNS надо уметь менять на ходу |
| Ядро — отдельная программа: события `__CSQTT_EVENT__|<вид>|<json>` в stdout при `CSQTT_EVENTS=1`, команды в stdin | `events.rs`, `main.rs` | Встраивать как библиотеку не нужно, граница процесса уже есть |
| При `CSQTT_EVENTS=1` закрытие stdin останавливает ядро | `main.rs` (`start_control_input`) | Смерть оболочки = смерть ядра, на всех ОС |
| Режим `-listen`: обмен пакетами по UDP на loopback, ответ — адресу последнего отправителя | `dispatcher.rs` (`read_udp`, `ArcSwapOption`) | Та же дыра, что в qwdtt-cli закрывало решение Р4: один чужой датаграм уводит туннель. Нужна правка П2 |
| Режим `-tun-uds`: ядро получает готовый дескриптор TUN через абстрактный unix-сокет (`SCM_RIGHTS`) | `tun.rs`, `dispatcher.rs` (`run_tun`) | На Linux пакеты могут идти мимо оболочки |
| Сокеты ядра наружу создаются в 5 местах | `dns.rs`, `turn.rs`, `turn_stream.rs`, `auth.rs`, `vk_js_calls.rs` | Обход туннеля — правкой в этих точках (§06) |
| Свой резолвер: UDP :53 к DNS Яндекса, системный — только до первого `TUNCONF` | `dns.rs` | DNS ядра тоже должен идти мимо туннеля; защита DNS обязана его пропускать |
| Пароль и хеши VK передаются аргументами `-password`, `-vk` | `main.rs` (`Arguments`) | Видны любому процессу машины. Нужна правка П1 |
| Капча: ядро печатает `CAPTCHA_SOLVE|<auto\|manual>|<redirect_uri>|<session_token>` и ждёт `CAPTCHA_RESULT|<токен или error:…>` | `captcha.rs` | Окна капчи qwdtt-cli подключаются к этому протоколу (§08) |
| Проверка хешей: `--validate-vk-hashes` печатает `HASH_CHECK:<json>` на каждый хеш и завершается | `main.rs` | Команда `csqtt-cli hashes` без своей логики |
| Воркеры — группами по 9, максимум 126; без `auto_js` — не больше 27 на хеш | `main.rs`, `worker.rs` | Нормализацию числа воркеров повторяем в валидации профиля |
| Ядро собирается под Windows (MSVC) | проверено сборкой в CSQTT-Windows | Сборка под `linux-gnu`/`musl` — проверить в Э0 |

### Что изучено рядом

- **CSQTT-Windows** ([r3waz73/CSQTT-Windows](https://github.com/r3waz73/CSQTT-Windows)) —
  клиент стороннего автора: WinForms, ядро без правок отдельным процессом, мост
  Wintun ↔ UDP на C#. Мимо туннеля ведут маршруты `/32`, адреса TURN выбираются регулярным
  выражением из журнала ядра. Ядро в нём совпадает с апстримом 2.1.9. Полезен как
  проверенный контракт запуска ядра.
- **focsq** ([luminescq/focsq](https://github.com/luminescq/focsq)) — Flutter, ядро собрано
  библиотекой, Wintun и `/dev/net/tun` встроены в само ядро. Мимо туннеля ведут половинные
  маршруты, 13 захардкоженных подсетей VK, `/32` на TURN и NRPT. Полезны правки ядра с
  пометкой `[FOCSQ]`: капча на десктопе, не-IP пакеты в TUN. Дизайн и бренд focsq закрыты
  — не берём.

### Что берём и что нет

**Берём:** ядро CSQTT целиком — авторизацию VK, решатель капчи, TURN по UDP и TCP/TLS,
WRAP-ключ, маскировку `audio`/`video`, FEC, диспетчер и воркеры, проверку хешей.
Режим `auto_js` (ядро само создаёт звонки по токену VK) — отдельным этапом (Э5).

**Не берём:** установку сервера по SSH, веб-панель, автообновление, автопаузу на Wi-Fi,
исключения приложений, виджеты, Android-обвязку капчи.

## 02. Восемь решений

### Р1. Ядро — отдельный процесс, оболочка — на Go

`csqtt-cli` запускает `csqtt-core` (собранный из `core/` клиент CSQTT) и говорит с ним
через аргументы, stdin и stdout — как Android-приложение CSQTT.

**Причина.** Ядро уже устроено как подпроцесс: весь обмен — текстовые команды и события.
Связать Rust-библиотеку с Go — значит включить cgo, а qwdtt-cli собирается без него
(статический бинарь, кросс-сборка одной командой). Переписать на Rust оболочку — это
около 13 тысяч строк кода, уже проверенного на живых прогонах. Отдельный процесс заодно
держит границу лицензий: PolyForm NC у ядра, MIT у оболочки.

**Цена.** В qwdtt-cli библиотека была необходимым условием обхода туннеля: хук на сокеты
ставился изнутри процесса. Здесь этот хук переезжает в само ядро — правкой П3 (Р3).

### Р2. Ядро вендорится целиком, правки — правилами

Исходники `rust-client/` и `shared/` апстрима лежат в `core/` без изменений, поверх —
наши правки П1–П6 (§07). Перенос — `go run ./scripts/vendorcore` из свежего клона апстрима
(соседний каталог `csqtt` или `-upstream <клон>`), как в qwdtt-cli: каждое правило —
шаблон и обязательное число совпадений. Апстрим переписал строку — перенос падает, а не
теряет правку молча. `vendorcore -check` сверяет `core/` с апстримом и правилами. Версия
апстрима — в `core/CORE_VERSION`.

`core/` целиком принадлежит `vendorcore`: своих файлов там нет, лишний файл перенос
удаляет, а `-check` называет. Не трогается только выход сборки cargo
(`core/rust-client/target`). Текст переносится с LF, как он лежит в git апстрима; концы
строк `-check` не различает — git на Windows выкладывает файлы с CRLF. Лицензия ядра
из корня апстрима переносится в `core/LICENSE`: PolyForm требует, чтобы текст лицензии
шёл с каждой копией кода.

**Причина.** Апстрим публикуется снимками без истории изменений, и между версиями меняется
протокол: клиент от прежней ревизии с новым сервером несовместим. Поэтому `rust-client` и
`shared` переносятся только вместе и только целиком. Свои правки должны быть видны
отдельно от кода апстрима, иначе каждое обновление превращается в ручное слияние.
focsq правит ядро изнутри — так делать не будем.

### Р3. Обход туннеля — привязка сокетов ядра к физическому интерфейсу

Когда `tun` забирает весь трафик системы, сокеты ядра — VK, DNS, TURN — тоже попадают в
туннель, и туннель зависит от самого себя. Оболочка выбирает физический интерфейс (как
`netguard` в qwdtt-cli) и передаёт его индекс ядру. Ядро привязывает к нему каждый свой
сокет: на Windows — `IP_UNICAST_IF`/`IPV6_UNICAST_IF`, на Linux — `SO_BINDTOIFINDEX` и
метка `SO_MARK` для защиты DNS (§06).

**Причина.** Оба существующих десктоп-клиента ведут трафик ядра мимо туннеля маршрутами, и
это ненадёжно. Адреса TURN узнаются из журнала уже после того, как сокет открыт; адреса VK
меняются вместе с CDN; захардкоженные подсети устаревают; между новым адресом и
появлением маршрута есть окно, когда пакеты уходят в туннель. С kill-switch маршруты не
помогают вовсе — нужен признак сокета, а не адреса.

### Р4. Канал пакетов: loopback с закреплённым отправителем, на Linux — дескриптор TUN

- **Windows, `tun` и `socks`; Linux, `socks`.** Оболочка держит UDP-сокет на
  `127.0.0.1` и обменивается с ядром сырыми IP-пакетами (режим `-listen`). Правка П2:
  ядро принимает датаграмы только от адреса, переданного при запуске, и только ему
  отвечает. Сокет оболочки на Windows — с `SO_EXCLUSIVEADDRUSE`, чтобы его порт никто не
  занял.
- **Linux, `tun`.** Оболочка создаёт `/dev/net/tun` (`IFF_TUN | IFF_NO_PI`, без
  `IFF_VNET_HDR`), настраивает его и передаёт дескриптор ядру через `-tun-uds` — тем же
  способом, что Android. Пакеты идут между ядром и адаптером напрямую, без копирования
  через оболочку. Правка П4: ядро принимает дескриптор только от процесса с тем же uid
  (`SO_PEERCRED`) — абстрактный сокет открыт всем процессам машины.

**Отвергнуто:** Wintun внутри ядра, как у focsq, — это второй платформенный слой на Rust
рядом с нашим `winsys` и большая правка ядра.

### Р5. Жизнь процесса ядра

Ядро запускается на каждую попытку подключения и завершается с ней. Порядок остановки:
команда `STOP`, ожидание до 3 секунд, затем принудительное завершение. Страховки на
случай падения оболочки:

- stdin ядра — канал оболочки; при `CSQTT_EVENTS=1` его закрытие останавливает ядро на
  любой ОС;
- Windows — Job Object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`: ядро не переживёт оболочку,
  даже если зависнет;
- Linux — `Pdeathsig: SIGKILL` при запуске, вдобавок к проверке `getppid` в самом ядре.

`csqtt-core` ищется только в каталоге `csqtt-cli`, как `wintun.dll` в qwdtt-cli: ни
текущий каталог, ни `PATH` не подходят.

### Р6. Секреты — через stdin, не через аргументы

Правка П1: флаг `-secrets-stdin`, и первой строкой stdin ядро читает
`SECRETS:<base64 json>` с паролем и хешами. Токен VK для `auto_js` и так приходит через
stdin (`VK_JS_BOOTSTRAP:`).

**Причина.** Командную строку процесса видит любой пользователь машины: на Linux —
`/proc/<pid>/cmdline`, на Windows — `Win32_Process.CommandLine`. Пароль подключения — это
WRAP-ключ: из него выводится ключ маскировки, и его утечка равна компрометации всего
транспорта.

### Р7. Капча: решатель ядра, затем окно, затем вручную

Цепочка ядра (`captcha.rs`, режим `auto`): Rust v2 дважды → два автоматических
прогона в WebView по 10 секунд → Rust v2 ещё раз → ручное окно на 60 секунд. Оболочка
отвечает на `CAPTCHA_SOLVE`:

- `auto` — сразу `error:unsupported`: невидимого автопрогона на десктопе нет, ждать
  20 секунд незачем;
- `manual` — окно капчи из qwdtt-cli: WebView2 на Windows, браузер на Chromium под
  управлением (CDP) на Linux, иначе — ручной режим со страницей в браузере системы и
  токеном, который человек переносит в терминал.

Правка П5 поднимает время ручного окна с 60 до 180 секунд: опыт qwdtt-cli показал, что
человеку минуты не хватает.

### Р8. Профили в TOML, секреты — в DPAPI и связке ключей

Как в qwdtt-cli: в `profiles.toml` нет ни одного секрета; пароль, хеши и токен VK
шифруются DPAPI на Windows и лежат в связке ключей (Secret Service) на Linux, без неё — в
`secrets.json` с правами `0600`. Поля профиля — §10.

## 04. Протокол с ядром (`coreproc`)

### Запуск

| Поле профиля | Аргумент ядра |
|---|---|
| `peer` | `-peer <хост:порт>` |
| `workers` | `-n <число>` — уже нормализованное (§10) |
| `obfs` | `-obfs audio\|video` |
| `turn_transport` | `-turn-transport udp\|tcp_tls` |
| `turn_host`, `turn_port` | `-turn`, `-port` — только если заданы |
| `fingerprint` | `-fingerprint` |
| `client_ids` | `-client-ids` |
| `vk_auth_mode` | `-vk-auth-mode` |
| `captcha_mode` | `-captcha-mode` (по умолчанию `auto`) |
| `device_id` | `-device-id` — постоянный на профиль |
| пароль, хеши | через stdin (П1) |
| — | `-listen 127.0.0.1:0` и `-listen-peer` (П2) или `-tun-uds <случайное имя>` |
| — | `-bind-if <индекс>`, на Linux ещё `-mark <метка>` (П3) |

Окружение: `CSQTT_EVENTS=1`. Число потоков рантайма ядро выбирает само по числу воркеров.

### События (stdout)

| Событие | Что делает оболочка |
|---|---|
| `PROCESS {pid}` | запоминает pid для журнала |
| `CONFIG {config}` с `TUNCONF:…` | первое — `Datapath.Start`; следующие — `UpdateDNS` |
| `PROGRESS {kind:"credentials"}` | шаг «VK» в строке состояния |
| `READY {worker}` | первый — «туннель работает»; счётчик живых воркеров |
| `STATS {active, bytes_up, bytes_down}` | строка состояния: воркеры, трафик, скорость |
| `ACTIVE_ZERO` | живых воркеров нет — `Degraded` (§09) |
| `NETWORK_SUSPECT` | серия таймаутов TURN — проверить сеть, `Degraded` |
| `CALL_UNAVAILABLE {hash, code}` | хеш помечается мёртвым (как 954 в qwdtt-cli) |
| `SERVER_RESTART {source:"panel"}` | сервер перезапущен из панели — перезапуск через 4 с, как на Android |
| `ERROR {code, message, fatal}` | `fatal` — конец попытки; `handshake_rejected` и `handshake_timeout` — отказ и молчание сервера, у каждого своя строка для пользователя (тексты — по живым прогонам) |
| `STOPPED` | ядро закончило уборку |

Кроме событий в stdout приходят `CAPTCHA_SOLVE|…` (§08) и `HASH_CHECK:{…}`. Остальной вывод
ядра — журнал на русском в stderr: он идёт в журнал `csqtt-cli` и на экран при `-v`.

### Команды (stdin)

`STOP` · `PAUSE` · `RESUME` · `CAPTCHA_RESULT|<токен>` · `CAPTCHA_RESULT|error:<причина>`.
Добавляет правка П3: `BIND_IF:<индекс>` — новый физический интерфейс без перезапуска
ядра (§06).

Разбор событий и строк — чистая функция с тестами на записях настоящего вывода ядра,
снятых живым прогоном (без адресов и хешей).

## 05. Datapath

Ядро всегда делает одно: принимает сырые IP-пакеты и уносит их через TURN. Datapath
решает, откуда пакеты берутся, и настраивает систему по `TUNCONF`.

```go
type Datapath interface {
    // Link — как ядро получает пакеты: адрес loopback или имя сокета для
    // дескриптора TUN. Известен до запуска ядра.
    Link() Link
    // Start — первый TUNCONF попытки: адрес /32 и DNS.
    Start(ctx context.Context, conf TunConf) error
    // UpdateDNS — повторный TUNCONF с другим DNS, без переподключения.
    UpdateDNS(dns []netip.Addr) error
    Requires() Requirements
    Close() error
}
```

`Requirements`, `Persistent` (`Suspend`), `Reserver` — из qwdtt-cli без изменений по смыслу.

| Реализация | Как доставляет трафик | Права | Охват | Этап |
|---|---|---|---|---|
| `socks` | gVisor netstack + SOCKS5 на `127.0.0.1:1080`, канал — loopback | не нужны | только программы с прокси | Э1 |
| `tun` (Windows) | Wintun (`golang.zx2c4.com/wireguard/tun`, без WireGuard) ↔ loopback | администратор | весь трафик системы | Э2 |
| `tun` (Linux) | `/dev/net/tun`, дескриптор у ядра | root | весь трафик системы | Э3 |

`external` из qwdtt-cli нет: WireGuard в протоколе не участвует.

**`socks`.** В qwdtt-cli netstack стоял за wireguard-go, здесь он сам — конец туннеля:
адрес — из `TUNCONF`, MTU — 1300, как у ядра. SOCKS5 — свой: `CONNECT` в Э1, `UDP ASSOCIATE`
позже. Имена из запросов `CONNECT` резолвятся DNS туннеля через тот же netstack, так что
DNS приложения не идёт мимо туннеля.

**`tun`, общее.** Маршруты — как в qwdtt-cli: `0.0.0.0/1` и `128.0.0.0/1` на адаптер,
исходный шлюз не трогается. Сервер выдаёт только IPv4, но `::/1` и `8000::/1` тоже уходят
на адаптер: иначе весь IPv6 машины шёл бы мимо туннеля с настоящим адресом. Пакеты IPv6
оболочка отбрасывает, не отдавая ядру, и программы откатываются на IPv4. На Linux, где
пакеты идут мимо оболочки, IPv6 не маршрутизируется в туннель вовсе — его закрывает
таблица защиты (`datapath.IPv6Blocker` из qwdtt-cli).

Не-IP пакеты от сервера (служебные ответы) в адаптер не пишутся: на Windows их
отбрасывает мост, на Linux — правка П6 в ядре.

## 06. Обход туннеля

```
ДОРОЖКА 1 — ТРАФИК ПРИЛОЖЕНИЙ

 Приложения → адаптер csqtt-cli → канал пакетов → диспетчер ядра → маскировка → TURN-relay VK → VPS
                                  (loopback или                    9…126 воркеров
                                   дескриптор TUN)

ДОРОЖКА 2 — СОБСТВЕННЫЕ СОКЕТЫ ЯДРА

 Сокеты ядра → привязка к индексу физического интерфейса → Wi-Fi / Ethernet → Интернет
 VK HTTPS, DNS, TURN UDP/TCP        (П3: IP_UNICAST_IF · SO_BINDTOIFINDEX + SO_MARK)
```

### Пять точек

| # | Где | Что | Правка |
|---|---|---|---|
| 1 | `dns.rs` · `query_dns_server` | DNS для имён VK, UDP :53 | привязка перед `send_to` |
| 2 | `turn.rs` · `UdpSocket::bind` | TURN по UDP | привязка после `bind` |
| 3 | `turn_stream.rs` · `TcpStream::connect` | TURN по TCP/TLS | сокет через `socket2`, привязка, затем `connect` |
| 4 | `auth.rs` · `build_browser_client` | API VK по HTTPS | коннектор `primp` |
| 5 | `vk_js_calls.rs` · `Client::builder` | API звонков VK (`auto_js`) | коннектор `primp` |

Точки 1–3 — один вызов `setsockopt` на сокет. С точками 4–5 сложнее: `primp` — обёртка над
форком reqwest, и способ зависит от того, что он умеет. `local_address` у `primp` есть, и
на Windows его может хватить: сокет с привязанным адресом отправляет через интерфейс этого
адреса. На Linux нужен `interface` (`SO_BINDTODEVICE`) или правка коннектора в
`vendor/primp`. Выбрать — первая задача Э2.

Сторож — тест по образцу `TestNetguardCoverage` из qwdtt-cli: он ищет в `core/` все
конструкторы сокетов и падает на каждом новом, не покрытом П3. Новая версия апстрима с
новым сокетом не пройдёт `vendorcore -check`, а не начнёт молча уводить трафик в петлю.

**Смена сети.** Индекс интерфейса выбирает и сторожит `netguard` из qwdtt-cli (уведомления
о маршрутах, сворачивание серий событий). На смену оболочка шлёт `BIND_IF:<новый>`. Новые
сокеты ядра привяжутся к новому интерфейсу, а старые умрут по таймаутам, и воркеры
переподключатся сами. Если этого окажется мало или выйдет медленнее перезапуска,
запасной путь — перезапуск ядра, как в qwdtt-cli. Решается замером в Э2.

**Свои сокеты оболочки.** Прокси окна капчи (§08) ходит к VK сокетами `csqtt-cli` — их
привязывает тот же `netguard`, что в qwdtt-cli.

## 07. Правки ядра

Все правки — правила `scripts/vendorcore` поверх апстрима (Р2). Каждая — с тестом на
Rust в самом ядре и упоминанием в `doc/upstream-proposals.md`, если её стоит предложить
автору.

| # | Правка | Зачем | Этап |
|---|---|---|---|
| П1 | `-secrets-stdin`: пароль и хеши первой строкой stdin | секреты не видны в списке процессов (Р6) | Э1 |
| П2 | `-listen-peer <адрес>`: принимать и отвечать только ему; порт ядра — в событии | чужой датаграм не уводит туннель (Р4) | Э1 |
| П3 | `-bind-if`, `-mark`, команда `BIND_IF:`: привязка сокетов в 5 точках | обход туннеля (Р3, §06) | Э2 |
| П4 | проверка `SO_PEERCRED` при приёме дескриптора TUN | чужой процесс не подменит TUN (Р4) | Э3 |
| П5 | ручное окно капчи — 180 с вместо 60 | человеку не хватает минуты (Р7) | Э1 |
| П6 | не-IP пакеты не пишутся в TUN и не роняют запись | ответ сервера не валит туннель (по опыту focsq — проверить на 2.1.9) | Э3 |

Правки меняют только интерфейс запуска и сокеты. Протокол и формат пакетов не трогаются:
сервер не отличает csqtt-cli от Android-клиента.

## 08. Капча

Решатель — в ядре (Р7), окна — из qwdtt-cli (`internal/captcha`): WebView2 на Windows,
браузер под управлением по CDP на Linux, ручной режим везде. Меняется только источник
запроса: вместо вызова из Go-ядра — строка `CAPTCHA_SOLVE` в stdout ядра, ответ —
`CAPTCHA_RESULT` в stdin.

Капча может понадобиться нескольким воркерам сразу, но окно всегда одно: ядро отдаёт
запросы по одному (канал результата в `captcha.rs` один и стоит под замком, лишние ответы
отклоняются). Следующий запрос приходит, только когда прежний решён или вышло время.

Перехват токена в окне пишется заново, по поведению страницы VK. Код Android-клиентов
(`CaptchaWebViewManager.kt` у qWDTT и CSQTT) не переносится из-за лицензии (§11).

**Kill-switch.** Как в qwdtt-cli: окно ходит через локальный прокси `csqtt-cli` (только
`CONNECT` на 443 к доменам VK), сокеты прокси привязаны к физическому интерфейсу, и
kill-switch на время капчи не снимается. В ручном режиме, в браузере системы, он снимается
со строкой в выводе.

## 09. Супервизор

Автомат из qwdtt-cli, состояния — по событиям ядра:

```
Idle ──▶ Starting ──▶ Credentials ──▶ Configuring ──▶ Connected ◀──▶ Degraded
            ▲         (PROGRESS)       (TUNCONF)       (READY)        (ACTIVE_ZERO,
            │                                                          NETWORK_SUSPECT)
            └──── Reconnecting ◀── выход ядра · fatal ERROR · SERVER_RESTART ·
                                   долгий Degraded · смена сети (запасной путь)

Stopping ◀── из любого состояния: Ctrl+C или годных хешей не осталось
```

- Воркеры ядро переподключает само. Перезапуск процесса ядра — только когда ядро
  завершилось, прислало `fatal`, сервер перезапущен из панели или `Degraded` длится
  дольше порога. Порог подбирается живым прогоном.
- Backoff — как в qwdtt-cli: `1 · 2^попытка` секунд, не больше 64.
- `CALL_UNAVAILABLE` исключает хеш из следующих попыток. Годных хешей не осталось —
  остановка с подсказкой, а меню само спрашивает новые ссылки.
- `tun` — `Persistent`: адаптер живёт весь `csqtt-cli connect`, между попытками `Suspend`
  снимает маршруты и защиту DNS (с kill-switch вместо них встаёт «закрыто»). На Linux ядро
  получает новый дубликат дескриптора адаптера на каждую попытку.

## 09а. Специфика Windows

Почти всё — из qwdtt-cli (его §09), с двумя отличиями:

- **Разрешение в WFP — двум программам.** Правила «свой процесс» в защите DNS и
  kill-switch пишутся для app ID и `csqtt-cli.exe`, и `csqtt-core.exe`: DNS к VK и TURN
  идут из ядра.
- **DNS меняется на ходу.** Повторный `TUNCONF` меняет DNS адаптера
  (`SetInterfaceDnsSettings`) и пересобирает фильтры защиты DNS под новые адреса.
  Переход — без мига без защиты, тем же порядком «новые от тяжёлых к лёгким, старые от
  лёгких к тяжёлым».

Права, мьютекс второго запуска, маршруты `/1`, защита DNS фильтрами WFP, kill-switch и
форки зависимостей (`tailscale/wf`, `go-webview2`) — без изменений.

**Поставка.** Zip: `csqtt-cli.exe`, `csqtt-core.exe`, `wintun.dll` с лицензией,
`csqtt-cli.example.toml`, `LICENSE` (MIT), `LICENSE-core.txt` (PolyForm NC),
`THIRD_PARTY_NOTICES.txt` (зависимости Go и Rust), `README.md`.

## 09б. Специфика Linux

Из qwdtt-cli (его §09а): root через `sudo` с файлами и браузером от имени вызвавшего,
блокировка второго запуска абстрактным сокетом, netlink без `ip` и `nft`, DNS системы
тремя способами, таблица nftables с `owner`.

- **Метка ядра.** Пропуск в таблице защиты DNS и kill-switch — по `SO_MARK`. Метку
  выбирает оболочка, ядро ставит её на свои сокеты (П3). Ядро под `sudo` работает с
  правами root, как оболочка, поэтому `CAP_NET_ADMIN` для метки у него есть.
- **Адаптер мимо оболочки.** Пакеты `tun` идут между ядром и `/dev/net/tun` напрямую
  (Р4), оболочка их не видит.

**Поставка.** `tar.gz` для `amd64` и `arm64`: статический `csqtt-cli` и `csqtt-core`
(цель `musl`, если сборка ядра это позволит — Э0), лицензии, пример настроек, README.

## 10. Конфиг и секреты

```toml
# %APPDATA%\csqtt-cli\profiles.toml · ~/.config/csqtt-cli/profiles.toml

default_profile = "home"

[profile.home]
peer           = "203.0.113.10:46000"
password_ref   = "dpapi:…"         # пароль подключения = WRAP-ключ
vk_hashes_ref  = "dpapi:…"
device_id      = "…"               # создаётся при записи профиля, не меняется
workers        = 18                # кратно 9; не больше 126 и 27 на хеш
obfs           = "audio"           # audio | video
turn_transport = "udp"             # udp | tcp_tls
datapath       = "tun"             # tun | socks

[profile.home.socks]
listen = "127.0.0.1:1080"
```

- **`device_id`** — постоянный: сервер может закрепить главный пароль за первым
  подключившимся устройством, и новый id на каждый запуск выглядел бы как чужое устройство.
- **Ссылки `csqtt://`** — `csqtt://connect?v=2&host=…&peer=…&password=…&hashes=…` и старый
  вид `csqtt://<пароль>@<хост>:<порт>`; разбор — в `config/sharelink.go`, как для
  `qwdtt://` в qwdtt-cli: ссылку при вставке не видно, пароль и хеши сразу уходят в
  хранилище секретов.
- Неизвестный ключ — ошибка; секрет в самом TOML — ошибка с подсказкой, куда его класть.
  Файл пишется целиком из структуры, пустые поля не записываются. Всё — как в qwdtt-cli.

## 12. Этапы

### Э0. Фундамент — 1–2 дня

Модуль Go, перенос пакетов из qwdtt-cli без кода qWDTT, `scripts/vendorcore` для Rust
и `core/` из апстрима 2.1.9, `scripts/buildcore`. Сборка `csqtt-core` на Windows и под
Linux (`gnu` и `musl`, `amd64` и `arm64`) — выяснить, что нужно `aws-lc-rs` и не мешают
ли участки ядра под `cfg(target_os = "android")`. CI: тесты Go и `cargo test` ядра.

### Э1. Подключение без прав — `socks`, Windows и Linux

`coreproc` (запуск, события, команды, Job Object / Pdeathsig), правки П1, П2, П5, канал
loopback, `socks` на netstack, профили и секреты, окно капчи, команда `hashes`. Итог:
браузер через SOCKS5 ходит в сеть через сервер CSQTT.

### Э2. Системный VPN на Windows

`tun` на Wintun ↔ loopback, правка П3 (выбор способа для `primp`), маршруты, DNS со сменой
на ходу, защита DNS и kill-switch с двумя app ID, слежение за сетью и замер
`BIND_IF` против перезапуска.

### Э3. Linux

`tun` с дескриптором у ядра, правки П4 и П6, метка `SO_MARK`, nftables, DNS системы,
`sudo`. Живая приёмка — в контейнере и на машине, как Э4 qwdtt-cli.

### Э4. Интерактивный режим и релизы

Меню при запуске без аргументов, мастер профиля, ссылки `csqtt://`, проверка ссылок на
звонки, архивы релиза со `SHA256SUMS.txt`.

### Э5. Режим `auto_js`

Вход в VK через OAuth в окне WebView2 или браузере под управлением, токен — в хранилище
секретов, передача ядру через `VK_JS_BOOTSTRAP:`. Перед включением — предупреждение о
риске для аккаунта VK (на Android ему посвящён отдельный диалог).

## 13. Риски

| Риск | Оценка | Что делаем |

| Апстрим меняет протокол, старый клиент несовместим с новым сервером | высокая | Р2: ядро переносится целиком, правки — правилами с проверкой; `CORE_VERSION`; README называет совместимую версию сервера |
| Апстрим публикуется снимками без истории — правки не видно | высокая | `vendorcore` сравнивает дерево со снимком; наши правки отделены от кода апстрима |

| Антивирус реагирует на два неподписанных exe, один из которых создаёт адаптер | средняя | Как в qwdtt-cli: подпись релизов; до неё — предупреждение в README |
